1 章节主旨

核心一句话：通过 MCP 标准协议，让 Agent 能动态发现和调用外部服务提供的工具，而不需要自己手写每个工具的实现。

解决了什么问题：s01 到 s18，Agent 的所有工具都是手写的——bash、read_file、write_file、create_task、spawn_teammate、create_worktree……每个工具的定义和执行逻辑都是硬编码在代码里的。但真实世界中有大量外部服务（Jira API、GitHub API、部署系统、Notion 知识库），不可能为每个都手写工具代码。

解决方案：MCP（Model Context Protocol）——一个标准化协议，外部服务只要实现它，Agent 就能通过 connect_mcp 发现工具，通过 assemble_tool_pool 把 MCP 工具和内置工具混在一起用。

课程原话："外接工具, 标准协议" — 发现、组装、调用，Agent 不需要知道工具是谁写的。

核心思想转变

s01-s18: 内置工具全部手写，工具池固定不变 s19: 内置工具 + MCP 工具动态组装，工具池可以扩展 connect_mcp("docs") → MCPClient 发现 2 个工具 connect_mcp("deploy") → MCPClient 发现 2 个工具 assemble_tool_pool() → [bash, read_file, ..., mcp__docs__search, mcp__docs__get_version, mcp__deploy__trigger, mcp__deploy__status]

3 MCP 是什么：外部服务，标准协议

一句话：MCP（Model Context Protocol）是一个标准化协议，让不同的外部服务把自己的能力以"工具"的形式暴露给 LLM 调用。

内置工具 vs MCP 工具

维度内置工具MCP 工具
谁写的Agent 开发者手写外部服务提供者实现
例子bash、read_file、write_fileGitHub 的 create_pr、数据库的 query
存在形式硬编码在代码里通过 MCP 协议动态发现
工具池固定不变可扩展——连上新服务器就加新工具
┌─────────────────────────────────────────────┐ │ LLM Agent (s19) │ │ │ │ 内置工具: bash, read_file, write_file... │ │ ← Agent 自己写的 │ │ │ │ MCP 工具: │ │ mcp__docs__search ─────────────────┐ │ │ mcp__deploy__trigger ─────────────────┤ │ │ mcp__deploy__status ─────────────────┤ │ │ ← 外部服务通过 MCP 协议暴露的 │ │ └───────────────────────────────────────────┼────┘ │ 通过 MCP 协议连接 │ │ ┌──────────────┐ ┌──────────────┐ │ docs 服务器 │ │ deploy 服务器 │ │ (文档服务) │ │ (部署服务) │ │ search │ │ trigger │ │ get_version │ │ status │ └──────────────┘ └──────────────┘

真实世界中 MCP 服务器的例子

  • GitHub MCP → create_pr、list_issues、review_code
  • 数据库 MCP → query、run_migration、list_tables
  • Slack MCP → send_message、list_channels、create_channel
  • Jira MCP → create_issue、search_issues
教学版 vs 真实版：教学版用 Python 函数 mock 了 MCP 服务器的行为（没有网络通信）。真实 MCP 通过 stdio 子进程或 HTTP 与远程服务器通信，用 JSON-RPC 格式收发请求。Mock 的好处是不依赖外部服务就能跑通流程。

4 MCPClient 类详解

class MCPClient:
    """Discovers and calls tools on an MCP server (mock for teaching)."""
    def __init__(self, name: str):
        self.name = name
        self.tools: list[dict] = []
        self._handlers: dict[str, callable] = {}

    def register(self, tool_defs: list[dict],
                  handlers: dict[str, callable]):
        self.tools = tool_defs        # 工具定义（给 LLM 看的 schema）
        self._handlers = handlers     # 处理函数（给代码执行的逻辑）

    def call_tool(self, tool_name: str, args: dict) -> str:
        handler = self._handlers.get(tool_name)
        if not handler:
            return f"MCP error: unknown tool '{tool_name}'"
        try:
            return handler(**args)       # 字典解包成关键字参数
        except Exception as e:
            return f"MCP error: {e}"

字段说明

字段类型含义
self.namestr服务器名字，如 "docs"、"deploy"
self.toolslist[dict]工具定义列表，格式和 Anthropic API 的 tools 参数一致
self._handlersdict[str, callable]工具名 → 处理函数，收到 LLM 调用请求时查这个字典来执行

callable 类型注解

dict[str, callable] 的意思是：字典的键是字符串，值是"任意可调用对象"（函数、lambda、实现了 __call__ 的类实例等）。它只是一个类型注解（文档作用），不影响运行。

handler(**args) 拆解

步骤表达式结果
1假设 args = {"query": "python"}—
2handler(**args)等价于 handler(query="python")
3实际 handler 是 lambda query: ...参数 query 拿到 "python"

register() 是一次性注册

self.tools = tool_defs 是直接替换，不是 extend 追加。重复调用 register 会覆盖之前的全部工具。

call_tool 的三层保护

  1. 工具不存在 → dict.get() 返回 None → 友好错误信息
  2. 参数正确 → handler(**args) 正常执行
  3. 执行异常 → try/except 兜底，返回错误字符串，不崩溃

5 Mock 服务器工厂

全局变量与辅助函数

mcp_clients: dict[str, MCPClient] = {}   # 已连接的 MCP 服务器缓存
_DISALLOWED_CHARS = re.compile(r'[^a-zA-Z0-9_-]')

def normalize_mcp_name(name: str) -> str:
    """Replace non [a-zA-Z0-9_-] with underscore."""
    return _DISALLOWED_CHARS.sub('_', name)
代码解释
mcp_clients全局字典，缓存已连接的 MCP 客户端。键是服务器名，值是 MCPClient 实例。既防重复连接，又给 assemble_tool_pool 提供数据源
normalize_mcp_name把所有非 a-zA-Z0-9_- 的字符替换成下划线。如 "my-server@v2" → "my-server_v2"，防止工具名中包含特殊字符导致 API 报错

_mock_server_docs — 文档服务器

def _mock_server_docs():
    client = MCPClient("docs")
    client.register(
        tool_defs=[
            {"name": "search", "description": "Search documentation. (readOnly)",
             "inputSchema": {"type": "object",
                             "properties": {"query": {"type": "string"}},
                             "required": ["query"]}},
            {"name": "get_version", "description": "Get API version. (readOnly)",
             "inputSchema": {"type": "object", "properties": {},
                             "required": []}},
        ],
        handlers={
            "search": lambda query: f"[docs] Found 3 results for '{query}'",
            "get_version": lambda: "[docs] API v2.1.0",
        })
    return client

MOCK_SERVERS 注册表

MOCK_SERVERS = {
    "docs": _mock_server_docs,      # 存的是函数本身，不是调用结果
    "deploy": _mock_server_deploy,
}

这是一个工厂字典——值不是 MCPClient 实例，而是创建实例的函数。每次调用工厂函数（如 _mock_server_docs()）都创建一个全新的 MCPClient 实例。想加新服务器只需要往这个字典加一条。

教学版的固定返回：Mock 服务器返回的是假结果，比如 "[docs] Found 3 results for 'python'"。它不会真的查文档——只是模拟"流程能跑通"。就像驾校模拟器，教你流程，不真的上路。

6 connect_mcp — 连接与发现

def connect_mcp(name: str) -> str:
    if name in mcp_clients:                        # ① 防重复连接
        return f"MCP server '{name}' already connected"
    factory = MOCK_SERVERS.get(name)              # ② 查工厂函数
    if not factory:
        available = ", ".join(MOCK_SERVERS.keys())
        return f"Unknown server '{name}'. Available: {available}"
    mcp_client = factory()                        # ③ 创建客户端（工厂模式）
    mcp_clients[name] = mcp_client                # ④ 存入全局缓存
    tool_names = [t["name"] for t in mcp_client.tools]
    print(f"  \033[31m[mcp] connected: {name} → {tool_names}\033[0m")
    return (f"Connected to MCP server '{name}'. "
            f"Discovered {len(mcp_client.tools)} tools: {', '.join(tool_names)}")
┌─────────────────────────────────────────────┐ │ connect_mcp 流程图 │ │ │ │ 输入: name = "docs" │ │ │ │ ┌─ 已连接过？ ──→ "already connected" │ │ │ │ │ ├─ 有工厂函数？ ──→ "Unknown server" │ │ │ │ │ └─ 创建客户端 → 存入缓存 → 打印日志 → 返回 │ │ │ │ 每个服务器只创建一次 MCPClient 实例 │ │ mcp_clients 字典做了缓存 │ └─────────────────────────────────────────────┘
步骤代码作用
①if name in mcp_clients防重复连接——已存在就直接返回
②MOCK_SERVERS.get(name)查找工厂函数，找不到给友好提示（列出可用服务器）
③factory()调用工厂函数，创建新的 MCPClient 实例（此时 register 已完成）
④mcp_clients[name] = mcp_client存入全局缓存，供后续 assemble_tool_pool 遍历
为什么需要工厂函数？封装和隔离。如果不使用工厂函数，connect_mcp 里就要写 if name == "docs": client = MCPClient(...); client.register(...)，每加一个服务器就多一段 elif，函数会变得臃肿。工厂函数把"每个服务器怎么建"的逻辑拆分到各自的函数里。

7 assemble_tool_pool — 动态工具池组装

这是整个 MCP 系统的核心函数。它把"内置工具"和"所有已连接的 MCP 工具"合并成一个统一的工具池，返回 (tools列表, handlers字典)。

def assemble_tool_pool() -> tuple[list[dict], dict]:
    """Assemble builtin tools + all MCP tools into one pool."""
    tools = list(BUILTIN_TOOLS)                  # ① 复制内置工具
    handlers = dict(BUILTIN_HANDLERS)            # ② 复制内置处理器

    for server_name, mcp_client in mcp_clients.items():
        safe_server = normalize_mcp_name(server_name)  # ③ 规范化服务器名
        for tool_def in mcp_client.tools:
            safe_tool = normalize_mcp_name(tool_def["name"])  # ④ 规范化工具名
            prefixed = f"mcp__{safe_server}__{safe_tool}"     # ⑤ 加前缀

            tools.append({
                "name": prefixed,
                "description": tool_def.get("description", ""),
                "input_schema": tool_def.get("inputSchema", {}),
            })

            handlers[prefixed] = (                    # ⑥ 注册桥接 lambda
                lambda *, c=mcp_client, t=tool_def["name"], **kw:
                c.call_tool(t, kw))

    return tools, handlers

逐行拆解

行号代码作用
①list(BUILTIN_TOOLS)复制内置工具列表，防止后续 .append() 污染原始数据
②dict(BUILTIN_HANDLERS)复制内置处理器字典，同上
③normalize_mcp_name(server_name)规范化服务器名，如 "my-server" → "my-server"（不变）
④normalize_mcp_name(tool_def["name"])规范化工具名，如 "search" → "search"
⑤f"mcp__{safe_server}__{safe_tool}"拼出带命名空间前缀的工具名，避免不同服务器的同名工具冲突
⑥lambda *, c=..., t=..., **kw: c.call_tool(t, kw)创建桥接 lambda——用默认参数快照当前值，解决闭包陷阱

为什么加 mcp__ 前缀？

  • 防命名冲突：不同服务器的工具可能同名（比如 docs 和 deploy 都有 status），前缀让名字唯一
  • 可溯源：LLM 看到 mcp__docs__search 就知道这个工具来自 docs 服务器

键名映射问题

MCP 工具定义用 inputSchema（驼峰），而 Anthropic API 用 input_schema（蛇形）。这里直接照搬 MCP 的键名到 input_schema 字段上——相当于做了重命名。

一句话总结 assemble_tool_pool：每次调用都重新读 mcp_clients 字典，把内置工具 + 当前所有已连接的 MCP 工具合并成一个新列表返回。不缓存，所以每次都是最新的。

8 闭包陷阱深度解析

问题：在循环中创建 lambda，lambda 里引用了循环变量，导致所有 lambda 都拿到循环结束后的最后一个值。

错误示例

# ❌ 闭包陷阱 —— 所有 lambda 都返回 "deploy/status"
items = [("docs", "search"), ("deploy", "trigger")]
handlers = {}

for server, tool in items:
    handlers[f"tool_{tool}"] = lambda **kw: f"{server}/{tool}"

print(handlers["tool_search"]())      # ❌ "deploy/trigger" 而不是 "docs/search"
print(handlers["tool_trigger"]())    # ❌ "deploy/trigger"

为什么？

Python 闭包中的自由变量（没有默认值的变量引用）是延迟绑定的——lambda 里引用的不是"变量的值"，而是"变量名本身"。调用时才会去查这个变量名当前指向什么值。

循环第1次: server = "docs", tool = "search" 创建 lambda，lambda 记录了"去查 server 和 tool 这两个变量名" 循环第2次: server = "deploy", tool = "trigger" server 和 tool 的指向变了！ 但之前创建的 lambda 仍然引用"server 和 tool 这两个变量名" 循环结束: server → "deploy" (最后一个值) tool → "trigger" (最后一个值) 调用任意 lambda: 去查 server → "deploy" 去查 tool → "trigger"

正确写法：默认参数快照

# ✅ 正确：用默认参数把当前值"快照"进 lambda
for server, tool in items:
    handlers[f"tool_{tool}"] = lambda *, s=server, t=tool: f"{s}/{t}"
    #                ↑ 默认参数 s=server 在定义时求值，固定了当前值

print(handlers["tool_search"]())      # ✅ "docs/search"
print(handlers["tool_trigger"]())    # ✅ "deploy/trigger"

为什么默认参数能解决？

Python 的默认参数在函数定义时求值（不是调用时）。所以 s=server 在循环的每次迭代的那一瞬间就把 server 的当前值复制到 s 里了，之后 server 怎么变都不影响 s。

写法server 是？取值时机结果
lambda: server自由变量调用时查当前值全部拿到最后一个
lambda s=server: s默认参数定义时固定值各自拿到自己的

代码中的实际应用

handlers[prefixed] = (
    lambda *, c=mcp_client, t=tool_def["name"], **kw: c.call_tool(t, kw))
#            ↑ 默认参数          ↑ 默认参数        ↑ 收集剩余参数
#     固定当前 mcp_client   固定当前工具名    透传给 call_tool
那为什么 Python 不修复这个行为？因为这不是 bug，是 feature。Python 的设计哲学是"一致性"——函数里的变量永远是调用时求值，不管是不是闭包。如果自动"快照"了，会破坏这种一致性，还会导致性能损失和向后兼容问题。绕过去的方法很简单（默认参数），所以 Python 选择不修复。

9 lambda 语法拆解

最核心也最令人困惑的一行：

handlers[prefixed] = (
    lambda *, c=mcp_client, t=tool_def["name"], **kw: c.call_tool(t, kw))

展开成 def

# 等价于：
def _anonymous_handler(*, c=mcp_client, t=tool_def["name"], **kw):
    return c.call_tool(t, kw)

逐部分拆解

部分含义
lambda定义匿名函数的关键字
*分隔符——后面的参数必须用关键字传入，不能用位置传入。如 f(c=obj, t="search") 而不是 f(obj, "search")
c=mcp_client默认参数——在 lambda 定义时把 mcp_client 的当前值固定下来（闭包快照）
t=tool_def["name"]默认参数——在 lambda 定义时把工具名固定下来
**kw收集所有剩余的关键字参数到一个字典里（如 {"query": "python"}）
c.call_tool(t, kw)函数体——调用 call_tool(tool_name, args_dict)

什么是"关键字传入"？没有 * 就不用关键字？

# 位置传入：按顺序填
f(1, 2)            # a=1, b=2

# 关键字传入：指名道姓
f(a=1, b=2)        # a=1, b=2

# 有 *，位置传不行：
def f(*, a, b): ...
f(1, 2)             # ❌ TypeError
f(a=1, b=2)         # ✅ 正确

代码中 * 的意思是：c 和 t 不能用位置传，必须用 c=...、t=... 这种方式。但实际调用中，调用方（Agent）只传 handler(**{"query": "python"})，c 和 t 用默认值，query="python" 被 **kw 吃掉。

加 * 是一种编码规范——告诉读代码的人："c 和 t 不是给外部调用者用的，是我内部固定的"。去掉 * 也能工作。

完整的 **dict 解包和 **kw 打包往返

# 调用方（Agent）：
handler(**{"query": "python"})
# 等价于 handler(query="python")

# 进入 lambda：
lambda *, c=docs_client, t="search", **kw: c.call_tool(t, kw)
# kw = {"query": "python"}  ← **kw 把 query="python" 重新打包成字典

# 执行函数体：
c.call_tool(t, kw)
# → docs_client.call_tool("search", {"query": "python"})

这一趟 **dict 解包 → 参数传递 → **kw 打包 看似多此一举，但好处是：这个 lambda 不关心参数具体叫什么名字、有多少个，任何参数都能原封不动地透传给 call_tool。它是个"万能适配器"。

10 动态工具池 vs 固定工具池

s19 最大的架构变化：工具从固定不变的常量（TOOLS），变成了可以动态扩展的变量（tools）。

s18 固定工具池

# 代码里写死的，永远不会变
TOOLS = [{"name": "bash", ...}, {"name": "read_file", ...}, ...]
TOOL_HANDLERS = {"bash": run_bash, "read_file": run_read, ...}

# agent_loop 里直接引用常量
response = client.messages.create(tools=TOOLS)
handler = TOOL_HANDLERS.get(block.name)

s19 动态工具池

# 每次调用 assemble_tool_pool() 都重新组装
tools, handlers = assemble_tool_pool()
# tools 可能包含: [bash, read_file, ..., mcp__docs__search, ...]

# agent_loop 里引用局部变量
response = client.messages.create(tools=tools)
handler = handlers.get(block.name)

# 在 connect_mcp 之后重新组装
if connect_mcp 被调用:
    tools, handlers = assemble_tool_pool()  # ← 新 MCP 工具加入
    system = assemble_system_prompt(context)  # ← 通知 LLM 有新工具

为什么去掉了 prompt 缓存？

12 常见困惑与 FAQ

Q：MCP 是"外部提供的"还是"Agent 自己写的"？

A：外部提供的。 MCP 是一个标准化协议，让不同的外部服务（GitHub、数据库、Slack 等）把自己的能力以"工具"形式暴露给 LLM。Agent 不需要自己写这些工具，只需要连上对应的 MCP 服务器就能发现并使用。

Q：mock 服务器返回固定字符串（如 "[docs] Found 3 results for 'python'"）是啥意思？

A：因为是 Mock（模拟），不做真正的事。 就像驾校模拟器——踩油门不会真的上路，只是显示速度变了。教学版只关心"流程能不能跑通"，不关心实际搜索结果。真实的 MCP 服务器会做真正的操作（查数据库、调 API 等）。

Q：为什么只有 docs 和 deploy 两个 MCP 服务器？

A：这是教学 demo，不是完整产品。 MOCK_SERVERS 字典就是一个注册表，想加多少就加多少。比如加一个数据库服务器："database": _mock_server_database，然后定义 _mock_server_database() 工厂函数即可。扩展性就是这个系统的设计目标。

Q：实际 MCP 也是把所有工具放在一个 list 里传给 LLM，不区分哪个是谁的吗？

A：对，一样。 LLM 不关心工具"来自哪里"，它只看工具的 name + description 来决定用哪个。不同来源通过命名空间前缀 mcp__{server}__{tool} 区分。当 LLM 返回 tool_use.name = "mcp__docs__search" 时，代码通过前缀路由到对应的 MCPClient。

Q：lambda 是只在 for 循环结束后才执行的吗？就只有 lambda 有这个特性？

A：对，函数体只在调用时才执行。 for 循环里 handlers.append(lambda: server) 只是在"造函数、存起来"，不执行函数体。等 handlers[0]() 调用时才真正去查 server 的值。而且这不是 lambda 独有的，def 定义的函数也一样——所有函数都是定义时记录逻辑，调用时才执行。

Q：**{"query": "python"} 解包变成 query="python"，然后 **kw 又变回 {"query": "python"}，多此一举？

A：不是多此一举。 这一层让 lambda 成为"万能适配器"——它不关心参数具体叫什么、有多少个，任何参数都能原封不动透传给 call_tool。如果 LLM 调用 search(query="python", limit=10)，kw 自动变成 {"query": "python", "limit": 10}，全部传下去。不需要为每个工具写不同的 lambda。

Q：mcp_clients 是个全局字典，会不会不安全？

A：教学简化。 真实产品中 MCP 连接状态会有更好的管理方式（依赖注入、连接池等）。这里用全局字典是最简单的教学演示——assemble_tool_pool 需要遍历它，connect_mcp 需要写入它，全局字典让这两者共享数据最方便。

Q：connect_mcp 也是工具，那 LLM 怎么知道有这个工具？

A：connect_mcp 在 BUILTIN_TOOLS 里定义了。 它和其他内置工具（bash、read_file 等）一样，一开始就在工具列表里。所以 LLM 一开始就知道可以用 connect_mcp("docs") 来连接 MCP 服务器。连接成功后，assemble_tool_pool 重新组装，新工具就加入了。

Q：callable 在类型注解里是啥意思？

A：表示"任意可调用对象"。 也就是任何能写成 xxx() 形式的对象——普通函数、lambda、实现了 __call__ 的类实例等。dict[str, callable] 意思是"键是字符串，值是函数/lambda 等可调用对象"。它只是个类型注解，不影响运行。
