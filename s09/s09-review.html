1 整体架构与核心概念

一句话：记忆系统让 AI agent 可以跨会话记住用户偏好、项目约定等长期信息，而不是每次新会话都从零开始。

核心原则

s09 强调一个关键边界：不是所有信息都该进 memory。只有满足以下条件的才值得保存：

  • 跨会话仍然有价值 — 当前对话结束后，下次重开还能用到
  • 不能轻易从当前仓库状态重新推导 — 比如用户偏好、合规原因等

4 load_all() — 从磁盘加载记忆

代码位置：L71-91

def load_all(self):
    self.memories = {}                              # ① 先清空，保证幂等性
    if not self.memory_dir.exists():
        return

    for md_file in sorted(self.memory_dir.glob("*.md")):    # ② 扫描所有 .md 文件
        if md_file.name == "MEMORY.md":
            continue                                   # ③ 跳过索引文件
        parsed = self._parse_frontmatter(md_file.read_text())
        if parsed:
            name = parsed.get("name", md_file.stem)         # ④ 没 name 就用文件名
            self.memories[name] = {
                "description": parsed.get("description", ""),
                "type": parsed.get("type", "project"),
                "content": parsed.get("content", ""),
                "file": md_file.name                     # ⑤ 记录文件名
            }

    count = len(self.memories)
    if count > 0:
        print(f"[Memory loaded: {count} memories from {self.memory_dir}]")

关键问题解答

Q：为什么 __init__ 和 load_all() 里都有 self.memories = {}？

目的不同：

  • __init__ 中的是初始化，确保刚创建 MemoryManager() 时属性存在
  • load_all() 中的是重新加载前清空，避免多次调用 load_all() 时旧数据和新数据混在一起

如果不先清空，连续调用两次 load_all() 会导致记忆数量翻倍：

mm = MemoryManager()
mm.load_all()     # 加载了 3 条
mm.load_all()     # 不清空的话就变成 6 条

Q：glob("*.md") 是什么用法？

Path.glob() 是 pathlib 的模式匹配方法，类似终端执行 ls *.md。它返回一个生成器（generator），一次遍历后就空了。所以代码中先用 sorted() 把它转成列表再遍历。

Q：md_file 是什么格式？md_file.stem 是什么？

md_file 是 Path 对象。它的几个常用属性：

属性示例值（Path(".memory/prefer_tabs.md")）
.name"prefer_tabs.md" — 完整文件名
.stem"prefer_tabs" — 去掉后缀的主干
.suffix".md" — 文件扩展名
.parentPath(".memory") — 父目录
注意：Path 对象只是"路径的表示"，不代表文件真实存在。只有调用了 .read_text()、.write_text()、.exists() 等方法，才真正与磁盘交互。就像一张写着地址的纸条，不等于那栋房子。

5 load_memory_prompt() — 构建提示词记忆区

代码位置：L93-113

def load_memory_prompt(self) -> str:
    if not self.memories:
        return ""

    sections = []
    sections.append("# Memories (persistent across sessions)")
    sections.append("")

    # 按类型分组展示
    for mem_type in MEMORY_TYPES:                    # user → feedback → project → reference
        typed = {k: v for k, v in self.memories.items() if v["type"] == mem_type}
        if not typed:
            continue
        sections.append(f"## [{mem_type}]")
        for name, mem in typed.items():
            sections.append(f"### {name}: {mem['description']}")
            if mem["content"].strip():
                sections.append(mem["content"].strip())
            sections.append("")

    return "\n".join(sections)

功能

把内存中的记忆格式化为 Markdown 字符串，供注入到系统提示词中。输出示例：

# Memories (persistent across sessions)

## [user]
### prefer_tabs: User prefers tabs for indentation
The user explicitly stated they use tabs for Python code.

## [project]
### api_endpoint: Production API base URL
https://api.example.com

详细解释：字典推导式

typed = {k: v for k, v in self.memories.items() if v["type"] == mem_type}

这行代码是字典推导式（dict comprehension），等同于：

typed = {}
for k, v in self.memories.items():
    if v["type"] == mem_type:
        typed[k] = v

items() 是字典的方法，返回 (key, value) 对的视图：

d = {"a": 1, "b": 2}
for k, v in d.items():
    print(k, v)   # a 1 \n b 2

具体执行例子，假设 mem_type = "user"：

遍历到的 kv["type"]匹配？
"prefer_tabs""user"✅ 加入 typed
"api_base_url""project"❌ 跳过
"likes_detail""feedback"❌ 跳过

结果：只筛选出 type 为 "user" 的记忆。这样可以让记忆按类型分组展示，增加可读性。

6 save_memory() — 保存记忆到磁盘

代码位置：L115-155

def save_memory(self, name: str, description: str, mem_type: str, content: str) -> str:
    if mem_type not in MEMORY_TYPES:
        return f"Error: type must be one of {MEMORY_TYPES}"  # ① 类型校验

    safe_name = re.sub(r"[^a-zA-Z0-9_-]", "_", name.lower())   # ② 净化文件名
    if not safe_name:
        return "Error: invalid memory name"

    self.memory_dir.mkdir(parents=True, exist_ok=True)          # ③ 确保目录存在

    frontmatter = (                                       # ④ 构建 frontmatter
        f"---\n"
        f"name: {name}\n"
        f"description: {description}\n"
        f"type: {mem_type}\n"
        f"---\n"
        f"{content}\n"
    )
    file_name = f"{safe_name}.md"
    file_path = self.memory_dir / file_name
    file_path.write_text(frontmatter)                        # ⑤ 写入文件

    self.memories[name] = {                                # ⑥ 更新内存
        "description": description,
        "type": mem_type, "content": content, "file": file_name
    }

    self._rebuild_index()                                  # ⑦ 重建索引
    return f"Saved memory '{name}' [{mem_type}] to {file_path.relative_to(WORKDIR)}"

逐段详解

文件名净化：re.sub(r"[^a-zA-Z0-9_-]", "_", name.lower())

把记忆名称中所有不能出现在文件名中的"脏"字符替换为下划线：

原 namename.lower()re.sub 后
"User's Preference!@#""user's preference!@#""user_s_preference___"
"API Endpoint URL""api endpoint url""api_endpoint_url"

re.sub(pattern, replacement, string) 是正则替换函数。[^a-zA-Z0-9_-] 中 ^ 在 [] 里表示"取反"，所以匹配任何不是字母、数字、下划线、短横线的字符，替换为下划线。

mkdir(parents=True, exist_ok=True)

参数含义类比
parents=True递归创建父目录。如果 .memory/ 的父目录也不存在，一并创建mkdir -p
exist_ok=True目录已存在时不报错安全创建，有就算了

relative_to() 用法

file_path = Path("/home/user/project/.memory/prefer_tabs.md")
file_path.relative_to(WORKDIR)   # → Path(".memory/prefer_tabs.md")

返回相对路径，让输出信息更简洁，比如 "Saved memory 'prefer_tabs' [user] to .memory/prefer_tabs.md"。

为什么 save_memory 要调用 _rebuild_index()？

为了保证索引文件和实际记忆文件始终保持一致。每次保存新记忆后，都重新生成 MEMORY.md，让它包含最新所有记忆的摘要。如果不调用，索引文件会永远停留在旧状态。

类比：你往书架上放了一本新书（保存 .md 文件），同时也要更新图书目录（MEMORY.md），这样别人查目录时才能找到它。

生成的 .md 文件示例（.memory/prefer_tabs.md）

---
name: prefer_tabs
description: User prefers tabs for indentation
type: user
---
The user explicitly stated they use tabs for Python code.

这里的 --- 包裹的部分叫做 frontmatter，是放在正文前面的结构化元数据，让系统先知道这条记忆叫什么、大致是什么、属于哪一类。

7 _rebuild_index() — 重建索引文件

代码位置：L157-168

def _rebuild_index(self):
    lines = ["# Memory Index", ""]
    for name, mem in self.memories.items():
        lines.append(f"- {name}: {mem['description']} [{mem['type']}]")
        if len(lines) >= MAX_INDEX_LINES:        # 200 行上限
            lines.append(f"... (truncated at {MAX_INDEX_LINES} lines)")
            break
    self.memory_dir.mkdir(parents=True, exist_ok=True)
    MEMORY_INDEX.write_text("\n".join(lines) + "\n")

为什么不加 content？

索引文件的定位是快速一览，就像书的目录只列标题和页码，不会把整章内容都写在目录里。如果想看完整内容，去 .memory/ 下打开对应的 .md 文件。

实际上加了 type：[{mem['type']}] 这部分就是 type，放在方括号里展示。

生成的 MEMORY.md 示例：

# Memory Index

- prefer_tabs: User prefers tabs for indentation [user]
- review_style: User likes detailed reviews [feedback]
- api_endpoint: Production API base URL [project]

8 _parse_frontmatter() — 解析元数据

代码位置：L170-175

def _parse_frontmatter(self, text: str) -> dict | None:
    match = re.match(r"^---\s*\n(.*?)\n---\s*\n(.*?)", text, re.DOTALL)
    if not match:
        return None
    header, body = match.group(1), match.group(2)
    result = {"content": body.strip()}
    for line in header.splitlines():
        if ":" in line:
            key, _, value = line.partition(":")
            result[key.strip()] = value.strip()
    return result

正则详解

r"^---\s*\n(.*?)\n---\s*\n(.*?)"
部分含义
^---以 --- 开头
\s*\n可能有的空白 + 换行
(.*?)捕获组1（header）：非贪婪匹配所有内容，直到遇到 \n---
\n---\s*\n第二个 --- 分隔符
(.*?)捕获组2（body）：非贪婪匹配剩余内容
re.DOTALL让 . 可以匹配换行符

parse 的具体例子

输入：

---
name: prefer_tabs
description: User prefers tabs
type: user
---
Some content here
变量值
match.group(1)（header）"name: prefer_tabs\ndescription: User prefers tabs\ntype: user"
match.group(2)（body）"Some content here"
result{"content": "Some content here", "name": "prefer_tabs", "description": "User prefers tabs", "type": "user"}
partition 比 split 更安全：line.partition(":") 返回 (key, ":", value) 三元组，只在第一个 : 处分隔。如果 description 里包含 :（比如 "time: 10:30"），用 split(":") 会拆出3段，而 partition 只拆成2段，不会出错。

9 DreamConsolidator 总览

代码位置：L178-326

一句话：DreamConsolidator 是记忆的"后台整理机制"，灵感来自"人在快速眼动睡眠（REM）期间大脑会整理、巩固、清理记忆"这一生物学概念。

类常量

常量值含义
COOLDOWN_SECONDS86400（24小时）两次 consolidate 之间至少间隔 24 小时
SCAN_THROTTLE_SECONDS600（10分钟）两次检查之间至少间隔 10 分钟
MIN_SESSION_COUNT5至少积累 5 次会话数据才合并
LOCK_STALE_SECONDS3600（1小时）锁文件超过 1 小时视为过期

4 阶段（教学模拟，无实际处理）

阶段描述文本实际该做什么
1. Orient扫描 MEMORY.md 索引读取索引，了解当前记忆的分类情况
2. Gather读取每个详细文件读取所有 *.md 获取完整内容
3. Consolidate合并相关、移除过时调用 LLM 判断哪些可以合并、哪些过时了
4. Prune将索引控制在 200 行删除超出 MAX_INDEX_LINES 的旧条目
重要：当前 consolidate() 只是打印阶段描述文本，没有真正的处理逻辑。这是教学版本的设计——先搭好框架，后续可以插入真正的 LLM 调用。就像画了一张流程图，标好了每个步骤该干什么，但按钮还没连上真正的机器。

10 should_consolidate() — 7 道关卡

代码位置：L207-248

一句话：逐一检查 7 个条件，全部通过才能执行合并操作。任何一个不通过就立即返回失败原因。
Gate 1: enabled? → ❌ "合并已禁用" Gate 2: 目录有记忆文件? → ❌ "没有记忆文件" Gate 3: 不是 plan 模式? → ❌ "plan模式不允许合并" Gate 4: 距离上次合并 >24小时? → ❌ "冷却中，还剩 X 秒" Gate 5: 距离上次检查 >10分钟? → ❌ "节流中，还剩 X 秒" Gate 6: 会话数 >= 5? → ❌ "会话数不足" Gate 7: 能获取锁? → ❌ "锁被其他进程持有" │ 全部通过 → (True, "All 7 gates passed")

COOLDOWN vs THROTTLE 区别

COOLDOWN_SECONDS (Gate 4)SCAN_THROTTLE_SECONDS (Gate 5)
值86400 秒（24小时）600 秒（10分钟）
限制对象真正执行合并 consolidate()仅仅是检查能否合并 should_consolidate()
类比你每天最多跑一次步你每 10 分钟可以看一下手表评估"现在该跑步了吗？"

为什么需要两个限制？如果只有 24 小时的限制，每次检查都发现"才过了1小时，不行"，退回——但 1 秒后又来检查，又退回……反复浪费资源。所以加一个 10 分钟的"检查频率限制"来避免这个问题。

Bug 提醒：Gate 6 的报错信息写反了——f"need at least {self.session_count} sessions, need {self.MIN_SESSION_COUNT}" 打印的是当前会话数而不是所需的最小会话数。应该是 f"need at least {self.MIN_SESSION_COUNT} sessions, only have {self.session_count}"。

11 consolidate() — 执行 4 阶段合并

代码位置：L250-277

def consolidate(self) -> list[str]:
    can_run, reason = self.should_consolidate()        # ① 先过 7 道关卡
    if not can_run:
        print(f"[Dream] Cannot consolidate: {reason}")
        return []

    print("[Dream] Starting consolidation...")
    self._last_scan_time = time.time()

    completed_phases = []
    for i, phase in enumerate(self.PHASE, 1):            # ② 遍历 4 阶段
        print(f"[Dream] phase {i}/4 : {phase}")
        completed_phases.append(phase)                      # ③ 只记录描述文本

    self._last_consolidation_time = time.time()             # ④ 更新冷却时间
    self._release_lock()                                     # ⑤ 释放锁
    return completed_phases

enumerate(self.PHASE, 1) — 为什么加 1？

enumerate() 同时获取索引和元素。默认从 0 开始，加 1 后从 1 开始，打印时显示 "phase 1/4"、"phase 2/4"……对人类更自然。

写法输出
enumerate(PHASE)"phase 0/4: Orient..."
enumerate(PHASE, 1)"phase 1/4: Orient..." ✅
Bug 提醒：L271 中 self.last_scan_time = time.time() 少了一个下划线（应为 self._last_scan_time），导致 Gate 5 的节流逻辑永远失效——因为 should_consolidate() 检查的是 self._last_scan_time，而这个属性从未被更新。

12 _acquire_lock / _release_lock — PID 锁机制

代码位置：L274-326

一句话：用文件系统做跨进程互斥锁，防止多个进程同时执行合并。锁文件是 .memory/.dream_lock。

锁文件内容格式

"12345:1684567890.123456"
  ↑pid     ↑时间戳

_acquire_lock() 的完整流程

_acquire_lock() │ ├── 锁文件不存在？ │ └── 写入当前 PID:时间戳 → 返回 True（获取锁成功） │ └── 锁文件存在？ ├── 读取 PID 和时间戳 │ ├── 情况 A：锁已过期（>1小时） │ └── 删除旧锁 → 写入新锁 → True │ ├── 情况 B：锁持有者还活着 │ └── os.kill(pid, 0) 不抛异常 → 返回 False │ └── 情况 C：锁文件损坏 └── 捕获异常 → 删除 → 写新锁 → True

os.kill(pid, 0) — 为什么不会杀死进程？

这是 Unix/Linux 中最常用的"探活"技巧。信号编号 0 是特殊信号 SIGNULL，内核只做权限检查和进程是否存在检查，不向进程发送任何信号。

try:
    os.kill(pid, 0)      # 相当于问内核：这个进程还活着吗？
    # 没抛异常 → 进程存在
    return False          # 锁有效，获取失败
except OSError:
    # 抛异常 → 进程已死
    self.lock_file.unlink()   # 清理孤儿锁

unlink() 是 Path 对象的删除文件方法。Unix 设计哲学中文件名是指向文件数据的"链接"（link），删除文件就是解除这个链接（unlink）。

锁文件是怎么产生的？

锁文件不是"天上掉下来的"，是 _acquire_lock() 方法中写进去的：

self.lock_file.write_text(f"{os.getpid()}:{time.time()}")

锁文件的生命周期：_acquire_lock() 写入 → 文件存在磁盘 → _release_lock() 删除

_release_lock() 的安全检查

if int(pid_str) == os.getpid():      # 只有锁是当前进程的才删除
    self.lock_file.unlink()

这个判断防止误删其他进程的锁。只有锁文件中记录的 PID 等于当前进程的 PID 时，才执行删除。

MEMORY_GUIDANCE（L455-474）

# 该存的时候：
- 用户说"我喜欢 tab"             → type: user
- 用户纠正你"不要那样做"          → type: feedback
- 你发现一个非代码可见的项目约定   → type: project
- 你知道了一个外部文档 URL        → type: reference

# 不该存的时候：
- 能从代码直接看出来的（函数签名、文件结构）
- 临时任务状态（当前分支、PR 号）
- 敏感信息（API key、密码）

build_system_prompt()（L476-482）

def build_system_prompt() -> str:
    parts = [f"You are a coding agent at {WORKDIR}. Use tools to solve tasks."]
    memory_section = memory_mgr.load_memory_prompt()
    if memory_section:
        parts.append(memory_section)
    parts.append(MEMORY_GUIDANCE)
    return "\n\n".join(parts)

为什么每次循环都重新构建？如果 AI 在这一轮调用了 save_memory 保存了一条新记忆，下一轮构建 system prompt 时就能把这条新记忆包含进去，AI 立即就能"看到"自己刚刚保存的内容。

build_system_prompt() │ ├── 基础角色设定 │ "You are a coding agent at /home/... Use tools." │ ├── 记忆内容（如果有） │ "# Memories (persistent across sessions)" │ "## [user]" │ "### prefer_tabs: ..." │ └── 记忆使用指南 "When to save memories: ..." "When NOT to save: ..."

14 基础知识点详解

14.1 items() 方法

返回字典中所有 (key, value) 对的视图，用于同时遍历键和值：

d = {"a": 1, "b": 2}
for k, v in d.items():
    print(k, v)   # a 1 \n b 2

# 不调 items() 只能拿到 key
for k in d:       # 等价于 for k in d.keys()
    print(k)     # 只能拿到 a, b

14.2 list() 函数

把一个可迭代对象转成列表。因为 glob() 返回的是生成器，只能遍历一次，转成列表后可以反复使用和取下标：

files = list(self.memory_dir.glob("*.md"))
print(files[0])    # 可以取下标 ✅
print(len(files))  # 可以数个数 ✅

14.3 列表推导式 — 过滤而非删除

memory_files = [f for f in memory_files if f.name != "MEMORY.md"]

这不是在原列表上"删除"元素，而是创建了一个新列表，只包含不符合过滤条件的元素。就像用筛子筛面粉——不是把石头从面粉里拿出来，而是让面粉漏下去，石头留在筛子上。

14.4 mkdir() 参数详解

写法结果
Path("a/b/c").mkdir()如果 a/ 不存在 → 报错。如果 a/b/c/ 已存在 → 报错
Path("a/b/c").mkdir(parents=True, exist_ok=True)安全创建，类似 mkdir -p，目录存在也不报错

14.5 re.sub() 详解

re.sub(pattern, replacement, string) 是正则替换函数。在文件名净化中的应用：

name = "User's Preference!@#"
re.sub(r"[^a-zA-Z0-9_-]", "_", name.lower())
# 结果: "user_s_preference___"

[^a-zA-Z0-9_-] 中 ^ 在 [] 里表示"取反"，所以匹配任何不是字母、数字、下划线、短横线的字符，替换为下划线。确保生成的文件名在任何操作系统上都合法。

14.6 relative_to() 用法

返回路径相对于另一个路径的部分：

file_path = Path("/home/user/project/.memory/prefer_tabs.md")
file_path.relative_to(Path("/home/user/project"))
# 结果: Path(".memory/prefer_tabs.md")
