1 field — 数据类字段的精细控制

代码位置

s06_context_compact.py#L14-15
一句话：field 是 dataclasses 提供的函数，用于对单个字段做精细配置，最常见用途是提供可变类型的默认值。 
from dataclasses import dataclass, field

为什么需要 field？

直接在 dataclass 里写可变默认值（如 []、{}）会导致所有实例共享同一个对象，是一个经典的 Python 陷阱：

# ❌ 错误写法：所有 CompactState 实例共享同一个列表
@dataclass
class CompactState:
    recent_files: list[str] = []  # 不要这样写！

# ✅ 正确写法：每次实例化时都创建一个新列表
@dataclass
class CompactState:
    recent_files: list[str] = field(default_factory=list)

field 的常用参数

参数作用示例
default_factory接收一个无参可调用对象，每次实例化时调用它生成默认值field(default_factory=list)
default提供不可变类型的默认值field(default=42)
init=False该字段不参与 __init__field(init=False)
repr=False该字段不出现在 __repr__ 中field(repr=False)
compare=False该字段不参与比较field(compare=False)
本质：field() 返回一个 Field 对象，dataclass 的装饰器在内部识别这些对象并应用对应的行为。没有 field()，你就无法安全地在 dataclass 中声明列表、字典等可变类型的默认值。

2 CompactState — 压缩状态追踪

代码位置

s06_context_compact.py#L29-L33
一句话：记录压缩的历史状态，让后续压缩决策有据可依。 
@dataclass
class CompactState:
    has_compact: bool = False         # 是否已经执行过完整压缩
    last_summary: str = ""             # 最近一次压缩生成的摘要文本
    recent_files: list[str] = field(default_factory=list)  # 最近操作过的文件（最多 5 个）
字段类型意义
has_compactbool标记是否已做过完整压缩。一开始是 False，执行 compact_history() 后设为 True
last_summarystr保存上一次压缩得出的摘要。如果需要再次压缩，可以在此基础上叠加，而不是从头开始
recent_fileslist[str]一个 LRU 风格的最近文件列表。记录"最近操作过的文件路径"，压缩后告诉 AI "需要重新打开这些文件"

为什么不用 = []？ 因为 Python dataclass 的坑：可变默认值会被所有实例共享。用 field(default_factory=list) 确保每次 CompactState() 都得到一个全新的空列表。

设计意图：压缩不是一次性操作，而是需要持续追踪的状态。知道"之前压缩过没有"、"压缩成了什么"、"最近碰过哪些文件"，才能在下一次压缩时做出更好的决策，而不是每次从零开始。

3.2 track_recent_file — LRU 文件追踪

def track_recent_file(state: CompactState, path: str) -> int:
    if path in state.recent_files:
        state.recent_files.remove(path)    # ① 如果已存在，先移除旧记录
    state.recent_files.append(path)           # ② 追加到末尾（标记为"最新使用"）
    if len(state.recent_files) > 5:
        state.recent_files[:] = state.recent_files[-5:]  # ③ 只保留最后 5 个（最近使用的）
步骤作用
① remove如果路径已在列表中，先移除它——避免重复记录
② append追加到列表末尾，表示"最新使用的文件"
③ 保留后 5 个recent_files[-5:] 切片取最后 5 个元素，[:] 是原地修改（保持同一个列表对象引用）

为什么是 LRU 风格？ 因为列表末尾总是最新的，开头总是最旧的。当列表超过 5 个时，最旧的自动被"挤出"。这就是"最近最少使用"的淘汰逻辑。

3.3 safe_path — 路径安全校验

def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()                   # ① 拼接后解析为绝对路径
    if not path.is_relative_to(WORKDIR):              # ② 检查是否还在工作目录内
        raise ValueError(f"Path escapes workspace: {p}")
    return path
步骤说明
① .resolve()把路径解析为绝对路径，处理掉 ..、.、符号链接
② is_relative_to检查最终路径是否以 WORKDIR 为前缀。防止路径穿越攻击（如传入 ../../etc/passwd）
为什么需要这个？如果 AI 被恶意提示词引导去读 /etc/passwd 或写 ~/.ssh/authorized_keys，safe_path 会拦截！所有涉及文件读写的函数（run_read、run_write、run_edit）都会调用它做检查。

4 第 1 层压缩：大输出落盘

代码位置：L69-87

一句话：当工具输出太大时，不把全文塞进上下文，而是存到磁盘文件，只保留一段预览。 
def persist_larget_output(tool_use_id: str, output: str) -> str:
    if len(output) <= PERSIST_THRESHOLD:    # ≤ 30,000 字符，不做处理
        return output

    TOOL_RESULTS_DIR.mkdir(parents=True, exist_ok=True)  # 创建目录（如果不存在）
    stored_path = TOOL_RESULTS_DIR / f"{tool_use_id}.txt"
    if not stored_path.exists():
        stored_path.write_text(output)               # 完整输出写到磁盘

    preview = output[:PREVIEW_CHARS]                     # 取前 2,000 字符作为预览
    rel_path = stored_path.relative_to(WORKDIR)
    return (
        "<persisted-output>\n"
        f"Full output saved to {rel_path}\n"
        "Preview:\n"
        f"{preview}\n"
        "</persisted-output>"
    )
项目值说明
PERSIST_THRESHOLD30,000超过此字符数的工具输出才会触发落盘
PREVIEW_CHARS2,000保留前 2000 字符作为预览给 AI 参考
存储路径.task_outputs/tool-results/<tool_use_id>.txt以工具调用 ID 为文件名，保证唯一
返回格式XML-like 标记用 <persisted-output> 包裹，AI 能理解这不是完整输出
核心思想：让模型知道"发生了什么"（通过预览），但不用一直背着整份原始大输出。全文没有丢，只是搬到了磁盘。如果需要，AI 可以再通过 read_file 工具读取完整内容。

返回的消息示例

<persisted-output>
Full output saved to .task_outputs/tool-results/toolu_abc123.txt
Preview:
(前 2000 字符...)
</persisted-output>
注意：函数名有拼写错误，应该是 persist_large_output（少了一个 r）。教学代码故意保留，不影响功能。

5 第 2 层压缩：微压缩旧结果

代码位置：L89-111

一句话：保留最近的 N 个工具结果完整，更早的替换为短占位符。

5.1 先找到所有工具结果

def collect_tool_result_blocks(messages: list) -> list[tuple[int, int, dict]]:
    blocks = []
    for message_index, message in enumerate(messages):
        content = message.get("content")
        # 在 Anthropic API 中，tool_result 以 role="user" 返回
        if message.get("role") != "user" or not isinstance(content, list):
            continue
        for block_index, block in enumerate(content):
            if isinstance(block, dict) and block.get("type") == "tool_result":
                blocks.append((message_index, block_index, block))  # 三元组
    return blocks

返回值是三元组列表：(消息索引, 块索引, 块本身)。三个元素分别定位了这个 tool_result 在整个消息列表中的精确位置。

5.2 微压缩执行

def micro_compact(messages: list) -> list:
    tool_results = collect_tool_result_blocks(messages)
    if len(tool_results) <= KEEP_RECENT_TOOL_RESULTS:   # ≤ 3 条，不压缩
        return messages

    for _, _, block in tool_results[:-KEEP_RECENT_TOOL_RESULTS]:  # 除最后 3 条外
        content = block.get("content", "")
        if not isinstance(content, str) or len(content) <= 120:  # 已经很短的就不动
            continue
        block["content"] = "[Earlier tool result compacted. Re-run the tool if you need full detail.]"
    return messages
项目值说明
KEEP_RECENT_TOOL_RESULTS3保留最近 3 个工具结果的完整内容
替换条件长度 > 120 且是字符串短结果本身很小，不值得压缩
替换内容占位提示文本告诉 AI "之前的工具结果已被压缩，如果需要可以重新运行工具"
为什么保留最近 3 条？最新的工具结果很可能正在被 AI 用于下一步推理，不能动。更早的结果已经被 AI"消化"了，可以放心压缩。这条边界（3 条）是教学简化版，生产环境可以动态调整。

6 第 3 层压缩：完整历史摘要

代码位置：L113-158

一句话：前两层还不够时，把整个对话交给 AI 自己总结成摘要，用 1 条消息替换整个历史。

6.1 存档 — write_transcript

def write_transcript(messages: list) -> Path:
    TRANSCRIPT_DIR.mkdir(parents=True, exist_ok=True)
    path = TRANSCRIPT_DIR / f"transcript_{int(time.time())}.jsonl"
    with path.open("w") as handle:
        for message in messages:
            handle.write(json.dumps(message, default=str) + "\n")  # JSONL 格式
    return path
项目说明
存储位置.transcripts/transcript_<unix_timestamp>.jsonl
格式JSONL（JSON Lines）：每行一条 JSON 消息
default=str遇到无法 JSON 序列化的对象时，用 str() 兜底，防止崩溃
目的压缩不可逆，存档以备后查
重要：存档在压缩之前执行。如果摘要信息不足，人类或 AI 可以回头读取这个 JSONL 文件恢复完整历史。

6.2 AI 摘要 — summarize_history

def summarize_history(messages: list) -> str:
    # ① 把对话转成 JSON，只取前 8000 字符（防止请求过大）
    conversation = json.dumps(messages, default=str)[:8000]

    # ② 构造摘要 prompt
    prompt = (
        "Summarize this coding-agent conversation so work can continue.\n"
        "Preserve: \n"
        "1. The current goal\n"
        "2. Important findings and decisions\n"
        "3. Files read or changed\n"
        "4. Remaining work\n"
        "5. User constraints and preferences\n"
        "Be compact but concrete.\n\n"
        f"{conversation}"
    )

    # ③ 让 AI 自己给自己写摘要
    response = client.messages.create(
        model=MODEL,
        messages=[{"role": "user", "content": prompt}],
        max_tokens=2000
    )
    return response.content[0].text.strip()
参数值说明
[:8000]输入截断只取对话的前 8000 字符作为 AI 的输入素材。原因：防止请求过大、节约 token
max_tokens=2000输出限制限制摘要输出最长 2000 tokens（约 1500 英文单词/800 汉字）
5 类保留信息目标/决策/文件/下一步/约束确保压缩后 AI 还能接着干活，而不是从头开始
注意缺陷：[:8000] 只取了对话的开头部分（最早的消息），而对话越靠后通常越重要（最新进度）。这是一个教学版本的简化缺陷，生产环境应该使用更智能的策略，如"保留开头 + 保留结尾 + 压缩中间"。

6.3 完整压缩入口 — compact_history

def compact_history(messages: list, state: CompactState,
                     focus: str | None = None) -> list:
    # ① 先存档
    transcript_path = write_transcript(messages)

    # ② AI 生成摘要
    summary = summarize_history(messages)

    # ③ 追加额外信息：focus 和 recent_files
    if focus:
        summary += f"\nFocus to preserve next: {focus}"
    if state.recent_files:
        recent_lines = "\n".join(f"- {path}" for path in state.recent_files)
        summary += f"\nRecent files to reopen if needed:\n{recent_lines}"

    # ④ 更新压缩状态
    state.has_compact = True
    state.last_summary = summary

    # ⑤ 返回单条消息替换整个历史
    return [{
        "role": "user",
        "content": (
            "This is conversation was compacted so the agent can continue working.\n\n"
            f"{summary}"
        )
    }]

执行流程

原始对话（可能 50,000+ 字符） │ ├──① write_transcript() → 存档到 .transcripts/ │ ├──② summarize_history() → AI 自己写摘要（max 2000 tokens） │ ├──③ 追加 focus + recent_files 信息 │ └──④ 返回 [{role: "user", content: 摘要}] │ ▼ 整个 messages 被替换为这条摘要消息
核心思想：压缩不是删除，而是"换一种表示方式"。最关键的是：当前目标、已完成动作、修改过的文件、关键决定、下一步工作——这些信息在摘要中必须保住，否则压缩就打断了工作连续性。

7 Python 语法细节

7.1 for _, _, block — _ 是什么？

for _, _, block in tool_results[:-KEEP_RECENT_TOOL_RESULTS]:

tool_results 中每个元素是一个三元组 (message_index, block_index, block)。在循环中，我们只关心 block（工具结果本身），不需要前两个索引值。

写法含义
_Python 的通用"垃圾桶变量名"，表示"我故意不要这个值"
_, _, block解包三元组，只取第三个元素，前两个丢弃
最佳实践：用 _ 比用 message_index, block_index, block（然后从不使用前两个变量）更好——它明确告诉读者"这些值是我故意忽略的"，而且不会触发 lint 工具的"未使用变量"警告。

7.2 json.dumps(message, default=str)

handle.write(json.dumps(message, default=str) + "\n")
参数作用
message要序列化的对象（通常是字典）
default=str兜底函数：当 json.dumps 遇到无法序列化的类型（如 Path、datetime、自定义对象）时，调用 str() 将其转为字符串

示例对比：

# 没有 default=str
json.dumps({"path": Path("/tmp/foo")})        # ❌ TypeError!

# 有 default=str
json.dumps({"path": Path("/tmp/foo")}, default=str)  # ✅ {"path": "/tmp/foo"}

7.3 [:8000] 截断 vs max_tokens=2000

这是两个不同维度的限制：

位置代码控制什么为什么
输入json.dumps(messages)[:8000]给 AI 看的素材只取前 8000 字符防止请求过大，防止 AI 被细节淹没
输出max_tokens=2000AI 回复的最大长度（2000 tokens）保证摘要足够精炼，压缩才有意义
原始对话: 50,000+ 字符 │ ▼ 截取前 8,000 字符 prompt: 8,000 字符 │ ▼ AI 阅读后输出精炼摘要 AI 输出: max_tokens=2000 (~2,500 字符) │ ▼ 替代整个历史 压缩后: ~2,500 字符（缩小 20 倍）
但这里有个问题：[:8000] 取的是消息列表的开头，而对话中最新的内容（可能在列表末尾）才是最重要的。后面的 42000+ 字符被直接丢弃了。这是一个教学简化妥协，生产环境应该用更好的采样策略（如保留开头 + 保留结尾，压缩中间）。

8.5 agent_loop 的核心变化

s06 的 agent_loop 不再只是"收消息→调模型→跑工具"，还多了一个关键责任：管理活跃上下文的预算。

s06 的伪代码逻辑变成：

def agent_loop(messages, state):
    while True:
        # 新责任：每次循环先尝试微压缩
        messages = micro_compact(messages)

        # 新责任：检查上下文大小，必要时完整压缩
        if estimate_context_size(messages) > CONTENT_LIMIT:
            messages = compact_history(messages, state)

        # 原有的：调模型→跑工具→收集结果
        response = client.messages.create(...)
        ...
一句话总结：s06 的核心变化不是"加了几个函数"，而是在 agent 的主循环中引入了"上下文预算管理"这一关键责任。这是从 s05 到 s06 最重要的心智模型升级——Agent 不仅要学会做事，还要学会管理自己做事的"工作台空间"。

8.6 教学边界

教程明确说明了这章的教学边界：

  • ✅ 什么该留在活跃上下文里
  • ✅ 什么该搬到磁盘或占位标记里
  • ✅ 完整压缩后，哪些连续性信息一定不能丢
  • ❌ 不讲所有产品化压缩技巧
  • ❌ 不讲跨会话记忆（那是 s09 memory 的范畴）

s06 的目标是建立稳定心智：压缩不是删历史，而是把细节搬走，好让系统继续工作。

9 execute_tool — 为什么不用 lambda 了

代码位置

s06_context_compact.py#L281-292
一句话：s05 的 lambda 字典靠 **block.input 按名字自动匹配参数；s06 需要传 block.id 和 state，这俩不在 block.input 里，lambda 模式就破了。

9.1 s05 的 lambda 为什么能工作

# s05 的定义
TOOL_HANDLERS = {
    "bash":      lambda **kw: run_bash(kw["command"]),
    "read_file": lambda **kw: run_read(kw["path"], kw.get("limit")),
    ...
}

# s05 的调用
handler = TOOL_HANDLERS[block.name]   # 按名字查到函数
output = handler(**block.input)       # 字典展开成关键字参数

**block.input 的作用是把字典展开成关键字参数，按参数名自动匹配。例如：

AI 调用block.input 的值handler(**block.input) 等价于
bash{"command": "ls -l"}run_bash(command="ls -l")
read_file{"path": "foo.py", "limit": 100}run_read(path="foo.py", limit=100)
edit_file{"path": "foo.py", "old_text": "a", "new_text": "b"}run_edit(path="foo.py", old_text="a", new_text="b")

虽然各函数参数不一样，但 ** 展开能自动按名字匹配，所以可以统一用 handler(**block.input) 调用。

9.2 s06 为什么不行了

s06 多了两个必须传、但 block.input 里没有的东西：

参数值在哪儿为什么需要
block.id工具调用的唯一 ID（如 "toolu_abc123"）block 对象本身的属性Anthropic API 要求 tool_result 必须带 tool_use_id，用于配对"调用"和"结果"
stateCompactState 实例主循环维护的变量压缩时 compact_history() 需要 state.recent_files 把最近文件写入摘要

block.id 和 state 都不在 block.input 字典里，没法用 **block.input 传过去。强行用 lambda 你得写成：

# 每个 lambda 都得写 block, state，还要手动取 block.input["xxx"]

# 而且每个 lambda 参数都是 (block, state)，不再是 **kw 了

既然 lambda 的统一接口已经保不住了，干脆用 if/elif 更直接。

9.3 block.id 到底用在哪

看 agent_loop 第 320 行：

results.append({
    "type": "tool_result",
    "tool_use_id": block.id,        # ← 只在这里使用了
    "content": str(output),
})
没干别的，就是：当 AI 调了工具，你把执行结果返回给 API 时，必须带上 tool_use_id 告诉 API "这个结果是对那次调用的回复"。block.id 就是那个配对用的 ID。

至于 run_bash(command, tool_use_id) 这类函数签名里的 tool_use_id 参数——函数体里根本没用到它，是死参数。

9.4 state 到底用在哪

看 agent_loop 第 326 行：

if manual_compact:
    messages[:] = compact_history(messages, state, focus=compact_focus)

compact_history 中：

if state.recent_files:                              # ← 用到了
    recent_lines = "\n".join(f"- {path}" ...)
    summary += f"\nRecent files to reopen if needed:\n{recent_lines}"

state.has_compact = True                            # ← 用到了
state.last_summary = summary                          # ← 用到了
state 的用途：只有 compact 工具被调用时才真正用到。把最近文件列表和压缩状态保存起来，确保压缩后的摘要包含足够的信息让 AI 恢复工作。

至于 run_read(path, tool_use_id, state, limit) 等函数签名里的 state——函数体里同样没用，也是死参数。

上下文窗口模型这一轮能看到的输入容量，不是无限的
活跃上下文当前继续工作时，模型最值得马上看到的那部分内容

大输出落盘工具输出太长时存到磁盘，只保留预览
微压缩旧工具结果替换为简短占位提示

工作连续性压缩后 AI 还能记住目标、已做工作、文件、决策、下一步
压缩 vs Memory压缩解决当前会话太长；Memory 解决跨会话信息保留（s09）
