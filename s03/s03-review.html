1 Python 基础语法速查

📍 enumerate — 同时取索引和元素

for index, raw_item in enumerate(items):

把列表变成 (索引, 元素) 的配对序列：

fruits = ["apple", "banana", "cherry"]
for i, v in enumerate(fruits):
    print(i, v)
# 0 apple
# 1 banana
# 2 cherry

注意：index 和 raw_item 是循环变量名，不是从 items 里取出来的字段。

📍 .get() — 字典的安全取值

raw_item.get("content", "")
参数含义
第一个参数要取的键名（key）
第二个参数键不存在时返回的默认值（可选，不传则返回 None）
d = {"name": "Alice"}
d.get("name")        # "Alice"
d.get("age", "?")     # "?"  ← 键不存在，返回默认值
d["age"]                # KeyError  ← 直接索引会报错

📍 .strip() — 去掉首尾空白字符

去掉字符串开头和结尾的空格、换行 \n、制表符 \t 等：

"  hello world \n  ".strip()  # "hello world"

变体：.lstrip()（去左边）、.rstrip()（去右边）

📍 .lower() — 转小写

统一大小写后再比较，避免大小写不一致的问题：

"Pending".lower()  # "pending"
"PENDING".lower()  # "pending"

2 raw_item 是字典还是 PlanItem 对象？

答案：raw_item 是字典（dict），不是 PlanItem 对象。

关键证据在第 57 行——调用了 .get() 方法：

raw_item.get("content", "")    # ← 字典才有的方法
raw_item.get("status", "pending")
raw_item.get("active_form", "")

如果 raw_item 是 PlanItem 对象，访问属性应该用点号：

raw_item.content   # ✅ 对象用点号
raw_item.get("content")  # ❌ 对象没有 .get() 方法，会 AttributeError
┌─ 外部传入（raw）─────────────┐ ┌─ 内部管理（normalized）──────┐ │ items = [ │ │ self.state.items = [ │ │ { │ → │ PlanItem( │ │ "content": "写单元测试", │ 验证 │ content="写单元测试", │ │ "status": "in_progress" │ 转换 │ status="in_progress", │ │ } │ │ ) │ │ ] │ │ ] │ └──────────────────────────────┘ └──────────────────────────────┘ ↑ raw_item 是这里每个 dict ↑ normalized 里是 PlanItem

数据流：外部传来的 JSON/dict → 验证/清洗 → 转成 PlanItem 对象存入状态

3 render() — 渲染函数详解

作用：把 self.state.items（PlanItem 列表）渲染成人类可读的文本。

状态 → 符号映射

marker = {
    "pending" : "[ ]",
    "in_progress" : "[>]",
    "completed" : "[x]",
}[item.status]

用字典做映射，代替 if-elif 链，更简洁。

进度统计

completed = sum(1 for item in self.state.items if item.status == "completed")

生成器表达式：遍历 → 筛选 → 每个符合条件的生成 1 → sum 求和。

完整输出示例

[>] 写单元测试 (test_foo.py)
[ ] 重构代码
[x] 添加注释

1/3 completed

等价于：

"[>]" + " " + "写单元测试" + " (test_foo.py)"  # 拼接逻辑
"\n".join([...])                                   # 换行合并

4 active_form 是什么？

active_form 代表"当前正在操作的文件/对象"。

在 render() 输出中显示在括号里：

[>] 写单元测试 (test_foo.py)    ← test_foo.py 就是 active_form

只对 in_progress 状态有效——渲染时只在该状态下才追加括号信息：

if item.status == "in_progress" and item.active_form:
    line += f" ({item.active_form})"

名字叫 active_form（活跃表单/文档）而不是 active_file，可能是：

  • 沿用了 Anthropic 官方 Todo API 的字段命名
  • 语义更通用——不一定是"文件"，也可以是正在填的表单、编辑的文档等

6 subprocess.run — 执行系统命令

result = subprocess.run(
    command,            # 要执行的命令字符串
    shell=True,         # 通过 /bin/sh 执行（支持管道 | 、重定向 > 等）
    cwd=WORKDIR,        # 工作目录
    capture_output=True, # 捕获 stdout 和 stderr
    text=True,          # 返回字符串而非字节 b"..."
    timeout=120,        # 超时 120 秒
)
参数作用
shell=True支持管道 |、变量、&& 等 shell 语法
capture_output=True捕获输出到内存，不打印到终端
text=True返回 str 而非 bytes
timeout=120超时后抛 TimeoutExpired 异常

危险命令过滤

dangerous = ["rm -rf /", "sudo", "shutdown", "reboot", "> /dev/"]
if any(d in command for d in dangerous):
    return "Error: Dangerous command blocked"

any() + 生成器：遍历危险关键词列表，只要有一个出现在命令里就拦截。

输出截断

output = (result.stdout + result.stderr).strip()          # 合并 stdout+stderr，去首尾空白
return output[:50000] if output else "(no output)"  # 最多 50000 字符

7 run_write — 为什么先创建父目录？

def run_write(path: str, content: str) -> str:
    file_path = safe_path(path)
    file_path.parent.mkdir(parents=True, exist_ok=True)  # ← 先确保父目录存在
    file_path.write_text(content)                          # ← 再写文件
    return f"Wrote {len(content)} bytes to {path}"
如果不先创建父目录：写入 src/utils/helper.py 时，如果 src/utils/ 不存在，会报 FileNotFoundError。

file_path.parent 一层层拆解：

file_path        # Path("/home/user/project/src/utils/helper.py")
       .parent   # Path("/home/user/project/src/utils")          ← 父目录
       .mkdir(   # 创建这个目录
           parents=True,   # 递归创建：a/b/c 全部不存在时也会一并创建
           exist_ok=True   # 目录已存在时不报错
       )
想写入: src/utils/helper.py │ ┌────▼────┐ │ 安全校验? │ ← safe_path() 防止路径穿越 └────┬────┘ │ ┌────▼─────────────┐ │ 创建父目录 │ │ src/utils/ │ ← 不存在就递归创建 └────┬─────────────┘ │ ┌────▼──────────┐ │ 写入文件 │ │ helper.py │ └────┬──────────┘ │ ┌────▼──────────────┐ │ 返回成功消息 │ │ "Wrote 42 bytes │ │ to src/utils/... │ └───────────────────┘

8 TOOLS — 给 AI 的工具说明书

这是 Anthropic API 的工具定义格式（JSON Schema），告诉 AI 模型可以调用什么工具、每个工具有什么参数。

{                                   # 工具定义 = 给 AI 的说明书
    "name": "bash",                # ① 工具名称
    "description": "Run a shell command.",  # ② 描述（自然语言）
    "input_schema": {                # ③ 参数结构（JSON Schema）
        "type": "object",
        "properties": {               # ④ 具体参数列表
            "command": { "type": "string" }
        },
        "required": ["command"]       # ⑤ 必填参数
    }
}
字段含义
name工具名，AI 在回复中通过这个名字指定调用哪个工具
description自然语言描述，AI 据此判断何时用这个工具
input_schema参数结构定义（JSON Schema 格式）
properties参数名 + 类型
required哪些参数是必填的

s03 新增的 todo 工具定义：

{
    "name": "todo",
    "description": "Rewrite the current session plan for multi-step work.",
    "input_schema": {
        "properties": {
            "items": {
                "type": "array",
                "items": {
                    "properties": {
                        "content": {"type": "string"},
                        "status": {"type": "string", "enum": [...]},
                        "activeForm": {"type": "string"}
                    },
                    "required": ["content", "status"]
                }
            }
        }
    }
}

9 TOOL_HANDLERS ↔ agent_loop 联动

这是整个程序的核心——Agent Loop（代理循环）。

TOOL_HANDLERS：字符串名 → 实际函数的映射表

TOOL_HANDLERS = {
    "bash":       lambda **kw: run_bash(kw["command"]),
    "read_file":  lambda **kw: run_read(kw["path"], kw.get("limit")),
    "write_file": lambda **kw: run_write(kw["path"], kw["content"]),
    "edit_file":  lambda **kw: run_edit(kw["path"], kw["old_text"], kw["new_text"]),
    "todo":       lambda **kw: TODO.update(kw["items"])       # ← s03 新增
}
为什么不用 if-elif 链？因为 AI 返回的是字符串 "bash"，字典映射比 elif 链更干净、更易扩展（加新工具只需加一行）。

agent_loop — 完整 8 步闭环

① 用户输入 │ ▼ ② 把用户消息 + TOOLS 定义一起发给 AI │ ▼ ③ AI 决定要调用哪个工具 block.name == "bash" block.input == {"command": "ls -la"} │ ▼ ④ TOOL_HANDLERS.get("bash") → 找到 run_bash │ ▼ ⑤ handler(**block.input) → run_bash(command="ls -la") │ ▼ ⑥ 拿到执行结果 "file1.txt\nfile2.txt" │ ▼ ⑦ 包装成 tool_result，塞回消息列表，再次发给 AI │ ▼ ⑧ 回到 ②，直到 AI 不再调用工具 → 返回最终回复

核心代码逻辑（[agent_loop](file:///home/zyh/learn-claude-code/s03/s03_todo_write.py#L226-L255)）：

def agent_loop(messages: list):
    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM,
            messages=messages,    # 把消息发给 AI
            tools=TOOLS,          # 告诉 AI 有哪些工具可用
        )
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":  # AI 不再调用工具 → 结束
            return

        results = []
        for block in response.content:           # 遍历 AI 返回的每个 block
            if block.type != "tool_use":          # 跳过文本块
                continue

            handler = TOOL_HANDLERS.get(block.name)  # 找到对应函数
            output = handler(**block.input)          # 调用函数执行

            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,            # 配对 ID
                "content": str(output)
            })

        messages.append({"role": "user", "content": results})  # 结果喂回 AI

AI 回复中的两种 block 类型

response.content = [
    {                               # 类型 1: 文本块 — AI 想说的话
        "type": "text",
        "text": "我先看看当前目录..."
    },
    {                               # 类型 2: 工具调用块
        "type": "tool_use",
        "id": "toolu_abc123",           # 唯一 ID，用于配对结果
        "name": "bash",                  # 工具名
        "input": {"command": "ls"}      # 参数
    },
]

10 ANSI 转义码 — 终端彩色文字

query = input("\033[36ms02 >> \033[0m")

这是 ANSI 转义码，用来在终端里显示彩色文字：

代码含义
\033[转义序列开始（\033 = ESC 字符）
36m设置文字颜色为青色
s02 >> 实际显示的提示文字
\033[0m重置颜色（不加的话后面所有文字都会变色）

常见颜色：

# 前景色（文字颜色）
"\033[31m"   # 红色
"\033[32m"   # 绿色
"\033[33m"   # 黄色
"\033[34m"   # 蓝色
"\033[35m"   # 紫色
"\033[36m"   # 青色
"\033[0m"    # 重置（一定要加）

纯装饰作用，不加也不影响程序逻辑。

核心设计意图

s02 架构（只有消息流）： messages ──→ AI ──→ tool_use ──→ 执行工具 ──→ 结果写回 messages （AI 独自在脑子里记忆上下文） s03 架构（多了外部计划状态）： messages ──→ AI ──→ tool_use ──→ 执行工具 ──→ 结果写回 messages ↑ │ │ PlanningState │ │ - items: [PlanItem] │ │ - rounds_since_update │ └────────── 提醒写回 messages ──────────┘ （"当前要做什么"从模型脑内移到系统可观察的状态里）
一句话总结 s03 的升级：把"当前要做什么"从模型脑子里移到了系统可观察的状态里。当 AI 连续 3 轮没更新计划时，系统自动插入提醒，拉回注意力。
