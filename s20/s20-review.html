1 数据类型：class, object, dataclass, 默认值

class 和 object 是一个东西吗？

不是。 class 是蓝图/模具，object 是根据蓝图造出来的具体实例。

在 Python 中，类的每个实例都是一个对象：

class Task: ...

task = Task(id="t1", subject="Fix bug")
print(isinstance(task, Task))    # ✅ True — 是 Task 的实例
print(isinstance(task, object))  # ✅ True — Python 中万物皆对象
print(isinstance(Task, object))  # ✅ True — 类本身也是对象（type 的实例）

@dataclass 自动生成什么？

@dataclass 自动生成 __init__、__repr__、__eq__ 等方法。所以不需要手写 def __init__(self, id, subject, ...)。

worktree 字段为什么需要默认值？

致命 bug：worktree: str | None 后面没有 = None。
导致 create_task() 中创建 Task(...) 时没有传 worktree 参数，抛出 TypeError。

修复：worktree: str | None = None —— Python @dataclass 中，有默认值的字段必须放在没有默认值的字段之后。

subject 字段是干什么的？

任务是任务的 简短标题，类似于 GitHub Issue 的标题。

  • 创建时：create_task("Fix login bug", "The login page crashes when...")
  • 日志打印：[claim] Fix login bug → in_progress
  • 解锁通知：unblocked = [t.subject for t in list_tasks() ...] → ["Fix login bug", "Add tests"]

和 description 的分工：subject 短（标题），description 长（详细信息）。

2 文件操作：Path, glob, iterdir, is_relative_to

Path 是 Python 标准库吗？

是的。from pathlib import Path 是 Python 3.4+ 内置标准库，不需要额外安装。提供面向对象的文件系统操作。

Path.is_relative_to() 是什么用法？

Python 3.9+ 引入的方法，检查一个路径是否在另一个路径之下。 
def safe_path(p: str, cwd: Path = None) -> Path:
    base = cwd or WORKDIR
    path = (base / p).resolve()
    if not path.is_relative_to(base):
        raise ValueError(f"Path escapes workspace: {p}")
    return path

安全防护——防止用户通过 ../../etc/passwd 逃离工作目录：

WORKDIR = "/home/user/project"
safe_path("../../etc/passwd")
# → Path("/home/user/project").resolve() / "../../etc/passwd"
# → Path("/etc/passwd") → is NOT relative to "/home/user/project"
# → ValueError: Path escapes workspace

cwd 代表什么？

Current Working Directory（当前工作目录）。让工具能在指定目录下操作，如队友的工作目录。

glob 是什么用法？

import glob as g
results = []
for match in g.glob(pattern, root_dir=base):
    results.append(match)
return "\n".join(results)
概念比喻代码
class（类）蓝图——定义了"任务"应该长什么样class Task: — 告诉 Python Task 有 id/subject/status 等字段
object（对象）根据蓝图造出来的具体实例Task(id="t1", subject="Fix bug") — 一个具体的任务
表达式含义
import glob as g标准库别名（as g 简化引用名）
g.glob("**/*.py")递归搜索所有 .py 文件
root_dir=base指定根目录（Python 3.10+）
**递归匹配所有子目录

iterdir() 是什么用法？

for directory in sorted(SKILLS_DIR.iterdir()):
    if not directory.is_dir():
        continue           # 跳过文件，只处理子目录
    manifest = directory / "SKILL.md"  # 用 / 拼接路径（Path 重载操作符）

Path.iterdir() 列出当前目录下的所有文件和子目录，返回迭代器（不一次性全加载到内存）。

directory.name 是 Path 对象的属性，返回路径的最后一级：

路径directory.name
/home/user/skills/code-review/"code-review"
/home/user/skills/task-manager/"task-manager"

为什么 task 路径用 task_id.json 格式？

_task_path 返回的是一个 .json 文件路径（不是存 JSON 数据）。选 .json 是因为这个路径将来要配合 json.dumps() / json.loads() 读写，后缀让人一眼知道文件内容是 JSON 格式。

每个 task 对应一个文件：

.tasks/
├── task_1718600000_0123.json    ← 每个任务一个文件
├── task_1718600001_4567.json
└── task_1718600002_8901.json

为什么不用一个文件？性能好——读一个任务不需要加载全部任务；隔离性好——删除/修改一个不影响其他。

3 JSON/YAML 格式：json.dumps, yaml.safe_load, Frontmatter

txt 文件也兼容 json.dumps() 吗？

兼容。 json.dumps() 的输出本身就是文本字符串。无论文件后缀是 .json、.txt 还是 .md，写入磁盘的内容完全一样。

# 以下两种写法，写入磁盘的内容完全一样
path1.write_text(json.dumps(data, indent=2))  # .json 后缀
path2.write_text(json.dumps(data, indent=2))  # .txt 后缀

后缀只是给人看的。但 .json 后缀有实际好处：编辑器自动 JSON 语法高亮、git diff 显示更清晰、别人看到就知道是 JSON 格式。

Frontmatter 格式是什么？为什么用 yaml？

Frontmatter 是 Markdown 文件开头的元数据区，用三横线 --- 包裹，内部用 YAML 格式。 
# 这是 SKILL.md 文件的格式：
---
name: code-review
description: Reviews code for bugs
---

# 实际 Markdown 内容从这里开始
You are a code reviewer. ...

---

# 代码解析 frontmatter：
parts = text.split("---", 2)  # 最多切 2 刀，得 3 块
# parts[0] = ""
# parts[1] = "\nname: code-review\ndescription: ...\n" (YAML)
# parts[2] = "\n# Code Review Skill\n\n..." (Markdown)

meta = yaml.safe_load(parts[1]) or {}  # YAML 字符串 → Python 字典
问题回答
为什么用 YAML 而不是 JSON？Frontmatter 是 Markdown 元数据的约定格式。YAML 更适合人写（不需要引号、更简洁）。最早在 Jekyll/Hugo 等静态网站生成器中流行。
为什么可以用 text.startswith("---")？Frontmatter 的约定——如果有元数据，文件必须以 --- 开头。
YAML 属于 text 吗？是的。yaml.safe_load(parts[1]) 就是解析"一段 YAML 文本"。parts[1] 是字符串，YAML 是这种字符串的格式。

meta 存放什么信息？

meta 是 Frontmatter 解析后的 Python 字典：{"name": "code-review", "description": "Reviews code for bugs"}。

在 scan_skills 中使用：

name = meta.get("name", directory.name)    # 优先从 meta 取，没有就用目录名
desc = meta.get("description", ...)        # 从 meta 取描述

Skill 目录结构是固定的吗？

是的，约定结构：

skills/
  code-review/     ← 目录名 = 技能名（后备）
    SKILL.md       ← 必须有这个文件（包含 Frontmatter）
  task-manager/
    SKILL.md
iterdir 遍历流程：SKILLS_DIR → 每个子目录 → 找 SKILL.md → 读取 → 解析 Frontmatter → 注册到 SKILL_REGISTRY

4 装包与解包：**dict 详解

Task(**json.loads(...)) 这一行发生了什么？

Task(**json.loads(_task_path(task_id).read_text()))
步骤表达式结果（示例）
1.read_text()'{"id": "task_...", "subject": "Fix bug", ...}'
2json.loads(...){"id": "task_...", "subject": "Fix bug", ...}（Python 字典）
3Task(**dict)Task(id="task_...", subject="Fix bug", ...)（字典解包成关键字参数）

装包 vs 解包 —— 怎么区分？

场景写法含义
解包（用在调用时）Task(**dict)把字典拆成关键字参数
装包（用在定义时）def f(**kwargs)把关键字参数收集成字典
# 解包示例（调用的地方） d = {"id": "t1", "subject": "bug"} Task(**d) # 等价于 Task(id="t1", subject="bug") # 装包示例（函数定义的地方） def f(**kwargs): print(kwargs) # 关键字参数被"装"成一个字典 f(a=1, b=2) # → {"a": 1, "b": 2}

"{name}" 和 "’{name}’" 有什么区别？

写法输出
f"’{name}’"'abc' — 值外面有引号包裹
f"{name}"abc — 直接输出值，没有引号

加上单引号是为了在错误消息中清晰标示"这里是用户传进来的值"，视觉上更容易区分。

5 消息压缩系统

s20 的压缩系统由多个层次组成，每一层解决不同的问题。

collect_tool_results — mi, bi 放到 found 里有什么用？

def collect_tool_results(messages: list):
    found = []
    for mi, msg in enumerate(messages):          # mi = message index
        ...
        for bi, block in enumerate(content):      # bi = block index
            if ... and block.get("type") == "tool_result":
                found.append((mi, bi, block))     # 存储位置坐标

mi 和 bi 是坐标（第几个消息的第几个块），作用是让后续操作能精确修改指定位置的内容。虽然 micro_compact 中直接用 block 引用修改（没用 mi, bi），但输出格式保留了坐标信息供将来使用。

tool_result_budget — 为什么算两次 total？

该函数实现了一个逐批裁剪大输出的算法：

1. 第一次 sum: 计算所有 tool_result 总大小 2. 若超出预算（200KB），从最大的开始裁 3. 每裁一个，重新计算总大小（第二次 sum） 4. 直到总大小 ≤ 200KB 时停止

因为每次把一个大 tool_result 替换成"Full output: /path/to/file.json" 短文本后，总字节数下降了，需要重新算才知道够不够。

snip_compact — 裁剪对话中间部分，保留开头和结尾

最复杂也最难懂的一段。 
def snip_compact(messages: list, max_messages: int = 50) -> list:
    if len(messages) <= max_messages:
        return messages

    # Step 1: 确定保留区
    head_end = 3                     # 保留开头 3 条
    tail_start = len(messages) - (max_messages - 3)  # 保留结尾 47 条

    # Step 2: 处理边界 —— 不能让 tool_use 和 tool_result 被拆开
    if head_end > 0 and message_has_tool_use(messages[head_end - 1]):
        while head_end < len(messages) and is_tool_result_message(messages[head_end]):
            head_end += 1

    # Step 3: 裁剪，中间用占位替换
    snipped = tail_start - head_end
    return (messages[:head_end]
            + [{"role": "user", "content": f"[snipped {snipped} messages]"}]
            + messages[tail_start:])
对话历史（共200条） ┌─┬─┬─┬─┬─┬─┬─┬───┬─┬─┬─┬─┬─┬─┬─┬──┬──┬──┐ │1│2│3│4│...│...│...│...│...│...│...│198│199│200│ └─┴─┴─┴─┴─┴─┴─┴───┴─┴─┴─┴─┴─┴─┴─┴──┴──┴──┘ ↑_______↑ 保留头部3条 ↑__________________↑ 保留尾部47条 head_end=3 tail_start=153 中间150条被裁剪 → [snipped 150 messages] ← 占位

为什么要保留 tool_use/tool_result 配对？ 如果大模型的 tool_use 被删了但对应的 tool_result 还在，API 会报错（不匹配）。

micro_compact — 微小压缩

micro = 微小的。不删除消息，只把消息内部的 tool_result 内容替换成更短的占位文本。

def micro_compact(messages: list) -> list:
    tool_results = collect_tool_results(messages)
    if len(tool_results) <= KEEP_RECENT_TOOL_RESULTS:  # KEEP = 3
        return messages
    for _, _, block in tool_results[:-KEEP_RECENT_TOOL_RESULTS]:
        block["content"] = "[Earlier tool result compacted. Re-run if needed]"
    return messages

逻辑：保留最近的 3 个 tool_result 完整，把更早的替换成占位文本。好处是改动最小，省空间最多——tool_result 是对话中最大的内容来源。

类比：micro_compact 不扔家具（不删消息），只是把大纸箱压扁（缩短 tool_result 内容）。

compact_history vs reactive_compact — 主动压缩 vs 被动压缩

维度compact_history（主动）reactive_compact（被动）
触发者Agent 主动调用API 报错时自动触发
触发时机对话变长但还没报错已经收到 prompt-too-long 错误
保留量存完整 transcript + 生成摘要只保留最近 5 条 + 摘要，更激进
类比"吃药预防生病""病倒了才去急救"
一句话区别：主动压缩是"预防性"的，被动压缩是"急救性"的——情况紧急所以保留更少的内容。

为什么叫 "fired"？

fired 来自术语 "cron job fired"（定时任务被触发了），就像闹钟"响了"。

6 压缩深度问题

压缩历史对话的同时要记录之前所有对话内容吗？

是的。 在 compact_history 中，每次压缩前会调用 write_transcript(messages) 把完整的对话历史写入 .transcripts/ 目录，确保不丢失原始数据：

def compact_history(messages: list) -> list:
    transcript = write_transcript(messages)  # 先存档
    summary = summarize_history(messages)    # 再用大模型生成摘要
    return [{"role": "user",
             "content": f"[Compact summary]\n\n{summary}"}]

现在的压缩是不是简单提取前多少内容？没让大模型遍历判断重要性？

不是简单提取。 summarize_history 把所有对话传给大模型，让大模型一次性生成摘要：

def summarize_history(messages: list) -> str:
    conversation = json.dumps(messages, default=str)[:80000]
    prompt = ("Summarize this coding-agent conversation so work can continue. "
              "Preserve current goal, key findings, changed files, remaining work, "
              "and user constraints.\n\n" + conversation)
    response = client.messages.create(...)
    return extract_text(response.content)
你的想法是对的：理想的方式应该是让大模型先遍历一遍，判断"什么重要、什么可以丢"。但这里有矛盾——如果对话已经长到需要压缩了，再传给大模型做摘要，本身就占用了很多 token。

工程上更优的方案是分层摘要：

Layer 1: 每 N 条消息做一个小摘要 Layer 2: 每 M 个小摘要合并为一个中摘要 Layer 3: ...

但 s20 是教学代码，选择最简单的做法——一次传进去让大模型摘要。缺点是如果对话非常长（超过 80000 字符限制），后面的内容就丢了。

transcripts 目录是干什么的？

TRANSCRIPT_DIR = WORKDIR / ".transcripts"

transcript 英文原意是"抄本/记录"，这里指 Agent 和大模型之间完整的对话历史。每次压缩前，完整对话被写入 .transcripts/transcript_{timestamp}.json 文件，然后再做摘要。

7 终端与打印

terminal_print 和 print 的区别？

核心问题：print 在后台线程直接输出会破坏用户正在输入的内容。
terminal_print 的解决方案：先保存用户输入 → 清当前行 → 打印消息 → 恢复用户输入行。 
def terminal_print(text: str):
    if threading.current_thread() is threading.main_thread() or not CLI_ACTIVE:
        print(text)                           # 主线程 → 直接打印
        return
    line = readline.get_line_buffer()              # 获取用户正在输入的内容
    print(f"\r\033[K{text}")                   # \r 回车 + \033[K 清行
    print(PROMPT + line, end="", flush=True)  # 恢复用户的输入行

parse_and_bind 是什么用法？

readline.parse_and_bind('set bind-tty-special-chars off')
部分含义
parse_and_bindreadline 库的方法，用来修改终端的行为设置
set bind-tty-special-chars off告诉 readline 不要把 Ctrl+C、Ctrl+D 等终端特殊字符交给 readline 处理，而是让终端驱动程序直接处理

不设置这个的话，在某些终端中 readline 会拦截 Ctrl+C（中断信号），导致用户无法正常中断程序。加上这行，Ctrl+C 行为恢复正常。

打个比方：readline 像一个"抢键盘的插件"。bind-tty-special-chars off 就是告诉它："Ctrl+C 和 Ctrl+D 这些快捷键你别管，让系统原样处理"。

PROMPT = "\033[36ms20 >> \033[0m" 是什么？

这是终端提示符（显示的输入前缀）。\033[36m 是 ANSI 转义码，将文本设为青色。所以用户看到的是蓝色的 s20 >> 前缀。\033[0m 重置颜色。

inbox_label 为什么判断 req_id 是否存在？

def inbox_label(msg):
    req_id = msg.get("metadata", {}).get("request_id", "")
    suffix = f" req:{req_id}" if req_id else ""
    return f"{msg.get('type', 'message')}{suffix}"

两种情况的输出对比：

场景输出
有 req_idshutdown_response req:042817
无 req_idmessage（干净利落，不显示空字段）

无 req_id 时不显示后缀，是为了避免在大多数普通通知消息上显示空尾巴（如 message req_id:）。

request_id 是干什么的？

request_id 类似于快递单号——它是一个 6 位随机数，用来匹配请求和响应：

Agent A 发请求:  {"type": "shutdown_request",  "request_id": "req_042817"}
Agent B 回响应:  {"type": "shutdown_response", "request_id": "req_042817"}

通过 request_id，协议系统能找到哪个待处理的请求被响应了：

state = pending_requests.get(request_id)  # 用 request_id 查表

8 Python 语法技巧

ast.literal_eval 是什么用法？

todos = ast.literal_eval(todos)  # 安全版 eval
函数行为安全性
eval()执行任意 Python 表达式❌ 危险！可执行 os.system("rm -rf /")
ast.literal_eval()只计算字面量（字符串、数字、列表、字典等）✅ 安全

这里先用 json.loads 解析（JSON 是严格格式），失败再用 ast.literal_eval（兼容 Python 格式），双重保险。

fn() 函数参数是什么用法？

函数式编程的常见模式——把"要执行的操作"和"重试逻辑"分离开。 
def with_retry(fn, state: RecoveryState):
    for attempt in range(MAX_RETRIES):
        try:
            result = fn()   # 调用传入的函数
            ...
        except Exception as e:
            ...
    raise RuntimeError("Max retries exceeded")

# 使用：传入函数本身（不加 ()）
result = with_retry(call_api, state)

fn 是一个函数参数（Functional Argument）。fn() = "执行你传进来的那个函数"。Python 中函数是一等公民，可以当作变量传来传去。

re.sub() 是什么用法？

_DISALLOWED_CHARS = re.compile(r'[^a-zA-Z0-9_-]')
normalized = _DISALLOWED_CHARS.sub('_', name)

# 等价于：
normalized = re.sub(_DISALLOWED_CHARS, '_', name)
部分含义
[^a-zA-Z0-9_-]正则中 ^ 在 [...] 开头表示"否定"——匹配不是字母数字下划线短横线的字符
.sub('_', name)把所有匹配到的字符替换成下划线
为什么叫 _DISALLOWED_CHARS因为它的作用就是找到不允许的字符并替换掉

示例：normalize_mcp_name("my-server@v2") → "my-server_v2"（@ 被替换成 _）

lambda 中的 * 是什么意思？

handlers[prefixed] = (
    lambda *, c=mcp_client, t=tool_def["name"], **kw: c.call_tool(t, kw))
部分含义
*分隔符——后面的参数必须用关键字传入，不能用位置参数
c=mcp_client默认参数——在 lambda 定义时固定 mcp_client 的值（闭包快照）
t=tool_def["name"]默认参数——在 lambda 定义时固定工具名
**kw收集所有剩余的关键字参数到一个字典
闭包陷阱：在循环中创建 lambda 引用循环变量，不加默认参数快照会导致所有 lambda 共享最后一个值。

9 错误处理：429, 529, FALLBACK_MODEL, raise, retry

HTTP 状态码：429 和 529

状态码含义处理方式
429Too Many Requests（请求太多）等待后重试（指数退避）
529Overloaded（服务器过载，Anthropic 特有）连续 2 次后切换到备用模型
# 判断 429
if "ratelimit" in name or "429" in msg:
    delay = retry_delay(attempt)
    time.sleep(delay)

# 判断 529
if "overloaded" in name or "529" in msg:
    state.consecutive_529 += 1
    if state.consecutive_529 >= MAX_CONSECUTIVE_529 and FALLBACK_MODEL:
        state.current_model = FALLBACK_MODEL  # 切换到备用模型

为什么错误判断中会有 name？

name = type(e).__name__.lower() 获取异常类的名字（如 RateLimitError → "ratelimiterror"）。因为不同的 SDK 可能用不同的异常类名，所以同时检查类名和消息文本来提高匹配准确率。

FALLBACK_MODEL 是什么？

PRIMARY_MODEL = MODEL                          # 主要用这个
FALLBACK_MODEL = os.getenv("FALLBACK_MODEL_ID")  # 备用模型

当主模型持续返回 529（过载）时，自动切换到备用模型。例如主模型是 claude-sonnet-4-20250514，备用模型是 claude-3-haiku-20240307（更快更便宜，但能力弱一些）。

MAX_RECOVERY_RETRIES = 2 是最多恢复几次？

2 次。不是重试 API 调用（那是 MAX_RETRIES = 3），而是在发生严重错误后，尝试恢复对话的次数。如果连续恢复失败 2 次，Agent 就放弃了。

raise 单独使用是什么？

raise 单独使用叫重新抛出（re-raise）。当 with_retry 遇到既不是 429 也不是 529 的异常时，说明这个错误重试也没用（比如参数错误、网络不通），所以直接往上抛，让上层处理。

has_escalated 表示"是否已经尝试过增加 max_tokens"。

10 后台任务：block, worker, background_tasks

block 里面都有什么？

block 是大模型返回的 tool_use 块，包含工具调用信息。 
{
    "type": "tool_use",
    "id": "toolu_abc123",       # block.id → 工具用 ID
    "name": "bash",              # block.name → 工具名（大模型写的）
    "input": {                    # block.input → 工具参数
        "command": "pip install pandas",
        "run_in_background": True
    }
}

block.name 由大模型决定——大模型在 API 返回的 tool_use 块中填写要调用的工具名，代码根据这个名字查 handlers 字典来执行。

block.input 和 block.name 什么区别？

属性含义值示例
block.name工具名（大模型决定调哪个工具）"bash"、"read_file"
block.input工具的参数字典{"command": "ls -la"}

后台任务的 worker 线程

def start_background_task(block, handlers: dict) -> str:
    ...
    def worker():
        handler = handlers.get(block.name)
        result = call_tool_handler(handler, block.input, block.name)
        with background_lock:
            background_tasks[bg_id]["status"] = "completed"  # 注意：写 background_tasks
            background_results[bg_id] = str(result)          # 注意：是简单赋值，不是 dict 嵌套

    threading.Thread(target=worker, daemon=True).start()

daemon=True 表示守护线程——主程序退出时自动结束，不需要手动管理。

11 Cron 调度系统

为什么写了 _cron_field_matches 又写 _validate_cron_field？

用途完全不同：

函数目的输出使用场景
_cron_field_matches匹配——检查当前时间是否匹配表达式True / False运行时，每隔 1 秒调用
_validate_cron_field验证——检查表达式语法是否正确None（正确）或错误消息注册时，校验用户输入

一个在运行时用的（匹配逻辑），一个在注册时用的（输入校验）。因为需求不同，所以代码也不同——验证函数比匹配函数多很多检查（如数字范围、步长合法性等）。

schedule_job 只是验证时间吗？

不只是。 它做三件事：

  1. 验证：调用 validate_cron() 检查 cron 表达式语法
  2. 创建：创建一个 CronJob 对象（含随机 ID）
  3. 存储：加入 scheduled_jobs 字典；如果需要持久化（durable=True），写入 .scheduled_tasks.json 文件

cron_scheduler_loop 由谁启动？

在文件加载时自动启动。 threading.Thread(target=cron_scheduler_loop, daemon=True).start() 在模块顶层（不在函数内），所以 import 或 python s20_comprehensive.py 时就会执行。

cron_queue 是线程安全的队列——Cron 线程把到期的 job 放入队列，主循环消费队列。这样不阻塞主循环。

run_list_crons 是"都列出来，大模型一一执行"吗？

不是。 run_list_crons 只是一个只读的列表查看工具，返回当前所有定时任务的文本描述。大模型看到这个列表后，决定是否要修改（取消某个任务），但列表本身不会自动执行任何任务。

执行逻辑在 cron_scheduler_loop 中——它每隔 1 秒检查一次，匹配的 job 会被放入 cron_queue，然后主循环在每次迭代时消费队列。

输出示例：

  cron_042817: '*/5 * * * *' -> Run tests on the project   [recurring, durable]
  cron_931204: '0 9 * * 1'   -> Send weekly report           [recurring, durable]

12 MCP 系统

为什么叫 _DISALLOWED_CHARS？

_DISALLOWED_CHARS = re.compile(r'[^a-zA-Z0-9_-]')

正则中的 ^ 在字符集 [...] 开头表示否定。所以 [^a-zA-Z0-9_-] 匹配不是字母数字下划线短横线的字符。

变量名叫 _DISALLOWED_CHARS（不允许的字符），因为它的作用就是找到这些字符并替换掉：

def normalize_mcp_name(name: str) -> str:
    return _DISALLOWED_CHARS.sub('_', name)

# "my-server@v2" → "my-server_v2"  (@ 被替换成 _)
# "Hello World"  → "Hello_World"   (空格被替换成 _)

factory 不是一个变量吗？为什么可以 factory()？

工厂模式：MOCK_SERVERS 字典的值是函数（而不是函数调用的结果）。 
MOCK_SERVERS = {
    "docs": _mock_server_docs,     # 注意：没有 ()，是函数本身
    "deploy": _mock_server_deploy,
}

factory = MOCK_SERVERS.get(name)  # factory 拿到的是函数
mcp_client = factory()            # 再调用它来创建实例

这样做的目的是每次都创建新的 MCPClient 实例，而不是复用同一个。想加新服务器只需要往这个字典加一条。

MCP 工具名前缀为什么是 mcp__server__tool？

prefixed = f"mcp__{safe_server}__{safe_tool}"

两个原因：

  • 防命名冲突：不同服务器的工具可能同名（如 docs 和 deploy 都有 status），前缀让名字唯一
  • 可溯源：LLM 看到 mcp__docs__search 就知道这个工具来自 docs 服务器

MessageBus 的 mailbox 为什么用 JSONL 格式？

.jsonl = JSON Lines，每行一个 JSON 对象。优点：

  • 追加写（append）非常高效——不需要读整个文件再写
  • 一行是一条消息，读取时 splitlines() 逐行解析即可
  • 可人工查看——每行都是独立有效的 JSON

metadata 存放协议相关的额外信息，如：

  • approve：审批结果（True/False）
  • feedback：审批反馈意见

更新 context

context.update(update_context(context, history))

context.update() 是 Python 字典的内置方法，把另一个字典的键值对合并到当前字典中。这里外层 .update() 是 dict 方法，内层 update_context() 是自定义函数（返回一个新的 context 字典）。

__main__ 中的 CLI_ACTIVE = True

这行在 if __name__ == "__main__" 块中，启动终端打印信息开关。因为模块顶层 CLI_ACTIVE = False，当作为脚本运行时设置为 True，启用终端打印功能。

为什么 agent_loop 和 cron_autorun_loop 都要上锁？

agent_lock 确保同一时间只有一个线程在运行 agent_loop。如果用户输入触发的 agent_loop 和 cron 触发的 agent_loop 同时运行，会相互干扰对话历史。

turn_start = len(history) 的作用？

记录当前轮次开始前的历史长度，用于 print_turn_assistants(history, turn_start) 只打印本轮新增的助手回复，而不是每次都打印全部历史。

常见困惑 FAQ

Q：所有 task 保存方式都是 task_id.json 吗？

A：对。 每个 task 对应一个文件。好处是读一个任务不需要加载全部任务（性能好），删除/修改一个不影响其他任务。

Q：class 和 object 是一回事吗？

A：不是。 class 是"造对象的模板"，object 是"用模板造出来的具体东西"。所有用 class 造出来的实例都是对象。在 Python 中，连类本身也是对象（type 的实例）。

Q：terminal_print 和 print 的区别？

A：print 在后台线程直接输出会破坏用户正在输入的内容。terminal_print 先保存用户输入 → 清行 → 打印 → 恢复输入行。

Q：什么是"index 0 in size 0"错误？

A：尝试访问空列表的第一个元素（list[0] 但 len(list) == 0）。比如 messages[-1] 在 messages 为空时报错。

Q：为什么 fn() 可以传函数？

A：Python 中函数是一等公民——函数可以像变量一样赋值、传参、返回。这就是高阶函数模式，把"要执行的操作"作为参数传递，实现"重试逻辑"的复用。

Q：主动压缩和被动压缩的效果一样吗？

A：从"把长对话变成摘要"的角度看一样。但触发时机不同（主动是预防、被动是抢救），保留量不同（被动更激进，只留 5 条）。紧急程度不同决定了保留策略不同。

Q：为什么压缩 tool_result 就够了（micro_compact）？

A：tool_result 是对话中最大的内容来源。一次 pytest 的 tool_result 可能有几千行输出，而其他消息（用户指令、助手回复）通常很短。所以压缩 tool_result 的性价比最高——改动最小，省空间最多。
