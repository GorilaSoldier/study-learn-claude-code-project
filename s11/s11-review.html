1 恢复常量详解

代码位置：L58-63

# Recovery constants
MAX_RECOVERY_ATTEMPTS = 3
BACKOFF_BASE_DELAY = 1.0    # seconds
BACKOFF_MAX_DELAY = 30.0    # seconds
TOKEN_THRESHOLD = 50000    # chars / 4 ~ tokens for compact trigger

含义与作用

常量值含义被哪里使用
MAX_RECOVERY_ATTEMPTS3每种恢复路径最多可以试几次内层 for 循环（API 重试）、外层 max_tokens 计数器
BACKOFF_BASE_DELAY1.0 秒指数退避的基准延迟时间backoff_delay()
BACKOFF_MAX_DELAY30.0 秒退避延迟的上限，避免无限增长backoff_delay()
TOKEN_THRESHOLD50000 字符超过此字符数触发主动压缩，约 12500 tokensagent_loop 末尾的主动压缩检查
关键理解：这些数字是"退路"的边界条件——重试不能无限次、等待不能无限长、上下文不能无限大。每个数字都对应一种防止系统失控的机制。

2 CONTINUATION_MESSAGE — 续传提示词

代码位置：L65-70

CONTINUATION_MESSAGE = (
    "Output limit hit. Continue directly from where you stopped.\n"
    "no recap, no repetition. Pick up mid-sentence if you need."
)

作用

当 LLM 输出被 max_tokens 截断时，Agent 把这句话作为新的用户消息发给 LLM，告诉它：

"你刚才话没说完就被打断了，直接接着继续说，不要重复前面的话。"

为什么特意强调"不要重复"？

如果只说"继续"，模型经常会：

  • 重新总结前面说过的内容
  • 重新开头
  • 重复已经输出过的内容

所以提示词明确了：no recap, no repetition. Pick up mid-sentence.

小细节：原代码中 stopped.\nno recap 是正确换行的，续传消息的语义是清晰的。

3 estimate_tokens — 粗估 token 数的原理

代码位置：L72-74

def estimate_tokens(messages: list) -> int:
    """Rough token estimate: ~4 chars per token."""
    return len(json.dumps(messages, default=str)) // 4

原理

  • 把消息列表序列化成 JSON 字符串
  • 取字符串长度
  • 除以 4（英文中平均 1 token ≈ 4 个字符
  • // 是整数除法，向下取整，保守估计
注意：这只是粗略估算，不是精确的 tokenizer 计数。不同模型的实际 token 化方式不同，中文字符约 1 字 ≈ 1-2 tokens，比英文更"贵"。

用途

用于主动压缩的触发判断：当 estimate_tokens(messages) > TOKEN_THRESHOLD 时，提前压缩上下文。

4 auto_compact 逐段拆解（核心）

代码位置：L76-104

功能

当对话历史太长时，让 LLM 自己总结浓缩历史，用摘要替换掉完整历史。相当于"记笔记"——把长篇讨论浓缩成要点。

4 个步骤逐一拆解

步骤 1：截取要压缩的历史（L77）

conversation_text = json.dumps(messages, default=str)[:80000]
  • 把对话消息转为 JSON 字符串
  • [:80000] 截断前 8 万字符，防止摘要请求本身太长
  • default=str：处理不可序列化的对象（如 Path、datetime），强转成字符串

步骤 2：构建压缩提示词（L78-87）

prompt = (
    "Summarize this conversation for continuity. Include:\n"
    "1) Task overview and success criteria\n"
    "2) Current state: completed work, files touched\n"
    "3) Key decisions and failed approaches\n"
    "4) Remaining next steps\n"
    "Be concise but preserve critical details.\n\n"
    + conversation_text
)

明确要求 LLM 摘要时包含 4 个维度：

  1. 任务总览 + 成功标准——我们在做什么？
  2. 当前状态——做了什么、改了哪些文件
  3. 关键决策 + 失败尝试——哪些方案试过行不通
  4. 下一步——还剩什么没做

步骤 3：调用 LLM 生成摘要（L88-94）

try:
    response = client.messages.create(
        model=MODEL,
        messages=[{"role": "user", "content": prompt}],
        max_tokens=4000
    )
    summary = response.content[0].text
except Exception as e:
    summary = f"(compact failed: {e}). Previous context lost."
  • 正常路径：LLM 生成摘要，限制 max_tokens=4000
  • 异常路径：如果 LLM 调用失败，标记"压缩失败，上下文丢失"

步骤 4：构建压缩后的消息（L96-103）

continuation = (
    "This session continues from a previous conversation that was compacted. "
    f"Summary of prior context:\n\n{summary}\n\n"
    "Continue from where we left off without re-asking the user."
)
return [{"role": "user", "content": continuation}]
  • 把摘要包装成一条新的用户消息
  • 核心意图：告诉 LLM "这是之前的摘要，接着干，不要问我"
  • 返回只有一条消息的列表，替换掉原来可能几百条消息的历史
为什么需要 auto_compact？
LLM 有上下文窗口限制（如 100K、200K tokens）。对话越长，推理成本越高、速度越慢、越容易"迷失"。压缩就是把对话历史浓缩为要点，扔掉冗余信息。

5 json.dumps(messages)[:80000] 的实现与信息丢失问题

问题：messages 是消息列表，json.dumps 怎么序列化它？

messages 是一个列表，每个元素是一个字典，类似：

messages = [
    {"role": "user",      "content": "帮我写一个 Python 脚本"},
    {"role": "assistant", "content": "好的，我来写..."},
    {"role": "user",      "content": "再加一些错误处理"},
    ...
]

json.dumps 做了什么

json.dumps(messages)
# 输出（一行）：
# [{"role": "user", "content": "帮我写个脚本"}, {"role": "assistant", "content": "好的"}]

把整个列表序列化为一个扁平的 JSON 字符串。如果中间有 Path 等不可 JSON 序列化的对象，default=str 会兜底用 str() 强转。

[:80000] 截断的问题

关键理解：截断即丢失。
如果对话历史的 JSON 字符串有 30 万字符，[:80000] 取前 8 万，后面 22 万字符（约 75% 内容）在传给 LLM 做摘要时完全消失了。
情况后果
关键信息在对话前半段（任务目标、初始决策）✅ 影响不大，摘要仍然可用
关键信息在对话后半段（最新调试发现、最新方案）❌ 摘要会遗漏重要信息，后续对话可能偏离方向
对话特别长（超 50 万字符）❌ 截断非常严重，可能只剩 1/6 的内容

可能的改进方案

方案思路优点
保留头+尾，丢中间截取前 40000 + 后 40000 字符同时保留早期任务定义和近期最新进展
按消息粒度截断从最新消息往前取，直到达阈值保留完整的最新中国消息
分块摘要把对话切块，分别摘要再合并覆盖全部内容，但代价更高
为什么作者这样设计？ 这是一种权衡：防止溢出（如果对话 200 万字符，不截断摘要请求就会超过 context window），且假设早期内容更重要。教学 demo 可以接受，生产环境需要更精细的策略。

6 response.content[0].text 为什么有 [0]？

问题：按理说 response 里不就 1 个元素吗？为什么还要区分 [0]？

Anthropic SDK 响应结构

Message(
    id="msg_xxx",
    model="claude-3-sonnet",
    role="assistant",
    content=[                     # ← 这是一个列表
        ContentBlock(
            type="text",
            text="这是 Claude 的回答..."
        ),
        ContentBlock(               # ← 可能有第二个块（工具调用）
            type="tool_use",
            id="toolu_xxx",
            name="run_bash",
            input={...}
        )
    ],
    stop_reason="end_turn",
    usage=Usage(input_tokens=100, output_tokens=200)
)

为什么 content 是列表？

因为 Claude 的响应可能同时包含文本和工具调用。例如模型既回答了问题又要调用工具：

content = [
    ContentBlock(type="text",     text="好的，我来查看这个文件..."),
    ContentBlock(type="tool_use", name="read_file", input={...})
]

response.content[0].text   # → "好的，我来查看这个文件..."
response.content[1].input  # → {"path": "/tmp/test.py"}

auto_compact 中为什么只用 [0]？

因为构造的 prompt 是纯文本请求（没有注册工具），所以 Claude 只会返回一个 text 类型的块。content[0].text 就是唯一的文本内容。使用 [0] 是取列表的第一个（也是唯一一个）元素。

7 backoff_delay — 指数退避 + jitter

代码位置：L106-109

def backoff_delay(attempt: int) -> float:
    """Exponential backoff with jitter: base * 2^attempt + random(0,1)."""
    delay = min(BACKOFF_BASE_DELAY * (2 ** attempt), BACKOFF_MAX_DELAY)
    jitter = random.uniform(0, 1)
    return delay + jitter

等待时间计算表

attempt2^attemptbase * 2^attemptmin(..., 30)+ jitter
0（首次重试）11.0s1.0s~1.0~1.9s
122.0s2.0s~2.0~2.9s
244.0s4.0s~4.0~4.9s
388.0s8.0s~8.0~8.9s
4+16+16.0s+30.0s（上限）~30.0~30.9s

两个关键设计

  1. 指数增长：每次重试等待时间翻倍，给系统逐步恢复的时间
  2. Jitter（抖动）：加上 random.uniform(0, 1) 的随机数，防止多个客户端同时重试造成"惊群效应"（thundering herd problem）
文档字符串与实际代码：文档里的公式写的是 base * 2^attempt + jitter + random(0,1)，但实际上只有 min(...) + random(0,1)，没有额外的 jitter 变量。实际代码是正确的。

9 内层 for 循环：API 重试机制（策略 2 & 3）

代码位置：L225-248

response = None
for attempt in range(MAX_RECOVERY_ATTEMPTS + 1):
    try:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000
        )
        break # success
    except APIError as e:
        error_body = str(e).lower()

        # Strategy 2: prompt_too_long -> compact and retry
        if "overlong_prompt" in error_body or ("prompt" in error_body and "long" in error_body):
            print(f"[Recovery] Prompt too long.Compacting... (attempt {attempt + 1})")
            messages[:] = auto_compact(messages)
            continue
        
        # Strategy 3: connection/rate errors -> backoff
        if attempt < MAX_RECOVERY_ATTEMPTS:
            delay = backoff_delay(attempt)
            print(f"[Recovery] API error: {e}. "
                    f"Retrying in {delay:.1f}s (attempt {attempt + 1}/{MAX_RECOVERY_ATTEMPTS})")
            time.sleep(delay)
            continue
        
        # All retries exhausted
        print(f"[Error] API call failed after {MAX_RECOVERY_ATTEMPTS} retries: {e}")
        return

流程

  1. 先尝试 API 调用——client.messages.create(...)
  2. 成功？→ break 跳出内层 for 循环
  3. 失败？→ 抛出 APIError，进入 except 块
  4. 在 except 中判断是哪种错误，选择对应的恢复策略

为什么上下文过长和网络延迟都是 APIError？

Anthropic SDK 把所有 API 层面的异常统一为 APIError（或其子类）。在 except 块中通过字符串匹配进一步区分：

错误类型本质区分方式
prompt_too_long输入消息太长检查错误信息文本："overlong_prompt" in error_body
rate_limit_error请求频率过高被限流走退避策略（和其他临时错误一样处理）
网络超时/连接失败DNS 解析失败、SSL 握手失败等SDK 包装成 APIError，走退避策略
API 500 错误服务器内部错误走退避策略
认证错误（401）API Key 无效也是 APIError，但退避重试也没用，3 次后失败
关键理解：except APIError 是一张"大网"，捕获所有 API 相关的异常，然后在里面通过字符串匹配进一步判断是哪种具体错误，选择不同策略。

10 attempt 计数：会不会每次跑满 4 次？

问题：for attempt in range(MAX_RECOVERY_ATTEMPTS + 1) 是不是不管有没有问题都会累加？

答案：不会。关键在 break

for attempt in range(4):  # → [0, 1, 2, 3]
    try:
        response = client.messages.create(...)
        break   # ← ★ 一旦成功，立刻跳出 for 循环
    except APIError as e:
        # 只有失败了才走这里
        ...
第 1 次（attempt=0） ├── 成功 → break → 进入 while 后续逻辑 ✅ 只用 1 次 └── 失败 → 进入 except 第 2 次（attempt=1） ├── 成功 → break ✅ 用了 2 次 └── 失败 → 进入 except 第 3 次（attempt=2） ├── 成功 → break ✅ 用了 3 次 └── 失败 → 进入 except 第 4 次（attempt=3，最后一次） ├── 成功 → break ✅ 用了 4 次 └── 失败 → 重试耗尽 → return ❌ 彻底失败

为什么是 range(MAX_RECOVERY_ATTEMPTS + 1) = range(4)？

次数attempt说明
第 1 次0首次调用（不是重试）
第 2 次1第 1 次重试
第 3 次2第 2 次重试
第 4 次3第 3 次重试（最后一次机会）

设计意图：1 次首次调用 + 3 次重试 = 总共 4 次机会。

在退避策略中，if attempt < MAX_RECOVERY_ATTEMPTS（即 attempt < 3）时才有退避重试。当 attempt == 3 时（第 4 次），不再退避，直接失败退出。所以最多经历 3 次退避等待 + 1 次最终尝试。

11 max_tokens 与 prompt_too_long 的本质区别

问题：max_tokens 属于"上下文超出"的情况吗？

答案：不属于。这是两个完全不同的概念。

max_tokens（输出截断）prompt_too_long（上下文超出）
问题在哪端输出端（模型回答）输入端（你的消息）
触发条件模型想说的话超过了 max_tokens=8000 的限制你发的 messages 总长度超过了模型的上下文窗口
表现形式response.stop_reason == "max_tokens"API 直接报错抛出 APIError
有无 response✅ 有 response，内容是部分回答❌ 无 response，调用本身失败
恢复方式注入 CONTINUATION_MESSAGE，让他继续说调用 auto_compact 压缩历史再重试
类比你让一个人写 8000 字作文，他写到 8000 字被喊停你给了这个人一本百科全书让他读，书太厚了他桌子放不下

为什么在代码中分两个地方处理？

这涉及到两个不同层面的恢复：

  • 内层 for 循环：处理 API 调用本身失败——包括上下文过长（prompt_too_long）、网络错误等
  • 外层 while 循环（max_tokens 策略）：处理 API 调用成功但输出被截断——response 对象正常返回了

max_tokens 不是 API 错误，API 正常返回了响应，只是响应不完整。所以它会在 for 循环中 break 成功，进入 while 的后续逻辑，在那里被 stop_reason == "max_tokens" 捕获。

12 max_output_recovery_count 与 x/y 分数表示

代码位置：L261-274

if response.stop_reason == "max_tokens":
    max_output_recovery_count += 1
    if max_output_recovery_count <= MAX_RECOVERY_ATTEMPTS:
        print(f"[recovery] max_tokens hit"
              f" ({max_output_recovery_count}/{MAX_RECOVERY_ATTEMPTS})"  # ← 这里
              f" Injecting continuation..."
        )
        messages.append(...)
        continue

x/y 是什么？

这是分数/进度显示的惯用写法，表示"当前值 / 总计"。

例如 max_output_recovery_count = 2、MAX_RECOVERY_ATTEMPTS = 3 时，打印：

[recovery] max_tokens hit (2/3) Injecting continuation...

意思是："已恢复 2 次，总共最多 3 次"。

为什么用 x/y 而不是文字描述？

写法输出解读成本
x/y(2/3)一眼就能看出进度——"已经试了 2 次，最多 3 次"
用文字(attempt 2 of 3)也可以，但更冗长

x/y 是一种超紧凑的信息密度最大化写法，常见于进度条、日志、CLI 工具的输出中。

两个计数器的区别

计数器所属层用途作用域
attempt内层 for 循环统计 API 调用的总尝试次数每次外层 while 迭代都重置
max_output_recovery_count外层 while 循环统计 max_tokens 恢复发生的次数跨 while 迭代累积，最多 3 次

13 异常恢复：prompt_too_long 分支详解

代码位置：L230-234

# Strategy 2: prompt_too_long -> compact and retry
if "overlong_prompt" in error_body or ("prompt" in error_body and "long" in error_body):
    print(f"[Recovery] Prompt too long.Compacting... (attempt {attempt + 1})")
    messages[:] = auto_compact(messages)
    continue

逻辑流程

  1. 把错误信息转小写，方便关键词匹配
  2. 检查是否含 "overlong_prompt"（精确错误码）或同时含 "prompt" 和 "long"（宽松匹配）
  3. 匹配成功 → 调用 auto_compact(messages) 压缩历史
  4. messages[:] = ... 切片赋值，原地替换 messages 内容
  5. continue 回到 for 循环开头，用压缩后的历史重试

错误匹配策略

使用两种匹配方式，提高容错率：

  • "overlong_prompt" in error_body：Anthropic API 的精确错误码
  • "prompt" in error_body and "long" in error_body：更宽松的关键词匹配，兼容不同 API 版本或代理的错误信息格式

14 messages[:] = 切片赋值的作用

问题：为什么用 messages[:] = 而不是 messages = ？

这是 Python 的一个经典问题：

messages[:] = auto_compact(messages)  # ✔ 原地修改，外层变量可见
messages = auto_compact(messages)      # ❌ 新绑定，外层 while 的 messages 不变
写法效果对外层影响
messages[:] = new_list列表切片赋值——直接修改列表对象本身，保持同一个对象✅ 所有引用这个列表的地方都看到变化
messages = new_list重新绑定——让局部变量指向新对象，原对象不受影响❌ 外层的 messages 仍然指向原列表
为什么这里必须用切片赋值？
因为 agent_loop 函数外部（__main__ 中的 history 变量）也持有同一个列表的引用。如果只重新绑定局部变量，外层看到的历史还是压缩前的旧内容，下一轮 API 调用还是超长。

15 主动压缩机制（Proactive Compact）

代码位置：L301-306

# Check if we should auto-compact (proactive, not just reactive)
if estimate_tokens(messages) > TOKEN_THRESHOLD:
    print("[Recovery] Token estimate exceeds threshold. Auto-compacting...")
    messages[:] = auto_compact(messages)

被动 vs 主动

被动压缩（策略 2）主动压缩（这里）
触发时机API 调用报错 prompt_too_long 时每次工具调用处理完后主动检查
类比等车坏了再修定期保养预防故障
优点只在必要时压缩避免 API 浪费、减少失败重试

这是代码中的第 4 种恢复机制（注释的三个策略 + 额外补充）：在工具调用处理后，主动检查 tokens 是否超过阈值（50000 字符），提前压缩，避免等到 API 报错。
