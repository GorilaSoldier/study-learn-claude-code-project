1 章节概述：为什么需要任务系统？

核心思路

s03 的 todo 已经能帮 agent 拆解目标，但有两个限制：

  • 不持久——对话结束就丢，重启后没有任务记录
  • 不表达依赖——不知道谁先谁后、谁等谁

s12 的升级：把"会话里的 todo"升级为"可持久化的任务图"。

最小心智模型

只要系统能稳定回答以下 4 个问题，最小任务系统就成立了：

  1. 现在有哪些任务？ → list_tasks()
  2. 每个任务什么状态？ → Task.status（pending → in_progress → completed）
  3. 哪些任务被卡住？ → blockedBy 未全部完成
  4. 哪些任务可以开始？ → can_start() 返回 True
记住：todo 更像本轮计划，task 更像长期工作板。todo 适合会话内快速列步骤，task 适合跨步骤、跨阶段、跨对话地协调工作。

2 Task 数据结构详解

代码位置：L55-62

@dataclass
class Task:
    id: str
    subject: str
    description: str
    status: str          # pending | in_progress | completed
    owner: str | None    # Agent name (multi-agent scenarios)
    blockedBy: list[str] # Dependency task IDs

逐字段解释

字段类型含义
idstr任务唯一标识，如 "task_1718600000_0001"
subjectstr任务标题/一句话摘要
descriptionstr详细描述，默认空字符串
statusstr状态：pending（待处理）→ in_progress（进行中）→ completed（已完成）
ownerstr \| None责任人，为多 Agent 场景预留。未分配时为 None
blockedBylist[str]依赖列表，存其他任务的 id。当前任务必须等这些依赖全部完成才能开始

关于 @dataclass

Python 3.7+ 引入的装饰器，自动生成 __init__、__repr__、__eq__ 等方法。没有它的话需要手写：

class Task:
    def __init__(self, id, subject, description, status, owner, blockedBy):
        self.id = id
        self.subject = subject
        # ... 每个字段都要写一遍 ...

关于 str | None

这是 Python 3.10+ 的类型联合写法（Union Type），等价于 Optional[str]。表示 owner 可以是字符串或 None。

关键理解：@dataclass + asdict() 配合使用，可以一键把对象转为字典，方便 JSON 序列化——这是整个持久化机制的基础。

3 文件持久化：一任务一文件

代码位置：L64-78

目录结构

.tasks/
    task_1718600000_0001.json
    task_1718600001_0002.json
    task_1718600002_8888.json

三个核心函数

_task_path(task_id) -> Path（L64-65）

def _task_path(task_id: str) -> Path:
    return TASKS_DIR / f"{task_id}.json"
  • 下划线开头表示私有函数，仅在模块内部使用
  • 将任务 ID 映射为文件路径："task_xxx" → ".tasks/task_xxx.json"
  • Path / str：pathlib 的路径拼接操作符，比 os.path.join() 更简洁

save_task(task)（L70-71）

def save_task(task: Task):
    _task_path(task.id).write_text(json.dumps(asdict(task), indent=2))
  • asdict(task)：dataclasses 内置函数，把 Task 对象递归转换为字典
  • json.dumps(..., indent=2)：字典 → 带缩进的 JSON 字符串
  • Path.write_text()：pathlib 的方法，自动创建/覆盖文件，等价于 with open(path, "w") as f: f.write(s)
  • 如果文件不存在会自动创建（但父目录必须先存在——TASKS_DIR.mkdir(exist_ok=True) 保证这一点）

load_task(task_id) -> Task（L73-74）

def load_task(task_id: str) -> Task:
    return Task(**json.loads(_task_path(task_id).read_text()))
  • Path.read_text()：读取整个文件为字符串
  • json.loads(...)：JSON 字符串 → Python 字典
  • Task(**dict)：字典解包为关键字参数，等价于 Task(id=..., subject=..., ...)
设计思路：一任务一文件的好处——独立读写互不影响，方便调试时手动编辑，删除某个任务不影响其他任务。

4 create_task：任务创建与 ID 生成

代码位置：L65-70

def create_task(subject: str, description: str = "",
                blockedBy: list[str] | None = None) -> Task:
    task = Task(
        id=f"task_{int(time.time())}_{random.randint(0, 9999):04d}",
        subject=subject,
        description=description,
        status="pending",
        owner=None,
        blockedBy=blockedBy or [],
    )
    save_task(task)
    return task

ID 生成策略

id=f"task_{int(time.time())}_{random.randint(0, 9999):04d}"

格式：task_时间戳_4位随机数

  • int(time.time())：当前 Unix 时间戳（秒级），如 1718600000
  • random.randint(0, 9999)：0~9999 的随机整数
  • :04d：格式化说明符，至少 4 位数字，不足补零。如 42 → 0042
  • 组合效果：同一秒内最多 10000 个不重复 ID，足以避免碰撞

默认值处理

blockedBy=blockedBy or []

这是一个常见的 Python 惯用写法：

  • 如果传了 None 或空列表 []，None or [] 或 [] or [] 都得到 []
  • 如果传了非空列表如 ["task_A"]，["task_A"] or [] 得到 ["task_A"]
  • 目的是保证 blockedBy 始终是列表，后续 for dep_id in task.blockedBy 不会报错
注意：参数默认值 blockedBy: list[str] | None = None 不能写成 = []，否则所有调用共享同一个列表对象（可变默认参数陷阱）。

5 list_tasks：glob + 列表推导式拆解

代码位置：L76-78

def list_tasks() -> list[Task]:
    return [Task(**json.loads(p.read_text()))
            for p in sorted(TASKS_DIR.glob("task_*.json"))]

从右往左读

步骤表达式结果
1TASKS_DIR.glob("task_*.json")匹配所有 task_开头.json结尾 的 Path 迭代器
如 [Path(".tasks/task_xxx.json"), ...]
2sorted(...)按文件名（字母序=时间序）排序
3for p in sorted(...)遍历每个 Path 对象
4p.read_text()读取文件全部内容 → 字符串（JSON）
5json.loads(...)JSON 字符串 → Python 字典
6Task(**dict)字典解包 → Task 对象，如 Task(id="task_xxx", subject="写提纲", ...)
7[Task(...) for p in ...]最终得到一个 Task 对象列表 [Task1, Task2, Task3]

glob 是什么？

Path.glob(pattern) 是 pathlib 的**文件通配匹配**方法：

  • * 匹配任意多个字符（不含路径分隔符）
  • ? 匹配单个字符
  • ** 匹配任意层级的子目录

TASKS_DIR.glob("task_*.json") 的意思就是："在 .tasks/ 目录下，找到所有以 task_ 开头、以 .json 结尾的文件"。

重要理解：列表推导式 [expr for x in xs if cond] 是 Python 核心语法。从上表可以逐层拆解它的执行流程。本代码在 L76、L100、L113 三处用了列表推导式，非常值得反复练习。

6 依赖系统：blockedBy 与 can_start

代码位置：L87-94

def can_start(task_id: str) -> bool:
    """Check if all blockedBy dependencies are completed.
    Missing dependencies are treated as blocked."""
    task = load_task(task_id)
    for dep_id in task.blockedBy:
        if not _task_path(dep_id).exists():
            return False
        if load_task(dep_id).status != "completed":
            return False
    return True

两个阻塞条件

  1. 依赖文件不存在 → 阻塞（被删了或从未创建，load_task 会抛 FileNotFoundError，所以先检查文件存在）
  2. 依赖存在但未完成 → status != "completed" 则阻塞

全部通过才返回 True。

状态流转图

┌──────────┐ claim_task() ┌────────────┐ complete_task() ┌───────────┐ │ pending │ ──────────────► │ in_progress │ ─────────────────► │ completed │ │ (待处理) │ │ (进行中) │ │ (已完成) │ └──────────┘ └────────────┘ └───────────┘ ▲ │ │ blockedBy 依赖 │ 完成时自动检查下游 │ 全部完成才能认领 │ 是否有任务被解除阻塞 └──────────────────────────────┘
课程核心：is_ready()（即代码中的 can_start()）是本章最关键的一条判断规则。任务系统的核心不是"保存清单"，而是"判断什么时候能开工"。

7 claim_task：认领任务的两道检查

代码位置：L96-107

def claim_task(task_id: str, owner: str = "agent") -> str:
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    if not can_start(task_id):
        deps = [d for d in task.blockedBy
                           if not _task_path(d).exists() or load_task(d).status != "completed"]
        return f"Blocked by: {deps}"
    task.owner = owner
    task.status = "in_progress"
    save_task(task)
    print(f"  \033[36m[claim] {task.subject} → in_progress (owner: {owner})\033[0m")
    return f"Claimed {task.id} ({task.subject})"

两道检查

  1. 状态检查：只有 pending 的任务才能被认领。已经是 in_progress 或 completed 的，直接返回错误。
  2. 依赖检查：调用 can_start()，如果不满足，额外计算具体被哪些依赖阻塞，一并返回以便下游调试。

deps 列表推导式详解

deps = [d for d in task.blockedBy
        if not _task_path(d).exists() or load_task(d).status != "completed"]

等价于：

deps = []
for d in task.blockedBy:            # 遍历依赖列表
    if not _task_path(d).exists():  # 条件1：文件不存在
        deps.append(d)
    elif load_task(d).status != "completed":  # 条件2：存在但没完成
        deps.append(d)

最终得到的是阻塞依赖的 ID 列表，如 ["task_A", "task_B"]。

关于 \033[36m

这是 ANSI 转义码，用于终端颜色输出：

  • \033[36m — 青色（用于 claim/create 日志）
  • \033[32m — 绿色（用于 complete 日志）
  • \033[33m — 黄色（用于 unblocked 日志）
  • \033[34m — 蓝色（用于 create 日志）
  • \033[0m — 重置颜色

8 complete_task：完成 + 级联解锁

代码位置：L109-124

def complete_task(task_id: str) -> str:
    task = load_task(task_id)
    if task.status != "in_progress":
        return f"Task {task_id} is {task.status}, cannot complete"
    task.status = "completed"
    save_task(task)
    unblocked = [t.subject for t in list_tasks()
                           if t.status == "pending" and t.blockedBy and can_start(t.id)]
    print(f"  \033[32m[complete] {task.subject} ✓\033[0m")
    msg = f"Completed {task.id} ({task.subject})"
    if unblocked:
        msg += f"\nUnblocked: {', '.join(unblocked)}"
        print(f"  \033[33m[unblocked] {', '.join(unblocked)}\033[0m")
    return msg

核心逻辑

  1. 状态校验：只有 in_progress 的任务才能完成
  2. 保存：更新状态为 completed，写入磁盘
  3. 级联解锁：检查有哪些下游任务因此解除了阻塞

unblocked 列表推导式拆解

unblocked = [t.subject for t in list_tasks()
             if t.status == "pending" and t.blockedBy and can_start(t.id)]

三个条件（按 and 短路求值顺序）：

条件作用为什么需要？
t.status == "pending"只看还没开始的任务已在进行的或已完成的任务不用管
t.blockedBy必须有依赖列表（非空）空列表是 False，没有依赖的任务本来就能开始，不属于"被解除阻塞"
can_start(t.id)检查所有依赖是否全部完成当前任务的完成可能让某个依赖全部满足，这个条件就变成 True
级联解锁示例：
假设 task_A（写提纲）完成后，task_B（写初稿）和 task_C（写摘要）都依赖于 task_A。
在 complete_task("task_A") 中，unblocked = ["写初稿", "写摘要"]，然后输出：
[complete] 写提纲 ✓
[unblocked] 写初稿, 写摘要

run_create_task(subject, description, blockedBy)（L198-204）

  • 拼接可选的 blockedBy 说明文字：', '.join(blockedBy)
  • 打印蓝色终端日志，返回描述性字符串给 LLM

  • 状态图标映射：pending → ○ / in_progress → ● / completed → ✓
  • 条件拼接：依赖说明 (blockedBy: ...) 和责任人 [owner]
  • 空列表友好提示："No tasks. Use create_task to add some."

  • 捕获 FileNotFoundError，返回友好错误消息而非让程序崩溃

  • 固定 owner="agent"，避免 LLM 乱传 owner
  • 保留包装层以备将来添加权限检查、审计日志

run_complete_task(task_id)（L225-232）

  • 最简包装，直接透传给 core 层
  • 保留包装层是为了架构一致性
三层架构的好处：修改隔离（改格式只改 Layer 1，改业务规则只改 Layer 2）、测试方便（可单独测试 core 层）、可演变（Layer 1 可从简单包装演变为鉴权、限流）。

与 s11 的差异

s12 的 TOOL_HANDLERS 直接传函数引用（如 "bash": run_bash），而 s11 用了 lambda **kw: run_bash(kw["command"])。原因是 s12 的 run_bash 函数签名直接匹配工具参数名，不需要 lambda 解包。

11 Prompt 组装系统

代码位置：L126-159

整体结构

PROMPT_SECTIONS = {                              # 模板段落"原材料"
    "identity": "You are a coding agent. Act, don't explain.",
    "tools": "Available tools: bash, read_file, ...",
    "workspace": f"Working directory: {WORKDIR}",
    "memory": "Relevant memories are injected below when available.",
}

def assemble_system_prompt(context: dict) -> str:
    sections = [PROMPT_SECTIONS["identity"],    # 1. 身份
                PROMPT_SECTIONS["tools"],       # 2. 工具
                PROMPT_SECTIONS["workspace"]]   # 3. 工作目录
    memories = context.get("memories", "")       # 4. 长期记忆（条件添加）
    if memories:
        sections.append(f"Relevant memories:\n{memories}")
    return "\n\n".join(sections)               # 用两个换行符拼接各段

为什么这样设计？

  • 分片段存储：各段独立，改一段不影响其他段
  • 条件组装：memory 只在有内容时才拼入
  • "分隔符".join(列表)：用空行分隔段落，LLM 更容易区分不同部分

缓存机制

_last_context_key, _last_prompt = None, None

def get_system_prompt(context: dict) -> str:
    global _last_context_key, _last_prompt
    key = json.dumps(context, sort_keys=True,
                      ensure_ascii=False, default=str)
    if key == _last_context_key and _last_prompt:
        return _last_prompt                 # 缓存命中，跳过组装
    _last_context_key = key
    _last_prompt = assemble_system_prompt(context)
    return _last_prompt
参数作用
sort_keys=True字典键排序，保证同样内容生成同样的键
ensure_ascii=False中文等非 ASCII 字符不转义
default=str不可序列化的类型（如 Path）强转字符串
为什么需要缓存？每一轮对话都要传 system prompt 给 LLM，但 context 可能很久不变。每次都重新组装和 JSON 序列化是浪费的。缓存通过比较 context 的 JSON 指纹来避免重复工作。

12 context 与 update_context

代码位置：L287-298

def update_context(context: dict, messages: list) -> dict:
    """Derive context from real state."""
    memories = ""
    if MEMORY_INDEX.exists():
        content = MEMORY_INDEX.read_text().strip()
        if content:
            memories = content
    return {
        "enabled_tools": list(TOOL_HANDLERS.keys()),
        "workspace": str(WORKDIR),
        "memories": memories
    }

context 是什么？

context 是一个只有 3 个键的小字典，不是"全部上下文"：

字段来源作用
enabled_toolsTOOL_HANDLERS.keys()告诉 LLM 当前可用工具列表
workspacestr(WORKDIR)工作目录路径
memories.memory/MEMORY.md 文件长期记忆内容

context 不是"全部上下文"

整个程序运行中的信息分成了三块：

┌───────────────────────────────────────────────────────┐ │ 程序运行的"全貌" │ │ │ │ context（字典） messages（列表） tools（映射表）│ │ ┌──────────────┐ ┌──────────────┐ ┌─────────┐ │ │ │ enabled_tools│ │ {"role": │ │ bash → │ │ │ │ workspace │ │ "user", │ │ 函数 │ │ │ │ memories │ │ "content": │ │ read → │ │ │ └──────────────┘ │ "你好..."} │ │ 函数 │ │ │ │ │ {"role": │ │ ... │ │ │ │ │ "assistant",│ └─────────┘ │ │ ▼ │ "content": │ │ │ 传给 system 参数 │ "..."} │ │ │ └──────────────┘ │ │ │ │ │ 传给 messages 参数 │ └───────────────────────────────────────────────────────┘
  • context → 注入 system prompt 的"静态背景知识"
  • messages → 对话历史，传给 API 的 messages 参数
  • TOOL_HANDLERS → 工具名到函数的映射，由路由代码使用

memories 的来源

memories 来自文件 .memory/MEMORY.md（如果存在的话）。update_context 每次被调用时都重新读取这个文件。

半成品状态：目前代码只有"读取 MEMORY.md"的逻辑，没有任何地方写入这个文件。所以 memories 的读取基础设施已就位，但写入功能尚未实现。如果有人手动创建 .memory/MEMORY.md 并写入内容，系统能正确读取并拼入 prompt。

13 agent_loop 详解：ReAct 循环

代码位置：L302-341

def agent_loop(messages: list, context: dict) -> None:
    system = get_system_prompt(context)       # [A] 进入循环前组装 system
    while True:                               # [B] 直到 LLM 不再调工具
        try:
            response = client.messages.create(  # [C] 调用 LLM API
                model=MODEL, system=system, messages=messages,
                tools=TOOLS, max_tokens=8000)
        except Exception as e:
            messages.append({"role": "assistant", "content": [
                {"type": "text",
                 "text": f"[Error] {type(e).__name__}: {e}"}]})
            return                            # [D] 出错返回

        messages.append({"role": "assistant", "content": response.content})  # [E]
        if response.stop_reason != "tool_use":
            return                            # [F] end_turn → 正常退出

        # -- Process tool calls --
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue                       # [G1] 跳过文本块
            print(f"\033[36m> {block.name}\033[0m")
            handler = TOOL_HANDLERS.get(block.name)       # [G2] 查找处理函数

            try:
                output = handler(**(block.input or {})) if handler else f"Unknown: {block.name}"
            except Exception as e:
                output = f"Error: {e}"                 # [G3] 工具内异常不崩溃

            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": str(output),
            })                                          # [G4] 构建 tool_result

        messages.append({"role": "user", "content": results})  # [H] 工具结果放回
        context = update_context(context, messages)            # [I] 更新 context
        system = get_system_prompt(context)                    # [J] 重新组装 system

完整执行流程

┌──────────────┐ │ 组装 system │ ← [A] 进入循环前 └──────┬───────┘ ▼ ┌──────────────┐ stop_reason ┌────────────────┐ │ 调用 LLM │ ──── "end_turn" ──► │ 退出循环，返回 │ │ API │ └────────────────┘ └──────┬───────┘ │ stop_reason = "tool_use" ▼ ┌──────────────┐ │ 执行所有工具 │ ← 可能有多个 tool_use 块 │ (可能多个) │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ 结果放回消息 │ │ 更新 context │ │ 重新组装 │ │ system prompt│ └──────┬───────┘ │ └──→ 回到"调用 LLM API" ──→ 直到 LLM 不再调工具

关键细节

代码含义
handler(**(block.input or {}))字典解包调用。如 block.input = {"subject": "写提纲"} → run_create_task(subject="写提纲")
stop_reason == "tool_use"LLM 请求调用工具 → 继续循环
stop_reason == "end_turn"LLM 给出最终回复 → 退出循环
results 的 "role": "user"Anthropic API 约定：tool_result 必须以 user 角色发回
type(e).__name__获取异常类名，如 "AuthenticationError"
与 s11 的关键差异：s12 的 agent_loop 是简化版——只保留最基本的 ReAct 循环，没有 s11 的 max_tokens 续接、prompt_too_long 压缩、连接退避重试等三层错误恢复。课程设计意图是"正交层分离"：错误恢复和任务系统是独立的能力，教学中分开讲，产品中通过组合使用。

整体流程

  2. 用户输入 → 追加到 history → 进入 agent_loop

易混淆点速查

json.dumps 不是写文件的
json.dumps(obj) 是把对象转为 JSON 字符串。Path.write_text() 才负责写文件。两者通过链式调用配合：path.write_text(json.dumps(data))。
glob 只匹配文件名，不匹配内容
Path.glob("task_*.json") 只根据文件名做通配符匹配，和文件内容无关。匹配到的每个 Path 对象需要你手动 read_text() 再 json.loads() 来获取内容。
列表推导式 [Task(...) for p in ...] 不会自动命名
执行结果得到一个列表，里面的 Task 对象没有叫 Task1、Task2 的名字。你只能通过下标 result[0] 或遍历 for t in result 来访问它们。
sorted(...) 不修改原数据
sorted(TASKS_DIR.glob(...)) 返回一个新的排序后的列表，不会改变原 glob 迭代器的状态。
