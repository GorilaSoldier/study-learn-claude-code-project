1 章节主旨

核心一句话：把任务分配的决策权从 Lead 转移到 Teammate，让队友变成"自治智能体"而不是"被动执行者"。

解决了什么问题：s16 的队友能通信、能握手关机。但每个队友等 Lead 分配任务——如果任务看板上有 10 个未认领任务，Lead 得手动 assign 10 次。这不能扩展。

解决方案：队友应该自己看任务看板，发现没人做的任务就认领，做完再找下一个。

课程原话："自己看板，自己认领" — 空闲时轮询，有活就干。

核心转变

s16: Lead → 手动分配 → Teammate 执行 s17: Lead → 创建任务看板 → Teammate 自己扫描 → 自己认领 → 执行

三阶段生命周期

阶段行为退出条件
WORKinbox → LLM → 工具循环stop_reason != "tool_use"
IDLE每 5s 轮询 inbox + 任务板60s 超时 或 收到 shutdown
SHUTDOWN发 summary，退出—
心智模型：队友不是"做完就跑"，而是"做完等一会儿，看看还有没有活"。

2 最小心智模型

自治的核心是"空闲后主动找活"，而不是被动等待分配。

┌─────────────────────────────────────────────────────┐ │ Teammate 线程 │ │ │ │ while True: │ │ # WORK 阶段 │ │ for _ in range(10): │ │ 检查 inbox → LLM 推理 → 执行工具 │ │ if stop_reason != "tool_use": break │ │ │ │ # IDLE 阶段 │ │ idle_result = idle_poll(...) │ │ if idle_result == "shutdown": break │ │ if idle_result == "timeout": break │ │ # "work" → 回到 WORK 阶段继续 │ │ │ │ # SHUTDOWN │ │ BUS.send(name, "lead", summary, "result") │ └─────────────────────────────────────────────────────┘

idle_poll 三种返回值

返回值含义行为
"work"收到消息或自动认领了任务不 break，回到 WORK 阶段
"shutdown"收到关机命令break 退出 while 循环
"timeout"60 秒无人问津break 退出 while 循环

关键设计

  • 外层 while True：WORK 和 IDLE 交替进行，直到超时或收到关机请求
  • 内层 for 10：WORK 阶段最多 10 轮 LLM 调用（防止无限循环）
  • IDLE 超时 60 秒：12 次轮询 × 5 秒 = 60 秒
  • shutdown_request 两阶段都能响应：WORK 阶段通过 handle_inbox_message 分发；IDLE 阶段 idle_poll 直接检查并回复

3 idle_poll 空闲轮询

职责：队友完成当前任务后不退出，进入 IDLE 阶段——每 5 秒检查一次有没有新工作。

# 常量定义
IDLE_POLL_INTERVAL = 5   # seconds
IDLE_TIMEOUT = 60        # seconds

def idle_poll(agent_name: str, messages: list,
              name: str, role: str) -> str:
    """Poll for 60s. Return 'work', 'shutdown', or 'timeout'."""
    for _ in range(IDLE_TIMEOUT // IDLE_POLL_INTERVAL):
        time.sleep(IDLE_POLL_INTERVAL)

        # ① 检查收件箱（优先）
        inbox = BUS.read_inbox(agent_name)
        if inbox:
            # shutdown_request 立即处理
            for msg in inbox:
                if msg.get("type") == "shutdown_request":
                    req_id = msg.get("metadata", {}).get("request_id", "")
                    BUS.send(name, "lead", "Shutting down gracefully.",
                             "shutdown_response",
                             {"request_id": req_id, "approve": True})
                    return "shutdown"
            # 普通消息注入上下文，回到 WORK
            messages.append({"role": "user",
                "content": "<inbox>" + json.dumps(inbox) + "</inbox>"})
            return "work"

        # ② 扫描任务看板
        unclaimed = scan_unclaimed_tasks()
        if unclaimed:
            task = unclaimed[0]
            result = claim_task(task["id"], agent_name)
            if "Claimed" in result:
                messages.append({"role": "user",
                    "content": f"<auto-claimed>Task {task['id']}: "
                               f"{task['subject']}</auto-claimed>"})
                return "work"

    return "timeout"

关键细节

片段解释
for _ in range(12)60 / 5 = 12 次轮询
time.sleep(5)每次等待 5 秒
inbox 优先检查协议消息（shutdown_request）优先处理，不等到下一轮
任务板其次没有 inbox 消息才扫描任务看板
"Claimed" in result检查认领结果，失败不注入
为什么 inbox 优先？因为 shutdown_request 等协议消息需要立即响应，不能等到下一轮轮询。

4 scan_unclaimed_tasks 扫描任务看板

职责：找 pending 状态、无 owner、所有依赖已完成（can_start）的任务。

def scan_unclaimed_tasks() -> list[dict]:
    """Find pending, unowned tasks with all dependencies completed."""
    unclaimed = []
    for f in sorted(TASKS_DIR.glob("task_*.json")):
        task = json.loads(f.read_text())
        if (task.get("status") == "pending"
                and not task.get("owner")
                and can_start(task["id"])):
            unclaimed.append(task)
    return unclaimed

三个条件

条件解释
task.get("status") == "pending"必须是待处理状态
not task.get("owner")没有 owner（没人认领）
can_start(task["id"])所有 blockedBy 依赖已完成

can_start 依赖检查

def can_start(task_id: str) -> bool:
    task = load_task(task_id)
    for dep_id in task.blockedBy:
        if not _task_path(dep_id).exists():
            return False
        if load_task(dep_id).status != "completed":
            return False
    return True
注意：有依赖不代表不能做，只有被未完成的任务阻塞才不能做。教学版按文件名排序取第一个；CC 用文件锁防止多个队友同时认领同一个任务。

5 claim_task owner 检查

s17 新增：认领前检查 task.owner，防止多个队友抢同一个任务。

def claim_task(task_id: str, owner: str = "agent") -> str:
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    if task.owner:                              # ← s17 新增
        return f"Task {task_id} already owned by {task.owner}"
    if not can_start(task_id):
        deps = [d for d in task.blockedBy
                if _task_path(d).exists() and load_task(d).status != "completed"]
        missing = [d for d in task.blockedBy if not _task_path(d).exists()]
        parts = []
        if deps: parts.append(f"blocked by: {deps}")
        if missing: parts.append(f"missing deps: {missing}")
        return "Cannot start — " + ", ".join(parts)
    task.owner = owner
    task.status = "in_progress"
    save_task(task)
    return f"Claimed {task.id} ({task.subject})"

s16 vs s17 对比

版本claim_task 检查项
s16status 检查 + can_start 依赖检查
s17status 检查 + owner 检查 + can_start 依赖检查
教学版没有文件锁，并发认领可能出现竞争。但至少 task.owner 检查避免了最明显的"后写覆盖"问题。CC 用 proper-lockfile 保护任务文件。

7 handle_inbox_message 协议分发

职责：处理一条收到的协议消息，返回 True 表示需要关机，False 表示不需要。

def handle_inbox_message(name: str, msg: dict, messages: list):
    """Dispatch incoming protocol messages by type."""
    msg_type = msg.get("type", "message")
    meta = msg.get("metadata", {})
    req_id = meta.get("request_id", "")

    if msg_type == "shutdown_request":
        BUS.send(name, "lead", "Shutting down gracefully.",
                 "shutdown_response",
                 {"request_id": req_id, "approve": True})
        return True  # 需要关机

    if msg_type == "plan_approval_response":
        approve = meta.get("approve", False)
        if approve:
            messages.append({"role": "user",
                "content": "[Plan approved] Proceed with the task."})
        else:
            messages.append({"role": "user",
                "content": f"[Plan rejected] Feedback: {msg['content']}"})
    return False

两种协议消息处理

消息类型处理方式返回值
shutdown_request回复 shutdown_response，approve=TrueTrue（关机）
plan_approval_response注入审批结果到 messagesFalse（继续）
设计模式：调用者遍历 inbox 列表，对每条消息调用一次这个函数。函数只知道自己该处理一条消息，职责单一，可复用。

8 WORK → IDLE → SHUTDOWN 生命周期

s17 的核心：队友做完任务不退出，而是进入 IDLE 阶段继续找活。

# Outer loop: WORK → IDLE cycle
while True:
    # Identity re-injection (s17)
    if len(messages) <= 3:
        messages.insert(0, {"role": "user",
            "content": f"<identity>You are '{name}', role: {role}. "
                       f"Continue your work.</identity>"})

    # WORK phase
    should_shutdown = False
    for _ in range(10):
        inbox = BUS.read_inbox(name)
        for msg in inbox:
            stopped = handle_inbox_message(name, msg, messages)
            if stopped:
                should_shutdown = True
                break
        if should_shutdown:
            break
        # ... LLM 调用 + 工具执行 ...
        if response.stop_reason != "tool_use":
            break

    if should_shutdown:
        break

    # IDLE phase (s17 new)
    idle_result = idle_poll(name, messages, name, role)
    if idle_result == "shutdown":
        break
    if idle_result == "timeout":
        break

# Summary
BUS.send(name, "lead", summary, "result")
active_teammates.pop(name, None)

流程图

spawn_teammate_thread() ├── 创建线程，立即返回（不阻塞） └── run() 在新线程中执行: ├── [身份重注入] ├── WORK 阶段 (最多10轮) │ └── 检查邮箱 → LLM推理 → 执行工具 → 循环 ├── IDLE 阶段 (60秒轮询) │ ├── 有消息？ → 回到 WORK │ ├── 有任务？ → 自动认领 → 回到 WORK │ ├── 关机命令？ → 退出 │ └── 超时？ → 退出 └── 发送总结报告 → 从活跃列表移除

9 身份重注入机制

问题：messages[-20:] 截断历史后，队友可能忘记自己是谁。

解决：每次进入 WORK 阶段时，如果 messages 很短（说明被压缩了），重新注入身份。

if len(messages) <= 3:
    messages.insert(0, {"role": "user",
        "content": f"<identity>You are '{name}', role: {role}. "
                   f"Continue your work.</identity>"})
片段解释
len(messages) <= 3多数情况是 True——新鲜线程只有初始 prompt。超过 3 条说明上下文被压缩过
messages.insert(0, ...)在列表头部插入，LLM 一开始就看到身份提示
<identity>...</identity>自定义 XML 标签，让 LLM 识别这是身份重申指令
真实 CC 中，context compaction 会保留 system prompt。教学版的简化实现需要手动处理。

10 consume_lead_inbox 统一收件入口

职责：读取 Lead 的邮箱，自动路由协议响应，返回所有消息。

def consume_lead_inbox(route_protocol: bool = True) -> list[dict]:
    msgs = BUS.read_inbox("lead")
    if not msgs:
        return []
    if route_protocol:
        for msg in msgs:
            meta = msg.get("metadata", {})
            req_id = meta.get("request_id", "")
            msg_type = msg.get("type", "")
            if req_id and msg_type.endswith("_response"):
                approve = meta.get("approve", False)
                match_response(msg_type, req_id, approve)
    return msgs

协议响应自动路由

消息类型以 _response 结尾？触发 match_response？
shutdown_response✅✅
plan_approval_response✅✅
message❌❌
result❌❌

被谁调用

  • run_check_inbox 工具——Lead LLM 主动调用 check_inbox
  • 主循环末尾——每次用户输入一轮对话后，自动检查 inbox 并注入
关键：无论是哪种调用路径，协议响应都会被正确路由到 match_response，更新 pending_requests 状态。

11 run_review_plan 计划审批

职责：Lead 审批 Teammate 提交的计划。

def run_review_plan(request_id: str, approve: bool,
                    feedback: str = "") -> str:
    state = pending_requests.get(request_id)
    if not state:
        return f"Request {request_id} not found"
    if state.status != "pending":
        return f"Request {request_id} already {state.status}"

    state.status = "approved" if approve else "rejected"
    BUS.send("lead", state.sender,
             feedback or ("Approved" if approve else "Rejected"),
             "plan_approval_response",
             {"request_id": request_id, "approve": approve})
    return f"Plan {'approved' if approve else 'rejected'} ({request_id})"

核心代码拆解

feedback or ("Approved" if approve else "Rejected")
approvefeedback最终 content 值
True"" (空)"Approved"
True"Good job!""Good job!"
False"" (空)"Rejected"
False"Missing tests""Missing tests"
短路求值 + 三元表达式：如果 Lead 提供了反馈文本，就用反馈；否则用默认的 "Approved" 或 "Rejected"。

approve 参数来源

是的，Lead LLM 自动决定调用，参数也是它自己填的。

1. Teammate submit_plan() → 发送 plan_approval_request 2. Lead inbox 收到 → 注入 history 3. Lead LLM 推理 → 决定 approve=True/False 4. Lead LLM 生成 tool_use: review_plan(request_id, approve, feedback) 5. 代码执行 run_review_plan(...)

12 Lead inbox 注入机制

问题：s16 的 Lead inbox 只打印在终端，LLM 看不到，无法做出决策。

解决：s17 把 inbox 内容注入到 Lead 的 history，LLM 能看到并调用相应工具。

# 主循环末尾
inbox = consume_lead_inbox(route_protocol=True)
if inbox:
    inbox_text = "\n".join(
        f"From {m['from']} [{m.get('type', 'message')}]: "
        f"{m['content'][:200]}" for m in inbox)
    history.append({"role": "user",
                    "content": f"[Inbox]\n{inbox_text}"})

关键细节

片段解释
m['content'][:200]截取前 200 字符，防止消息太长撑爆上下文
"role": "user"伪装成用户消息，LLM 会把它当作输入处理
[Inbox]标签包裹，让 LLM 知道"这是你的收件箱内容"
一句话：把"被动收到的消息"变成"LLM 能看到的对话输入"，让 Lead LLM 能根据这些消息做出决策。

14 常见困惑与 FAQ

Q1: {task['subject']} 为什么不是 task[subject]？

答案：字典键名要用引号括起来变成字符串字面量，否则 Python 会把它当成变量名去查找。 
task['subject']   # ✅ 正确：用字符串 "subject" 做键名
task[subject]     # ❌ 错误：用变量 subject 的值做键名

Q2: read_inbox 是一次性取所有 inbox 吗？

答案：是的，一次性全取出来，读完就删除文件（inbox.unlink()）。语义是"把积压的所有消息一次性拿走，然后清空邮箱"。

Q3: handle_inbox_message 只处理一条消息？

答案：是的，函数签名是单条消息 msg: dict。调用方负责遍历 inbox 列表，对每条消息调用一次这个函数。

Q4: approve 参数在哪里赋值的？

答案：approve 字段是在发消息的一方设置的。Lead 审批时调用 run_review_plan，传入 approve=True/False，然后 BUS.send 时写入 metadata。

Q5: inbox 里除了 "message" 还有什么类型？

类型用途
message普通对话消息
shutdown_request关机请求
shutdown_response关机确认
plan_approval_request计划审批请求
plan_approval_response计划审批回复
resultTeammate 结束时的总结报告

Q6: "result" 是队友返回结果的标志吗？

答案：是的，msg_type="result" 表示"这是 Teammate 结束工作后的总结报告"，和普通 "message" 的区别在于语义——"result" 是"人已经走了，这是留的便条"。

Q7: run_review_plan 是 Lead LLM 自动调用的吗？

答案：是的。LLM 根据对话上下文推理，决定调用 review_plan 工具，自己填写 request_id、approve、feedback 参数。代码只提供工具定义和处理函数，LLM 负责决策。

三元表达式详解

# 基本形式
值1 if 条件 else 值2

# 示例
"approved" if approve else "rejected"

# 等价于
if approve:
    state.status = "approved"
else:
    state.status = "rejected"

短路求值详解

# a or b
# 如果 a 是 truthy（非空、非零、非 None），返回 a
# 如果 a 是 falsy，返回 b

feedback or "Approved"
# feedback="Good job!" → 返回 "Good job!"
# feedback="" → 返回 "Approved"

for-else 语法

for item in items:
    if condition:
        break
else:
    # 如果 for 循环没有 break，执行这里
    print("没有找到")

字典解包 **

# **dict 把字典展开成关键字参数
block.input = {"command": "ls"}
handler(**block.input)  # 等价于 handler(command="ls")
