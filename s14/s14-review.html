1 章节主旨：后台任务 vs 定时调度

核心一句话：后台任务是在"等结果"，定时调度是在"等开始"。

s13 解决的问题：慢命令丢到后台线程执行——"稍后回来拿结果"。

s14 要解决的问题：很多需求不是"现在做"，而是"将来某个时间再做"。如每天晚上跑测试、每周一早上生成报告、30 分钟后提醒。

最核心的设计思想：定时任务并不是另一套 agent——它最终还是回到同一条主循环。调度器做的是"记住未来"，不是"取代主循环"。
机制回答的问题
后台任务（s13）"已经启动的慢操作，结果什么时候回来？"
定时调度（s14）"一件事应该在未来什么时候开始？"

2 最小心智模型

1. 调度记录 (Schedule Record) — 记住未来什么时间要做什么事 2. 定时检查器 (Timer Checker) — 后台线程每秒检查"现在是否匹配" 3. 通知队列 (Notification Queue) — 如果匹配，把任务放进队列等主循环处理

它们的关系：schedule_job() → 写入 scheduled_jobs + 磁盘 → cron_scheduler_loop 每秒检查 → 匹配则放入 cron_queue → queue_processor_loop 空闲时取走 → agent_loop 伪装成用户消息喂给 AI。

3 整体架构：4 层 + 3 线程

5 Cron 表达式匹配引擎

5.1 单字段匹配 (L289-L307)

def _cron_field_matches(field: str, value: int) -> bool:
    if field == "*": return True
    if field.startswith("*/"): step = int(field[2:]); return value % step == 0
    if "," in field: return any(_cron_field_matches(f.strip(), value) for f in field.split(","))
    if "-" in field: lo, hi = field.split("-", 1); return int(lo) <= value <= int(hi)
    return value == int(field)
语法示例逻辑
*"*"通配符，永远匹配
*/N"*/15"value % N == 0
A,B,C"1,3,5"递归检查，任一匹配即可
L-H"9-17"L <= value <= H
精确值"30"value == int(field)

5.2 完整表达式匹配 (L308-L339)

5 个字段：minute, hour, day-of-month (dom), month, day-of-week (dow)。

星期坐标转换：dow_val = (dt.weekday() + 1) % 7（Python Monday=0 → Cron Sunday=0）。

5.3 DOM 和 DOW 的 OR 逻辑（核心）

标准 cron 语义：分钟、小时、月用 AND；日和星期用 OR。

DOMDOW结果
**每天匹配
*有约束只看 DOW
有约束*只看 DOM
有约束有约束OR：任一匹配即可
为什么用 OR？ 例："0 9 15 * 5" = "每月15号以及每个周五"，不是"每月15号且恰好是周五"。

7 持久化：save / load durable jobs

保存 (L388-L393)

def save_durable_jobs():
    durable = [asdict(j) for j in scheduled_jobs.values() if j.durable]
    DURABLE_PATH.write_text(json.dumps(durable, indent=2))

遍历所有 job，取 durable=True 的写入磁盘。覆盖写——始终与内存状态一致。

加载 (L394-L409)

def load_durable_jobs():
    if not DURABLE_PATH.exists(): return
    try:
        jobs = json.loads(DURABLE_PATH.read_text())
        for j in jobs:
            job = CronJob(**j)               # 字典解包
            err = validate_cron(job.cron)     # 防御性校验
            if err: continue
            scheduled_jobs[job.id] = job

CronJob(**j) = CronJob(id=j["id"], cron=j["cron"], ...)。加载时重新校验 cron 表达式，防止磁盘文件被手动编辑出错。

关系：schedule_job = 存（内存+磁盘）；load_durable_jobs = 取（磁盘→内存）。

8 注册与取消：schedule_job / cancel_job

注册 (L410-L419)

def schedule_job(cron, prompt, recurring=True, durable=True) -> CronJob | str:
    err = validate_cron(cron)
    if err: return err
    job = CronJob(id=f"cron_{random.randint(0,999999):06d}", ...)
    with cron_lock: scheduled_jobs[job.id] = job
    if durable: save_durable_jobs()
    return job

成功返回 CronJob 对象，失败返回错误字符串。:06d 格式化为至少 6 位十进制补零。

取消 (L420-L429)

def cancel_job(job_id):
    with cron_lock: job = scheduled_jobs.pop(job_id, None)
    if not job: return f"Job {job_id} not found"
    if job.durable: save_durable_jobs()
    return f"Cancelled {job_id}"

dict.pop(key, default) 删除 key 并返回 value，不存在返回默认值（不抛 KeyError）。

9 调度器主循环：cron_scheduler_loop

代码位置：L430-L456

def cron_scheduler_loop():
    while True:
        time.sleep(1)
        now = datetime.now()
        minute_marker = now.strftime("%Y-%m-%d %H:%M")
        with cron_lock:
            for job in list(scheduled_jobs.values()):
                try:
                    if cron_matches(job.cron, now):
                        if _last_fired.get(job.id) != minute_marker:
                            cron_queue.append(job)
                            _last_fired[job.id] = minute_marker
                        if not job.recurring:
                            scheduled_jobs.pop(job.id, None)
                            if job.durable: save_durable_jobs()
                except Exception as e:
                    print(f"[cron error] {job.id}: {e}")
设计代码目的
每秒轮询time.sleep(1)分钟级任务，1s 足够
日期感知标记minute_marker含日期信息，天然区分"今天"和"明天"
防重复触发_last_fired.get(id) != marker同一分钟内不放行两次
快照遍历list(scheduled_jobs.values())遍历时安全修改 dict
故障隔离try/except 包住单个 job一个 job 抛异常不杀死整个线程
为什么用 minute_marker 不用计数器？假设 cron="0 9 * * *"：第1天09:00 → fire；第2天09:00 → 计数器还在 → 错误跳过。用 "2026-06-19 09:00" 这样的 marker 天然知道是新的一天。

10 消费队列：consume / has_cron_queue

代码位置：L457-L467

def consume_cron_queue() -> list[CronJob]:
    with cron_lock:
        fired = list(cron_queue)
        cron_queue.clear()
    return fired

def has_cron_queue() -> bool:
    with cron_lock: return bool(cron_queue)

这是调度线程 ↔ agent 主循环之间的桥梁。调度线程写队列，投递线程读队列。

为什么用 list(cron_queue) + clear()？ 不能直接 return cron_queue（外部可能修改），也不能在锁外清空（可能丢失数据）。锁内拷贝快照 + 清空原列表是标准做法。

不能写成 cron_queue = [] 重新赋值——这会断开引用，其他线程如果还持有旧列表引用，会继续往旧列表里写，导致数据丢失。

11 投递系统：queue_processor_loop

代码位置：L640-L652

def queue_processor_loop():
    global session_context
    while True:
        time.sleep(0.2)
        if not has_cron_queue(): continue
        if not agent_lock.acquire(blocking=False): continue
        try:
            if not has_cron_queue(): continue
            run_agent_turn_locked()
        finally:
            agent_lock.release()
设计目的
agent_lock.acquire(blocking=False)非阻塞获取锁。agent 忙就不等，下次再试。不打断用户交互。
双重检查 has_cron_queue()防止拿到锁后 job 已被取走的竞态条件
try/finally保证锁一定会释放，即使抛异常

12 agent_loop 里的消费逻辑

代码位置：L567-L571

# agent_loop 每轮循环开头：
fired = consume_cron_queue()                    # ⭐ 从队列取出
for job in fired:
    messages.append({"role": "user",               # 伪装成用户消息
                     "content": f"[Scheduled] {job.prompt}"})
关键理解：run_agent_turn_locked 本身没有投递逻辑。真正的投递发生在 agent_loop 内部——每轮循环开始时第一件事就是 consume_cron_queue()。

调用链：queue_processor_loop → run_agent_turn_locked() → agent_loop() → 开头 consume_cron_queue() → 注入到 messages → AI 看到并回复。

AI 看到 [Scheduled] 早上好 这条"用户消息"，就会像回复用户一样处理这个 cron job。

13 两把锁的设计：cron_lock vs agent_lock

锁保护什么使用场景
cron_lockscheduled_jobs, cron_queue, _last_fired调度线程和投递线程同时读写调度数据
agent_lockAI agent 的执行状态保证同一时间只有一个人（用户或 cron）使用 AI
比喻：agent_lock 像一把"只允许一个人说话"的麦克风。你打字时，cron 等着；你空闲时，cron 自动处理。

17 get_system_prompt 缓存机制

代码位置：L128-L136

_last_context_key, _last_prompt = None, None
def get_system_prompt(context: dict) -> str:
    global _last_context_key, _last_prompt
    key = json.dumps(context, sort_keys=True, ensure_ascii=False, default=str)
    if key == _last_context_key and _last_prompt:
        return _last_prompt                 # 命中缓存
    _last_context_key = key
    _last_prompt = assemble_system_prompt(context)  # 重新拼接
    return _last_prompt

大多数时候 context 没有变化，每次都重新拼接是浪费。用 _last_context_key（JSON 指纹）判断是否相同，相同则直接返回缓存的 prompt。

sort_keys=True 保证相同内容生成相同字符串；ensure_ascii=False 让中文不被转义；default=str 兜底无法序列化的类型。

19 常见困惑与 FAQ

Q1: 为什么需要两把锁？
A: cron_lock 保护调度数据，agent_lock 保护 AI 执行。不同资源分开加锁避免不必要阻塞。

Q2: consume_cron_queue 一次性全取走，不存在多个任务吗？
A: 对的，一次性全取走。多个 job 在同一分钟触发时，一次取走所有待处理的 job，避免频繁轮询。

Q3: cron_queue = [] 重新赋值 vs clear() 区别？
A: clear() 清空内容，对象不变，所有引用者看到"空了"。= [] 换新列表，其他线程还在引用旧列表，导致数据丢失。

Q4: 代码是伪代码吗？做不到真正的持久化？
A: 教学演示代码。重启后 durable=True 的 cron 任务从磁盘恢复，但对话历史、后台任务状态、_last_fired 都会丢失。

Q5: scheduled_jobs.values() 会有相同 job_id 吗？
A: 不会。dict 的 key 唯一，CronJob.id 随机生成不重复。

Q6: save_durable_jobs() 是追加写还是覆盖写？
A: 覆盖写。始终与内存状态一致。追加写无法处理删除操作。

Q7: 初学者最容易犯哪些错？

  1. 沉迷 cron 语法细节 — 主线其实是"调度记录如何进入通知队列并回到主循环"。
  2. 没有 last_fired_at — 没有防重复字段，会重复触发。
  3. 只放内存不支持落盘 — 重启就没了。
  4. 把调度触发结果在后台默默执行 — 应走通知队列，让主循环决定。
  5. 误以为必须绝对准点 — 这里更看重"有计划地触发"。

关于 if __name__ == "__main__"

模块级别代码从上到下依次执行。函数定义只定义不执行。if __name__ == "__main__" 是条件判断，确保直接运行时执行，被 import 时不执行。

注意：s14 的 load_durable_jobs() 和 Thread(cron_scheduler_loop).start() 在模块级别（L468-L469），不在 if __name__ 内。所以它们在文件被 import 时也会执行，设计上值得注意。
