1 章节主旨

核心一句话：给团队通信加上"编号 + 状态机 + 回执"，把自由聊天升级为结构化协议。

解决了什么问题：s15 让队友之间可以互相发消息。但如果所有事情都靠自由文本，会有两个明显问题：

  • 某些动作必须明确批准或拒绝，不能只靠一句模糊回复
  • 一旦多个请求同时存在，系统很难知道"这条回复对应哪一件事"

最典型的两个场景：

  1. 队友要不要优雅关机
  2. 某个高风险计划要不要先审批

这两件事看起来不同，但结构一样：一方发请求，另一方明确回复，双方都能用同一个 request_id 对上号。

课程原话："有了邮箱以后，团队已经能说话；有了协议以后，团队才开始会'按规矩协作'。"

2 最小心智模型

从教学角度，协议可以看成两层：

第1层：协议消息（ProtocolEnvelope） { "type": "shutdown_request", "from": "lead", "to": "alice", "request_id": "req_001", "payload": {}, } 第2层：请求追踪表（RequestRecord） requests = { "req_001": { "kind": "shutdown", "status": "pending" }, }

两层合在一起，系统就能同时回答两个问题：

  • 现在发生了什么（协议消息）
  • 这件事走到哪一步了（请求追踪表）

普通消息 vs 协议消息

维度普通消息协议消息
适用场景讨论、提醒、补充说明审批、关机、交接、签收
最小字段from / to / contenttype / request_id / from / to / payload
回答的问题"说了什么""这件事走到哪一步了"
处理方式注入 LLM 对话历史先 match_response 更新状态表，再注入

四个容易打结的对象

对象回答的问题典型字段
MessageEnvelope谁跟谁说了什么from / to / content
ProtocolEnvelope这是不是结构化请求/响应type / request_id / payload
RequestRecord协作流程走到哪一步kind / status / from / to
TaskRecord真正的工作项是啥、谁在做subject / status / blockedBy / owner
切记：协议请求不是任务本身。请求状态表也不是任务板。协议只负责"协作流程"，任务系统才负责"真正的工作推进"。

3 ProtocolState 与 pending_requests

3.1 ProtocolState dataclass

@dataclass
class ProtocolState:
    request_id: str             # 请求的唯一标识，如 "req_000042"
    type: str                   # "shutdown" | "plan_approval"
    sender: str                 # 谁发的请求
    target: str                 # 发给谁
    status: str                 # "pending" | "approved" | "rejected"
    payload: str               # 方案原文或关机原因
    created_at: float = field(default_factory=time.time)
字段说明类比
request_id请求的唯一编号快递单号
type两种：shutdown 或 plan_approval业务类型
sender发起方寄件人
target目标方收件人
status三态：pending → approved/rejected物流状态
payload附带的方案文本或原因包裹内容
created_atfield(default_factory=time.time)寄件时间戳，每次实例化时调用 time.time()，不共享

3.2 pending_requests 全局字典

pending_requests: dict[str, ProtocolState] = {}

这就是"请求追踪表"（RequestRecord）——键是 request_id，值是 ProtocolState。当一个请求发出后但还没收到回复时，它的记录就在这里。回复到来时通过 request_id 查到这个记录，更新状态。

相当于一个"在途请求登记簿"。

3.3 new_request_id 生成器

def new_request_id() -> str:
    return f"req_{random.randint(0, 999999):06d}"
片段解释
f"..."f-string，花括号内写表达式
random.randint(0, 999999)0~999999 的随机整数（100 万种可能）
:06d格式化：至少 6 位十进制，不足补零。42 → 000042

4 match_response 核心函数

职责：Lead 收到 Teammate 的响应消息时，用来将响应关联到原始请求。

def match_response(response_type: str, request_id: str, approve: bool):
    state = pending_requests.get(request_id)
    if not state:                                        # 找不到记录
        print(f"  \033[31m[protocol] unknown request_id: {request_id}\033[0m")
        return

    # 验证响应类型与请求类型匹配
    if state.type == "shutdown" and response_type != "shutdown_response":
        print(f"...type mismatch..."); return
    if state.type == "plan_approval" and response_type != "plan_approval_response":
        print(f"...type mismatch..."); return

    if state.status != "pending":                          # 重复响应防御
        print(f"  \033[33m[protocol] ...already {state.status}...\033[0m")
        return

    state.status = "approved" if approve else "rejected"  # 更新状态
    print(f"  \033[{color}m[protocol] {state.type} {icon} ...\033[0m")

逐块拆解

步骤代码做了什么
1pending_requests.get(request_id)用 request_id 查找登记簿。用 get 不抛异常，找不到返回 None
2if not state: return找不到记录 → 打印红色错误，拒绝处理
3类型匹配检查如果请求是 shutdown，响应必须是 shutdown_response；plan_approval 同理
4status != "pending"防止重复处理：如果请求已经被批准/拒绝了，第二次响应是多余的
5state.status = "approved"/"rejected"更新状态表中的记录
6打印日志绿色 ✓ = 批准，红色 ✗ = 拒绝
ANSI 颜色码：\033[31m 红色（错误），\033[33m 黄色（警告），\033[32m 绿色（成功），\033[0m 重置。

5 consume_lead_inbox 统一收件入口

设计意图（s16 fix）：在此之前，run_check_inbox 工具和主循环各自由地读 inbox，导致协议响应消息被当成普通消息消费了，但没有经过 match_response 处理——请求就一直停留在 pending 状态，永远得不到更新。 
def consume_lead_inbox(route_protocol: bool = True) -> list[dict]:
    msgs = BUS.read_inbox("lead")
    if not msgs:
        return []
    if route_protocol:                              # 开关参数
        for msg in msgs:
            meta = msg.get("metadata", {})            # 取元数据
            req_id = meta.get("request_id", "")      # 取 request_id
            msg_type = msg.get("type", "")            # 取消息类型
            if req_id and msg_type.endswith("_response"):  # 判断是否协议响应
                approve = meta.get("approve", False)    # 默认拒绝（安全设计）
                match_response(msg_type, req_id, approve)  # 关联到原始请求
    return msgs

关键细节

代码解释
msg.get("metadata", {})从消息中取 metadata 字典。用 get 防旧消息没有 metadata 字段
msg_type.endswith("_response")只处理响应消息，不处理请求消息（请求由普通注入处理）
approve = meta.get("approve", False)默认为 False——如果没传 approve，默认拒绝。这是"default deny"安全原则
match_response(msg_type, req_id, approve)调用核心匹配函数更新 pending_requests

被谁调用

  • run_check_inbox 工具——当 Lead LLM 主动调用 check_inbox 时
  • 主循环末尾——每次用户输入一轮对话后，自动检查 inbox 并注入
关键：无论是哪种调用路径，协议响应都会被正确路由到 match_response。这是 s16 解决的一个真实 bug，也是 s15 中存在的隐患。

7 handle_inbox_message 协议分发

内嵌函数定义在 spawn_teammate_thread 内部。当 Teammate 的收件箱有协议消息时，由它来分派处理。

def handle_inbox_message(name: str, msg: dict, messages: list) -> bool:
    msg_type = msg.get("type", "message")
    meta = msg.get("metadata", {})
    req_id = meta.get("request_id", "")

    if msg_type == "shutdown_request":                          # 关闭请求
        BUS.send(name, "lead", "Shutting down gracefully.",
                 "shutdown_response",
                 {"request_id": req_id, "approve": True})
        return True   # → 触发 break，退出循环

    if msg_type == "plan_approval_response":                     # 方案审批回复
        approve = meta.get("approve", False)
        if approve:
            messages.append({"role": "user",
                    "content": "[Plan approved] Proceed with the task."})
        else:
            messages.append({"role": "user",
                    "content": "[Plan rejected] Feedback: {msg['content']}"})
        return False  # 🐛 不触发 break（见 Bug 章节）

两种协议消息的处理对比

shutdown_requestplan_approval_response
返回值TrueFalse
对循环的影响触发 break，退出 inner while → 退出 outer while → summary不触发 break，继续 inner while 轮询
对 messages 的影响无注入 [Plan approved/rejected]
对 Lead 的回复自动发 shutdown_response无回复（已收到 response 了）

8 外层循环 vs 内层循环（核心难点）

这是整个 s16 中最容易搞混的部分，也是被问得最多的问题。

8.1 两个循环的分工

循环什么时候运行干什么费用类比
外层循环 (outer while)始终运行（直到 shutdown）完整的"想→做"轮次：读消息 → 调用 LLM → 执行工具 → 再读消息...调用 LLM（花钱）上班时间：接活 → 想 → 干 → 再接活
内层循环 (idle while)仅在 LLM 说完了没事做时（end_turn）零成本等待：sleep(1) → 读 inbox → 空就继续等0 元（不调 LLM）午休：没活干，趴着等，有活了再开工

8.2 为什么要有内层循环（不直接回到外层顶部）？

假设没有内层循环，LLM 返回 end_turn 后直接回到外层顶部：

shutdown_requested = False
while not shutdown_requested:
    读 inbox → 空
    调用 LLM → LLM 看到和之前一样的消息 → 返回一样的 "Done"
    执行工具 → 空操作
  → 回到 while 顶部
    读 inbox → 还是空
    调用 LLM → 又调一次！烧钱！
    执行工具 → 空操作
  → 回到 while 顶部
    读 inbox → 还是空
    调用 LLM → 又调一次！！无限烧钱！！！
内层循环的本质就是"零成本等待"阶段。没有新消息时绝不再调 LLM。用 sleep(1) 代替 API 调用，0 费用。只有确认有新消息进来了，才 break 出去让外层重新调 LLM。

8.3 内层循环的"怎么轮询"——关键在 continue 而不是 break

while not shutdown_requested:           # 内层循环
    time.sleep(1)                       # 睡 1 秒
    inbox = BUS.read_inbox(name)         # 读收件箱
    if not inbox:
        continue                           # 空 → 回到 while 顶部，继续 sleep→read→sleep→read
    # 有消息 → 处理...

continue 让流程回到 while 顶部，不退出 while。所以只要一直没消息，它就一直在 sleep(1) → read_inbox → 空 → continue → sleep(1) → ... 这个循环里打转。这就是轮询。

8.4 内层循环的三个出口

8.5 内联 for 循环中的 break

for msg in inbox:
    if 协议消息:
        should_stop = handle_inbox_message(...)
        if should_stop:
            break                              # 只跳出 for，不跳出 inner while
    else:
        non_protocol.append(msg)
if shutdown_requested:
    break                                  # 跳出 inner while
if non_protocol:
    ...注入对话...
    break                                  # 跳出 inner while

这里有两层 break：

  • 内层 break（在 for 内部）：只跳出 for 循环——因为已经收到了 shutdown_request，不需要继续遍历剩余的 inbox 消息了
  • 外层 break（在 for 外部）：跳出 inner while——无论是 shutdown 还是收到普通消息，都要退出空闲等待状态

9 完整执行流程举例

假设 Teammate "Alice" 被创建，经历了一个完整的生命周期：

场景：创建 → 干活 → 等待 → 新任务 → 关闭

第1轮 外层循环: 读 inbox → 空（初始任务在 messages 参数中） 调用 LLM → LLM 返回 tool_use（要创建 a.py） stop_reason == "tool_use" → 跳过内层循环 执行工具 → run_bash 创建文件 回到外层顶部 第2轮 外层循环: 读 inbox → 空 调用 LLM → LLM 返回 "Done"（end_turn） stop_reason != "tool_use" → 进入内层循环！ ↓ 内层循环: sleep(1) → 读 inbox → 空 → continue sleep(1) → 读 inbox → 空 → continue sleep(1) → 读 inbox → Lead 发来 "请修改 b.py" 普通消息 → non_protocol → 注入对话 break 出内层循环 ↓ （空工具执行段 → 回到外层顶部） 第3轮 外层循环: 读 inbox → 空（内层已取走） 调用 LLM → LLM 看到新任务，调用 bash 修改 b.py tool_use → 执行工具 → 回到外层顶部 第4轮 外层循环: 读 inbox → 空 调用 LLM → "Done"（end_turn） 进入内层循环: sleep(1) → 读 inbox → 空 → continue ... → Lead 发来 shutdown_request → handle_inbox_message 处理 → 自动发 shutdown_response 给 Lead → should_stop=True → shutdown_requested=True → break for → break inner while ↓ （空工具执行段） outer while 条件 False → 退出外层循环 ↓ 发 summary 给 Lead active_teammates.pop("alice") 线程结束

停止循环的路径

出口触发条件跳出什么跳出后到哪里
break (L532)收到 shutdown_request → shutdown_requested=True跳出 inner while空工具执行段 → outer while 条件 False → summary
break (L537)收到普通消息 → non_protocol 不为空 → 注入对话跳出 inner while空工具执行段 → outer while 顶部 → 下一轮调 LLM 处理新消息
continue (L522)inbox 为空回到 inner while 顶部继续轮询（不退出）
路径触发条件如何到 summary
路径1外层循环开头收到 shutdown_requestshould_stop=True → outer while break → summary
路径2LLM 调用抛异常except: break → summary
路径3内层循环中收到 shutdown_requestshutdown_requested=True → break inner → 外层条件 False → summary
注意：如果没有以上三个条件中的任何一个，Teammate 线程永不会走到 summary，会一直在内层循环中轮询等待。这是设计意图——后台 worker 永远在线。

10.2 Lead 发起关机

def run_request_shutdown(teammate: str) -> str:
    req_id = new_request_id()
    pending_requests[req_id] = ProtocolState(           # 登记
        request_id=req_id, type="shutdown",
        sender="lead", target=teammate,
        status="pending", payload="")
    BUS.send("lead", teammate, "Please shut down gracefully.",  # 发送
             "shutdown_request",
             {"request_id": req_id})

10.3 Teammate 提交方案

def _teammate_submit_plan(from_name: str, plan: str) -> str:
    req_id = new_request_id()
    pending_requests[req_id] = ProtocolState(           # 登记
        request_id=req_id, type="plan_approval",
        sender=from_name, target="lead",
        status="pending", payload=plan)
    BUS.send(from_name, "lead", plan,                  # 发送
             "plan_approval_request",
             {"request_id": req_id})
    return f"Plan submitted ({req_id}). Waiting for approval..."

10.4 Lead 要求提交方案（不走协议）

def run_request_plan(teammate: str, task: str) -> str:
    BUS.send("lead", teammate, f"Please submit a plan for: {task}",
             "message")                                    # 普通消息！
    return f"Asked {teammate} to submit a plan"

注意：这个函数发的不是协议消息（msg_type 是 "message" 而不是 "plan_approval_request"）。它只是提醒 Teammate 要交方案，Teammate 的 LLM 看到后自己调用 submit_plan 工具来发起协议。

10.5 Lead 审批方案

def run_review_plan(request_id: str, approve: bool, feedback: str = "") -> str:
    state = pending_requests.get(request_id)
    if not state: return "not found"                  # 找不到记录
    if state.status != "pending":                     # 防重复审批
        return f"Request already {state.status}"
    state.status = "approved" if approve else "rejected"  # 更新状态
    BUS.send("lead", state.sender,                      # 发响应
             feedback or ("Approved" if approve else "Rejected"),
             "plan_approval_response",
             {"request_id": request_id, "approve": approve})

10.6 完整通信链路

关机协议: Lead: run_request_shutdown("alice") → 登记 pending_requests → BUS.send(shutdown_request, {request_id}) ───────────────────────────────→ alice.jsonl alice 内层循环读到 → handle_inbox_message → BUS.send(shutdown_response, {approve:True}) ←─────────────────────────────── lead.jsonl Lead: consume_lead_inbox() → match_response() → status = "approved" 方案审批协议: Teammate: _teammate_submit_plan("alice", "步骤1...") → 登记 pending_requests → BUS.send(plan_approval_request, {request_id}) ───────────────────────────────→ lead.jsonl Lead: consume_lead_inbox() → 不调 match_response（不是 _response） → 注入对话 → Lead LLM 看到方案 → 调用 review_plan → run_review_plan(request_id, approve=True) → BUS.send(plan_approval_response, {request_id, approve}) ←─────────────────────────────── alice.jsonl Teammate: 内层循环读到 plan_approval_response → handle_inbox_message → 注入 [Plan approved] → 返回 False（不 break） 🐛

12 已知 Bug

Bug 1：plan_approval_response 不触发 break（源码自带）

位置：handle_inbox_message 中的 plan_approval_response 分支返回 False（L449）

问题：Teammate 提交方案后，Lead 批准了，发回 plan_approval_response。Teammate 端收到后，注入 [Plan approved] 到 messages，但因为没有触发 break 出内层循环，LLM 永远不会被再次调用，方案永远不会被执行。

现象：

内层循环:
  sleep(1) → 读 inbox → 收到 plan_approval_response
  → handle_inbox_message 注入 [Plan approved] 到 messages
  → 返回 False → should_stop=False → 不 break for
  → plan_approval_response 不进 else → non_protocol 为空
  → if shutdown_requested: False
  → if non_protocol: False（空的）
  → 回到内层循环顶部
  sleep(1) → 读 inbox → 空（已经读走了）
  continue → 继续轮询
  sleep(1) → 读 inbox → 空
  continue → 继续轮询
  ...无限等待...

修复方案：把返回 True 即可：

if msg_type == "plan_approval_response":
    ...
    return True   # 触发 break 出内层，让外层调 LLM 执行方案

变通方案：如果不改代码，Lead 再发一条普通消息就能触发 LLM 执行。[Plan approved] 会和新消息一起被 LLM 看到。

Bug 2：内层循环中 non_protocol 变量复用（潜藏）

位置：内层循环（L531-538）使用的 non_protocol 来自外层循环开头定义的同一个列表（L492），内层没有重新初始化。

问题：如果某次外层循环中 non_protocol 收集了消息但还没注入（条件不满足时），进入内层循环后又收到新消息，会追加到同一个列表，可能导致消息重复注入或内容混淆。

实际影响有限：每次外层循环开头都会 non_protocol = []，且内层循环结束后会回到外层顶部。但极端时序下可能出现问题。

Bug 3：TOOLS 残留 cron 工具定义（你的代码可能缺失协议工具）

如果你的代码是直接从 s15 复制而来：TOOLS 列表里可能还保留着 schedule_cron / list_crons / cancel_cron，但缺少了三个协议工具（request_shutdown / request_plan / review_plan）。

后果：Lead 的 LLM 不知道有这三个工具，协议功能完全不可用。

Bug 4：run_check_inbox 未使用 consume_lead_inbox（你的代码独有）

如果你的 run_check_inbox 直接用 BUS.read_inbox：消息被读走但没有经过 match_response，协议状态永远停留在 pending。

修复：改为 msgs = consume_lead_inbox(route_protocol=True)

13 常见困惑与 FAQ

Q1：metadata 是什么？

metadata 是 BUS.send 方法的第五个参数（可选字典），用于在消息本体之外附带协议相关的元信息（如 request_id 和 approve）。

可以把消息体比作信的内容（content），metadata 就是信封上的附注信息。

在 BUS.send 内部，metadata 被存入消息的 "metadata" 字段：

msg = {"from": ..., "content": ..., "metadata": metadata or {}}

Q2：msg['content'] 怎么确保就是 Lead 的反馈意见？

因为有且只有一个函数发送 plan_approval_response——run_review_plan，它把 feedback 参数放到了 content 字段里：

BUS.send("lead", state.sender, feedback or ("Approved" if approve else "Rejected"),
         "plan_approval_response", ...)

这是协议约定而非运行时保证——如果未来有另一段代码发送同样 type 但 content 含义不同的消息，这里就会出问题。

Q3：外层循环开头读 inbox 不是多余的吗？第一次肯定是空的。

第一次确实是空的，但后续每次都不是。代码没有区分"第一次"还是"第N次"。第一次浪费了，但后续每一次都很重要——在 LLM 思考和执行工具期间，Lead 可能已经通过 BUS 发来新消息了。

Q4：外层循环负责什么？内层循环负责什么？

外层循环内层循环
地位主工作循环空闲等待循环
触发时机一直运行（shutdown 前）仅在 LLM 返回 end_turn 时
做的事读消息 → 调 LLM → 执行工具 → 再读sleep → 读 inbox → 有消息就处理 → 没有继续等
类比上班接活干活午休趴着等

Q5：为什么不执行工具时要进内层循环（而不是回到外层顶部直接调 LLM）？

因为每次调 LLM 都花钱。如果 LLM 返回 end_turn 后直接回到外层顶部，而没有新消息，LLM 又看不到新消息，就会无限空转调用 LLM 烧钱。内层循环用 sleep(1) 代替 API 调用，0 费用。

Q6：stop_reason 不同时，代码执行路径是怎样的？

stop_reason = "tool_use"（LLM 要调用工具）
  → if stop_reason != "tool_use": False
  → 跳过 if 块（跳过内层循环）
  → 直接执行工具 → 回到外层顶部

stop_reason = "end_turn"（LLM 说完了）
  → if stop_reason != "tool_use": True
  → 进入内层循环等待
  → 等到有新消息或 shutdown
  → break 出内层 → 空工具执行段 → 回到外层顶部

Q7：初始任务不在 inbox 里，那第一次外层循环的读 inbox 不是空的？

是的，第一次确实是空的。但整个代码没有做"首次特殊处理"，设计上认为这点开销可以忽略。从第二次开始，每次读 inbox 都可能拿到新的消息。

Q8：metadata 参数的 approve 字段默认值为什么是 False？

approve = meta.get("approve", False) 中默认 False 是"default deny"安全原则——如果元数据里没有 approve 字段，默认是拒绝，而不是批准。

Q9：plan_approval_response 和 shutdown_request 在处理上有什么根本不同？

shutdown_requestplan_approval_response
handle_inbox_message 返回TrueFalse
是否触发 break for是否
是否触发 break 内层是（两层 break）否（继续轮询）
后续行为退出发 summary继续等，下次调 LLM 才看到结果

Q10：那 Lead 一直不发普通消息，Teammate 就卡住了？之前的 plan 也一直不执行？

对，这就是 bug 1（plan_approval_response 不触发 break）导致的后果。

[Plan approved] 已经躺在 messages 里了，但因为没有任何东西触发 break 出内层循环，LLM 永远不会被再次调用，方案永远不会被执行。

Q11：tool_use 时怎么执行的工具？代码哪里体现了？

关键在 if response.stop_reason != "tool_use": 这个条件判断——当 stop_reason 是 "tool_use" 时，条件为 False，整个内层循环块被跳过，执行流直接落到"执行工具"段：

results = []
for block in response.content:        # 遍历 LLM 回复中的每个块
    if block.type == "tool_use":       # 找到工具调用块
        handler = sub_handlers.get(block.name)  # 查表找处理函数
        output = handler(**block.input)         # 解包参数并执行
        results.append({...})
messages.append({"role": "user", "content": results})  # 结果送回 LLM

没有显式的 else——用的是"条件不成立就跳过"的方式。
