1 章节概述：为什么需要后台任务？

核心动机

前面几章（s00-s12）里，工具调用都是同步的：

模型发起 → 立刻执行 → 立刻返回结果

这对短命令没问题。但遇到 npm install、pytest、docker build 这些慢操作时，整个程序会被卡住——模型在等待期间什么都做不了，用户想继续别的工作也被堵住。

s13 要解决的问题

把"慢执行"移到后台，让主循环继续推进别的事情。

三个核心概念

概念含义代码对应
前台（同步）主循环发起后，必须立刻等结果的执行路径execute_tool(block) — 等返回
后台（异步）命令在另一条线程上跑，主循环不等，先干别的start_background_task(block) → 1ms 返回 bg_id
通知队列后台任务完成后，不直接把全文塞给模型，先写一条摘要，等下一轮再带回collect_background_results() → <task_notification>
记住最关键的句子：主循环仍然只有一条，并行的是等待，不是主循环本身。

2 最小心智模型

结构图

主循环（只有一条） │ ├─ background_run("pytest") │ → 立刻返回 task_id │ ├─ 继续处理其他工具调用 │ ├─ 下一轮调模型前 │ → collect_background_results() │ → 把摘要通知注入 messages │ └─ 调模型 后台执行线（另一条线程） │ ├─ 真正执行 pytest（可能跑几分钟） └─ 完成后写通知到队列

s13 和 s12 任务系统的边界

s12 的 tasks13 的 background task
本质工作目标正在运行的执行单元
关心要做什么、谁依赖谁、进度哪个命令在跑、状态、结果
存储磁盘（.tasks/*.json）内存（两个字典，仅当前会话有效）
类似工作看板运行中的作业
初学者最容易犯的错：
  1. 以为"后台"就是更复杂的主循环——不是，主循环始终只有一条。
  2. 只开线程，不登记状态——任务一多就不知道谁还在跑。
  3. 把长日志全文塞进上下文——上下文很快被撑爆。
  4. 把 s12 的工作目标和 s13 的运行任务混为一谈。

逐变量解释

变量类型作用谁写谁读/删
_bg_counterint自增计数器，生成唯一任务 IDstart_background_task—
background_tasksdict[str, dict]存所有后台任务的元信息（命令、状态、ID）主线程（写 running）
worker 线程（改 completed）		collect_background_results（pop）
background_resultsdict[str, str]存后台任务的执行结果worker 线程collect_background_results（pop）
background_lockthreading.Lock互斥锁，保证多线程读写字典安全所有需要读写字典的地方所有需要读写字典的地方

关键理解：为什么这两件事要分开？

两个字典分工明确：

  • background_tasks 存的是"生命周期状态"——任务在跑还是跑完了
  • background_results 存的是"执行产物"——命令的输出文本

分开的好处：collect_background_results 可以分别 pop，一个任务取完了两个字典都清干净，不会残留脏数据。

为什么需要锁？主线程和 worker 线程可能同时读写这两个字典。不加锁会出现"线程 A 读到写了一半的数据"等问题（竞态条件）。with lock: 保证同一时间只有一个线程能操作受保护的代码块。

4 is_slow_operation：启发式判断慢命令

代码位置：L293-300

def is_slow_operation(tool_name: str, tool_input: dict) -> bool:
    """Fallback heuristic: commands likely to take > 30s."""
    if tool_name != "bash":
        return False
    cmd = tool_input.get("command", "").lower()
    slow_keywords = ["install", "build", "test", "deploy", "compile",
                     "docker build", "pip install", "npm install",
                     "cargo build", "pytest", "make"]
    return any(kw in cmd for kw in slow_keywords)

逐行详解

  • L295-296：只对 bash 工具做判断。其他工具（读文件、写文件）通常不会慢，直接返回 False。
  • L297：从 tool_input 字典里取出 "command" 键的值，取不到就用空字符串 ""，然后统一转小写以便匹配。
  • L298-299：定义了慢命令关键词列表。

any(kw in cmd for kw in slow_keywords) 拆解

这是整个函数最核心的一行。拆开看：

# 原写法（一行）：
return any(kw in cmd for kw in slow_keywords)

# 等价的 for 循环写法：
for kw in slow_keywords:
    if kw in cmd:   # 检查关键词是否作为"子串"出现在命令中
        return True
return False

比如 cmd = "sudo apt install nginx"，"install" in cmd 是 True，所以函数返回 True。

5 should_run_background：决策路由

代码位置：L302-306

def should_run_background(tool_name: str, tool_input: dict) -> bool:
    """Model explicit request takes priority; fallback to heuristic."""
    if tool_input.get("run_in_background"):
        return True
    return is_slow_operation(tool_name, tool_input)

两条路径

  • 显式请求（优先级高）：模型在 tool_input 里传了 run_in_background: true，直接后台执行。
  • 启发式兜底（优先级低）：模型没明确说，但命令看起来像慢操作（含 install、build 等关键词），也放到后台。
should_run_background() │ tool_input 里有 run_in_background? │ ┌────┴────┐ YES NO │ │ │ is_slow_operation() │ │ │ ┌────┴────┐ │ YES NO │ │ │ └──┬──┘ │ │ │ 后台执行 前台同步

6 execute_tool：统一执行入口

代码位置：L308-312

def execute_tool(block) -> str:
    """Execute a tool call block, return output."""
    handler = TOOL_HANDLERS.get(block.name)
    if handler:
        return handler(**block.input)
    return f"Unknown: {block.name}"

为什么需要这个函数？

s12 里工具执行逻辑直接写在 agent_loop 的循环里。s13 里有两种场景都需要"执行工具"：

  • 同步执行：主循环直接调 execute_tool(block)，等结果
  • 后台执行：worker 线程里调 execute_tool(block)，不等

提取成独立函数避免重复代码。

handler(**block.input) 是什么意思？

**dict 是 Python 的字典解包语法，把字典展开成关键字参数：

# 假设 block.input = {"command": "ls -la"}
handler(**block.input)
# 等效于：
handler(command="ls -la")

7 start_background_task：启动后台任务

代码位置：L318-341

def start_background_task(block) -> str:
    """Run tool in a daemon thread. Returns background task ID."""
    global _bg_counter
    _bg_counter += 1
    bg_id = f"bg_{_bg_counter:04d}"
    cmd = block.input.get("command", block.name)

    def worker():                                    # ⚠️ 这里只是定义，不执行
        result = execute_tool(block)                    # 真正耗时的地方
        with background_lock:
            background_tasks[bg_id]["status"] = "completed"
            background_results[bg_id] = result

    with background_lock:                             # ⬅ 先注册为 running
        background_tasks[bg_id] = {
            "tool_use_id": block.id,
            "command": cmd,
            "status": "running"
        }

    thread = threading.Thread(target=worker, daemon=True)
    thread.start()                                      # ⬅ 到这行 worker 才开始执行
    print(f"  \033[33m[background] dispatched {bg_id}: {cmd[:40]}\033[0m")
    return bg_id

执行顺序（这是最容易搞混的部分）

def worker() 只是"定义"一个函数，里面的代码不会立即执行。真实顺序是：

行号 代码 谁在跑 什么时候 ──── ──── ───── ────────── L321 def worker(): 主线程 立即（只定义，不执行） L322-324 execute_tool / 加锁 — 还没执行！ L326-330 注册任务为 running 主线程 def 之后立即执行 L332 Thread(target=worker) 主线程 立即创建线程对象 L333 thread.start() 主线程 创建新线程 L334 print(...) 主线程 start 后立即 L335 return bg_id 主线程 立即返回 ↓ 新线程启动后： L322 execute_tool(block) 后台线程 start() 后在后台跑 L323-324 with lock / 改状态 后台线程 execute_tool 返回后

关键理解：这个函数很快返回是故意的

start_background_task 本身只做"安排任务"的事（注册状态 + 启动线程），大约耗时 1ms。真正的耗时操作在 worker 线程里，跟这个函数没关系。

注意：先注册为 "running"，再 thread.start()。等 worker 执行完 execute_tool 后，再把状态改为 "completed"。collect_background_results 通过检查状态变化来发现"哪个任务完成了"。

8 threading.Thread 详解

最基础用法

import threading

def say_hello():
    print("我在新线程里！")

t = threading.Thread(target=say_hello)   # 告诉线程：去执行 say_hello 函数
t.start()                                 # 创建新线程，开始运行
                                          # 主线程不等，继续往下走

target 的三种写法

写法示例适用场景
传已有函数名Thread(target=my_func)函数已定义好
传 lambdaThread(target=lambda: print("hi"))逻辑简单，一行搞定
传内部函数（闭包）def outer():
  x = 10
  def inner():
    print(x)
  Thread(target=inner)		你的代码用的方式——可以访问外部函数里的局部变量

带括号和不带括号的关键区别

# ✅ 正确：传函数本身
t = threading.Thread(target=worker)     # worker 是函数对象
t.start()                               # 新线程去执行 worker()

# ❌ 错误：传函数的返回值
t = threading.Thread(target=worker())   # 先执行了 worker()，把返回值传给 target
t.start()                               # 新线程试图执行返回值（字符串），报错

区分方法：worker = 菜谱（函数本身），worker() = 做出来的菜（调用结果）。

闭包（Closure）

你的代码里的 worker 定义在 start_background_task 内部，可以访问外部的 block 和 bg_id：

def start_background_task(block):
    bg_id = ...
    cmd = ...

    def worker():
        result = execute_tool(block)        # 访问了外部的 block
        background_tasks[bg_id][...] = ...   # 访问了外部的 bg_id

    thread = threading.Thread(target=worker)
    thread.start()

这省去了用 args 传参的麻烦。worker 自然"记住"了它定义时外面的变量值。

9 daemon=True 到底在干什么？

普通线程 vs 守护线程

# 普通线程（daemon=False，默认值）
t = threading.Thread(target=worker)
t.start()
# 即使主线程执行完了，也会等待 worker 执行完才退出程序

# 守护线程（daemon=True）
t = threading.Thread(target=worker, daemon=True)
t.start()
# 主线程执行完了，不管 worker 有没有跑完，程序直接退出
# worker 被强制终止

在 s13 中 daemon=True 保护什么？

保护的是：用户主动退出程序时，不需要等没跑完的后台任务。

场景：用户启动了 "npm install"（要跑 2 分钟），又不想等了： 第 10 秒：用户输入 q → 主循环 break，程序准备退出 如果没有 daemon=True： → Python 检查：还有后台线程在跑 → 等它跑完！（等 110 秒） → 用户按了 q，但程序卡住不动了 有 daemon=True： → 主线程退出 → 后台线程被强制终止 → 程序立即退出
但正常情况 worker 不会被杀死！因为程序在 while True 循环里一直运行，除非用户输入 q 退出，否则后台线程有充足的时间跑完。daemon=True 只在用户明确退出时生效。

10 collect_background_results：收作业

代码位置：L343-363

def collect_background_results() -> list[str]:
    """Collect completed background results as task_notification messages."""
    with background_lock:
        ready_ids = [bid for bid, task in background_tasks.items()
                     if task["status"] == "completed"]
    notifications = []
    for bg_id in ready_ids:
        with background_lock:
            task = background_tasks.pop(bg_id)
            output = background_results.pop(bg_id, "")
        summary = output[:200] if len(output) > 200 else output
        notifications.append(
            f"<task_notification>\n"
            f"  <task_id>{bg_id}</task_id>\n"
            f"  <status>completed</status>\n"
            f"  <command>{task['command']}</command>\n"
            f"  <summary>{summary}</summary>\n"
            f"</task_notification>"
        )
        print(f"  \033[32m[background done] {bg_id}: "
              f"{task['command'][:40]} ({len(output)} chars)\033[0m")
    return notifications

三步流程

步骤 1：找出已完成的任务（L344-346）

ready_ids = [bid for bid, task in background_tasks.items()
             if task["status"] == "completed"]
  • 遍历 background_tasks 字典，找到所有状态为 "completed" 的任务 ID
  • 注意这里先只拿 ID，不放锁后才逐个处理——尽量减少锁的持有时间

步骤 2：取出并删除（L349-351）

with background_lock:
    task = background_tasks.pop(bg_id)          # pop = 取出 + 删除
    output = background_results.pop(bg_id, "")
  • pop(key)：从字典中取出 key 对应的值，同时删除这个 key
  • pop(key, default)：如果 key 不存在，返回 default 而不是抛异常
  • 用 pop 而非 get 的好处：取完即删，下次再调这个函数就不会重复处理同一个任务

步骤 3：截断 + 格式化 + 返回（L352-363）

summary = output[:200] if len(output) > 200 else output
  • 输出只取前 200 个字符作为摘要，防止上下文被撑爆
  • 格式化为 XML 风格的通知字符串，方便 AI 模型解析

生成的通知消息示例：

<task_notification>
  <task_id>bg_0001</task_id>
  <status>completed</status>
  <command>pip install torch</command>
  <summary>Collecting torch... Successfully installed torch-2.0.0</summary>
</task_notification>

完整执行示例

调用前： background_tasks = { "bg_0001": {..., "status": "completed"}, "bg_0002": {..., "status": "running"}, ← 还在跑，跳过 "bg_0003": {..., "status": "completed"}, } collect_background_results() 执行后： background_tasks = { "bg_0002": {..., "status": "running"}, ← 没完成的还在 } 返回： ["<task_notification>...bg_0001...</task_notification>", "<task_notification>...bg_0003...</task_notification>"]

12 with 锁的用法详解

为什么需要锁？

多个线程同时读写同一个字典可能出问题：

# 场景：线程 A 在读，线程 B 同时在写
# 线程A: if task["status"] == "completed"   ← 读到一半的数据？
# 线程B: task["status"] = "completed"        ← 写了一半

with lock 的等价展开

# 写法 A（实际代码）：
with background_lock:
    background_tasks[bg_id]["status"] = "completed"
    background_results[bg_id] = result

# 写法 B（等价的）
background_lock.acquire()            # 上锁——如果锁被人拿着，会阻塞等待
try:
    background_tasks[bg_id]["status"] = "completed"
    background_results[bg_id] = result
finally:
    background_lock.release()         # 解锁——一定要在 finally 里保证释放

with 的好处

  • 自动调用 acquire() 和 release()
  • 即使代码抛出异常，锁也会自动释放（不会死锁）
  • 代码更简洁

with 只保护块内的代码

def worker():
    result = execute_tool(block)              # ← 没有锁保护！执行 60 秒都没人管
    with background_lock:                     # ← 只有这里被保护
        background_tasks[bg_id]["status"] = "completed"   # 这几行只需要几微秒
        background_results[bg_id] = result

只有真正操作共享字典的地方才加锁，尽量减少锁的持有时间。这样其他线程不会被长时间阻塞。
