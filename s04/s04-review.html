1 AgentTemplate._parse — Frontmatter 解析

📍 代码位置

s04_subagent.py#L76-87

📍 作用

解析 Markdown 文件中的 frontmatter（前置元数据），把元数据和正文分离开。

一句话：_parse 解析 --- 包裹的简易 YAML 头，把元数据和正文拆成两个部分分别存储。 
def _parse(self):
    text = self.path.read_text()                       # ① 读取整个 .md 文件
    match = re.match(r"^---\s*\n(.*?)\n---\s*\n(.*)",      # ② 正则提取 frontmatter
                     text, re.DOTALL)
    if not match:                                    # ③ 没有 frontmatter → 整个文件即正文
        self.system_prompt = text
        return
    for line in match.group(1).splitlines():      # ④ 逐行解析元数据
        if ":" in line:
            k, _, v = line.partition(":")         # 按 : 切 key/value
            self.config[k.strip()] = v.strip()
    self.system_prompt = match.group(2).strip()  # ⑤ 正文 = system prompt
    self.name = self.config.get("name", self.name) # ⑥ frontmatter 有 name 就覆盖

📍 正则详解

r"^---\s*\n(.*?)\n---\s*\n(.*)" │ │ │ │ │ └── group(2)：正文（贪婪匹配到结尾） │ └── group(1)：元数据（非贪婪，遇 \n--- 就停） └── 以 "---" 开头（可含空白） re.DOTALL ← 让 . 匹配换行符

📍 具体例子

假设文件 researcher.md 内容：
---
name: researcher
tools: bash, read, glob
---
You are a researcher agent.
Your task is to explore the codebase.

解析后：
  self.config = {"name": "researcher", "tools": "bash, read, glob"}
  self.name   = "researcher"           ← 来自 frontmatter 覆盖
  self.system_prompt = "You are a researcher agent.\nYour task is..."
注意：在这个文件中 AgentTemplate 只是教学展示，并未被实际使用。 父子 agent 的 system prompt 都是硬编码的常量 SYSTEM 和 SUBAGENT_SYSTEM。

2 run_subagent — 子 agent 执行循环

📍 代码位置

s04_subagent.py#L157-173
核心：子 agent 的价值不是"多一个模型实例"，而是"多一个干净上下文"。 
def run_subagent(prompt: str) -> str:
    sub_messages = [{"role": "user", "content": prompt}]  # ① 全新上下文
    for _ in range(30):                                     # ② 最多 30 轮
        response = client.messages.create(
            model=MODEL, system=SUBAGENT_SYSTEM, messages=sub_messages,
            tools=CHILD_TOOLS, max_tokens=8000
        )
        sub_messages.append({"role": "assistant", "content": response.content})  # ③
        if response.stop_reason != "tool_use":               # ④ 无工具调用 → 结束
            break
        results = []
        for block in response.content:                      # ⑤ 执行工具
            if block.type == "tool_use":
                handler = TOOL_HANDLERS.get(block.name)
                output = handler(**block.input) if handler else ...
                results.append({"type": "tool_result", ...})
        sub_messages.append({"role": "user", "content": results})  # ⑥ 结果喂回
    return "".join(b.text for b in response.content if hasattr(b, "text")) # ⑦ 摘要返回

📍 逐段拆解

步骤代码作用
①sub_messages = [{...prompt...}]上下文隔离的关键——子 agent 从空消息列表开始
②for _ in range(30)防止模型无限调用工具
③sub_messages.append({...response...})把模型回复追加到对话历史
④stop_reason != "tool_use"模型只输出 text 没调工具 → 任务完成
⑤for block in response.content遍历 tool_use 块，通过 TOOL_HANDLERS 找到函数并执行
⑥sub_messages.append({..."tool_result"...})工具结果喂回，让模型继续推理
⑦return "".join(b.text ...)只返回文本摘要，不返回中间工具调用细节

📍 标准 tool-use 循环示意

响应 响应 ┌───────────────┐ ┌───────────────┐ │ 模型输出 text │ │ 模型输出 text │ │ + │ │ + │ │ tool_use 块 │ │ tool_use 块 │ └───────┬───────┘ └───────┬───────┘ ↓ ↓ 执行工具代码 执行工具代码 (bash/read...) (bash/read...) ↓ ↓ 结果塞回 messages 结果塞回 messages ↓ ↓ 继续循环 stop_reason != "tool_use" → 跳出

📍 5 个关键设计要点

设计代码体现目的
上下文隔离sub_messages = [{"role": "user", "content": prompt}]子 agent 不继承父 agent 的对话历史
工具隔离CHILD_TOOLS 只有 4 个，没有 task防止子 agent 无限递归派生
信息压缩return "".join(b.text ...)只返回摘要，不返回中间细节
单向通信子 agent 只返回字符串父子之间没有双向对话
安全防护for _ in range(30)防止子 agent 无限循环

3 handler(**block.input) — 函数是一等公民

📍 代码位置

s04_subagent.py#L134-138 (TOOL_HANDLERS)
s04_subagent.py#L171     (使用处)

📍 核心原理

Python 中函数是一等公民——可以像普通值一样放入字典、赋值给变量。

TOOL_HANDLERS = {
    "bash":       lambda **kw: run_bash(kw["command"]),
    "read_file":  lambda **kw: run_read(kw["path"], kw.get("limit")),
    "write_file": lambda **kw: run_write(kw["path"], kw["content"]),
    "edit_file":  lambda **kw: run_edit(kw["path"], kw["old_text"], kw["new_text"]),
}                              ↑↑↑↑↑↑↑↑ 字典里存的都是 lambda 函数

📍 用法拆解

handler = TOOL_HANDLERS.get("bash") # handler 现在是: lambda **kw: run_bash(kw["command"]) ← 一个函数对象 handler(**{"command": "ls -la"}) # 等价于: run_bash("ls -la")

类比更简单的例子：

func_map = {"greet": lambda name: f"Hello, {name}"}

f = func_map["greet"]       # f 就是一个函数
result = f("Alice")        # 调用它 → "Hello, Alice"

📍 ** 解包

**{"command": "ls -la", "cwd": "/tmp"} 展开成 command="ls -la", cwd="/tmp"，这些作为关键字参数传给 lambda。

4 block.name 从哪里来？

block.name 的值来源于模型的自主选择，不是代码硬编码的。

📍 block 是什么？

response.content 是一个列表，里面每个元素是 Anthropic SDK 反序列化后的 ContentBlock 对象。

Block 类型出现时机关键属性类比
TextBlock模型想说话时.type = "text", .text = "..."模型在"说"
ToolUseBlock模型想调工具时.type = "tool_use", .name, .id, .input模型在"要"
ToolResultBlock你把结果写回时.type = "tool_result", .tool_use_id, .content你在"喂结果"

📍 完整链路

你传给模型的工具列表: CHILD_TOOLS = [ {"name": "bash", ...}, ← 告诉模型：有个工具叫 "bash" {"name": "read_file", ...}, ← 有个工具叫 "read_file" ... ] 模型在响应中说 "我想调 read_file": response.content = [ TextBlock(type="text", text="让我看看文件内容"), ToolUseBlock( ← SDK 对象，不是字典 type="tool_use", id="toolu_abc123", name="read_file", ← 模型选中了这个工具 input={"path": "main.py"} ← 模型自己填的参数 ) ] 代码中的查找链: block.name == "read_file" ↓ TOOL_HANDLERS.get("read_file") → lambda ↓ run_read(path="main.py") → 执行

📍 是谁定义了 ToolUseBlock 的属性？

层谁做的做了什么
API 规范Anthropic 公司规定 tool_use 块必须有 id、name、input 字段
SDKanthropic 包把 JSON 反序列化成 Python 对象，提供 .type、.name、.id、.input 属性
为什么是 block.name 而不是 block["name"]？
因为 SDK 把 API 返回的 JSON 转成了 Python 对象（ToolUseBlock），不是字典。对象访问属性用点号，字典用方括号。你可以在 Python 里验证： 
type(block)  # <class 'anthropic.types.tool_use_block_param.ToolUseBlockParam'>
isinstance(block, dict)  # False

5 父 agent 如何决定调用子 agent？

完全由大模型自主判断，代码里没有任何逻辑说"现在必须调子 agent"。

📍 代码做了哪两件事

第一：告诉模型有一个 task 工具可用

{"name": "task",
 "description": "Spawn a subagent with fresh context. It shares the filesystem but not conversation history.",
 "input_schema": {
     "type": "object",
     "properties": {
         "prompt": {"type": "string"},
         "description": {"type": "string", "description": "Short description..."}
     },
     "required": ["prompt"]
 }}

第二：把工具列表传给 API（里面包含 task）

response = client.messages.create(
    ...
    tools=PARENT_TOOLS,   # ← 5 个工具全传（含 task）
    ...
)

📍 模型看到了什么

工具名描述（给模型看的）模型何时可能调用它
bash"Run a shell command."想执行命令
read_file"Read file contents."想读文件
write_file"Write content to file."想写文件
edit_file"Replace exact text in file."想编辑文件
task"Spawn a subagent with fresh context..."觉得任务可以独立出去

📍 模型为什么"愿意"调 task？

  1. description 写得好——"Spawn a subagent with fresh context." 明确告诉模型可以外包
  2. 训练数据覆盖——Claude 训练时就学过"有 task 工具时，合适场景可以派生子任务"
类比: 你给一个人两个指令 ① 螺丝刀 —— 描述："拧螺丝" ② 电钻 —— 描述："在墙上打孔" 你自己决定什么时候用什么。 代码的角色 = 提供工具并描述清楚 模型的角色 = 看情况自己选

📍 实际推理过程（模拟）

用户问"这个项目用什么测试框架？"，模型的推理过程：

轮次模型想调用
1"我需要先读 pyproject.toml"read_file
2"再看看 requirements.txt"read_file
3"跑一下 pytest --version"bash
4"这些中间步骤没必要留在父对话里"task(prompt="检查测试框架...")

代码里没有 if 判断说"超过 3 轮就调子 agent"，完全是模型自主决定。

维度s03（待办写入）s04（子代理）
核心问题模型记不住多步计划父上下文被局部任务噪声填满
解决方案外部 Todo 计划追踪子 agent 独立上下文隔离

📍 新增 了什么

新增内容位置为什么加
SUBAGENT_SYSTEML58子 agent 需要自己的 system prompt（与父角色不同：执行者+总结者）
AgentTemplate 类L60-91教学展示：真实 Claude Code 的 agent 配置文件解析（当前未使用）
run_subagent()L157-173创建子 agent、隔离上下文、限制轮数、只返回摘要
CHILD_TOOLSL140-153子 agent 专属工具列表（4 个，不含 task）
PARENT_TOOLSL175-180父 agent 工具列表（5 个，多一个 task）
task 处理分支L197-200block.name == "task" 时不走 handler，直接启动子 agent

📍 删除 了什么

删除内容s03 中位置 / 作用为什么删
TodoManager 类体系~70 行计划管理s04 关注"上下文隔离"而非"计划管理"，焦点不同
PlanningState / PlanItem两个 dataclass计划系统的附属数据结构
PLAN_REMINDER_INTERVAL提醒间隔常量提醒机制是计划系统的附属功能

todo 工具定义TOOLS 列表 + TOOL_HANDLERS由 task 工具替代，不再需要

📍 修改 了什么

修改项s03s04
SYSTEM 提示词"...Use the todo tool for multi-step work.""...Use the task tool to delegate exploration..."
tool 处理逻辑所有工具统一 handler(**block.input)，额外检查 used_todotask 特殊处理（启动子 agent），其他 走 handler
TOOL_HANDLERS5 个（含 todo）4 个（无 todo，task 在 agent_loop 单独处理）

📍 演进逻辑

s03 → s04 的演进不是"替换"，而是换个方向解决不同问题：

s03：模型脑子里记不住计划 → 用外部 Todo 帮它记

s04：父上下文被局部任务填满 → 用子 agent 隔离出去做

两者不冲突，可以组合（需要时可以在 s04 基础上再加回 TodoManager）。

📍 架构对比图

s03 架构（只有消息流 + 外部计划状态）： ┌────────────────┐ │ PlanningState │ │ - items │ │ - rounds... │ └───────┬────────┘ │ messages ──→ AI ──→ tool_use ──→ 执行工具 ──→ 结果写回 messages ↑ │ └───────── reminder ─────────────────┘ s04 架构（多了子 agent 上下文隔离）： 父 agent 循环 子 agent 循环 messages ──→ AI ──→ tool_use ──→ task(prompt) ──→ sub_messages（全新） │ │ ↓ │ │ 执行工具... │ │ ↓ │ └── 摘要 ──→ 返回父对话 └── 其他工具 ──→ 执行 ──→ 结果写回 messages

7 概念速查表

概念一句话
子代理 (Subagent)父 agent 临时派生的、使用独立上下文的执行单元
上下文隔离子 agent 的 messages 从空开始，父 agent 的历史不污染它
摘要返回子 agent 只返回文本摘要，不返回中间工具调用历史
工具隔离子 agent 没有 task 工具，不能继续生子 agent
Frontmatter--- 包裹的 YAML 元数据段，用于定义 agent 角色属性
ToolUseBlockSDK 对象，表示"模型想调工具"，包含 .name, .id, .input
stop_reasonAPI 响应字段，"tool_use" 表示模型还要继续调工具
CHILD_TOOLS子 agent 的工具集：bash, read_file, write_file, edit_file（不含 task）
PARENT_TOOLS父 agent 的工具集：CHILD_TOOLS + task
函数一等公民Python 中函数可以像普通值一样存进字典、赋值给变量、当作参数传递
