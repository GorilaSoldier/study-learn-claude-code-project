1 load_dotenv — 从 .env 文件加载环境变量

代码位置

一句话：把 .env 文件中的键值对读入 os.environ，让程序能读取配置（如 API Key 等）。 
from dotenv import load_dotenv

load_dotenv(override=True)

参数 override=True 的含义

参数值行为
override=False（默认）系统中已存在的环境变量不会被 .env 覆盖
override=True.env 中的值强制覆盖系统中已有的同名变量

为什么需要它？

后续代码中使用了 os.getenv("ANTHROPIC_BASE_URL") 和 os.environ["MODEL_ID"] 来读取配置。如果不先调用 load_dotenv()，这些环境变量不会被加载到 os.environ 中，os.getenv 读到的一律是 None。

ANTHROPIC_BASE_URL=https://your-api-endpoint
MODEL_ID=claude-sonnet-4-20260514
常见用途：开发环境中把敏感配置（API Key、数据库密码）放在 .env 中，不上传到 Git。生产环境则通过系统环境变量注入。load_dotenv 让开发体验和产线体验一致。

2 常量和工具分类

MODES = ("default", "plan", "auto")

READ_ONLY_TOOLS = {"read_file", "bash_readonly"}

WRITE_TOOLS = {"write_file", "edit_file", "bash"}

2.1 MODES — 三种权限模式

模式含义适用场景
default未命中规则时询问用户日常交互，安全中等的默认模式
plan只允许读，不允许写计划、审查、分析——AI 只能看不能改
auto简单安全操作自动过，危险操作再问高流畅度探索，信任度较高的场景
设计意图：教学版只做三种模式，让读者先理解"模式"这个概念本身。不要一上来做 6 个模式、10 个策略源。

2.2 READ_ONLY_TOOLS 和 WRITE_TOOLS

用集合（set）存放，因为集合的查找速度是 O(1)，比列表快。

集合包含的工具为什么这样归类
READ_ONLY_TOOLSread_file, bash_readonly这些工具不会修改任何数据，只是读取
WRITE_TOOLSwrite_file, edit_file, bash这些工具会修改文件或执行命令，有潜在风险
注意：bash 被归类为写入工具！因为 bash 能做任何事（包括删除文件、修改配置），不能当作只读工具对待。

3 BashSecrityValidator — bash 安全检查器

代码位置：L46-84

一句话：在执行 bash 命令之前，用正则表达式检测它有没有危险操作。
课程核心思想："bash 不是普通文本，而是可执行动作描述。"

3.1 5 个危险模式

VALIDATORS = [
    ("shell_metachar",    r"[;&|`$]"),              # shell 元字符（连接多条命令）
    ("sudo",              r"\bsudo\b"),              # 提权操作（sudo）
    ("rm_rf",             r"\brm\s+(-[a-zA-Z]*)?r"), # 递归删除（rm -r）
    ("cmd_substitution",  r"\$\("),                  # 命令替换（$(...)）
    ("ifs_injection",     r"\bIFS\s*="),            # IFS 变量操纵
]
名称正则匹配什么示例
shell_metachar[;&|`$]shell 元字符，用于连接多条命令ls ; rm -rf、kill -9 $PID
sudo\bsudo\b提权操作sudo apt install
rm_rf\brm\s+(-[a-zA-Z]*)?r递归删除（带 -r 标志）rm -rf /、rm -r ./
cmd_substitution\$\(命令替换，执行嵌套命令echo $(whoami)
ifs_injection\bIFS\s*=修改 IFS 变量（shell 注入手段）IFS=/

3.2 三个核心方法

def validate(self, command: str) -> list:
    """返回匹配到的所有危险模式列表。空列表 = 安全。"""
    failures = []
    for name, pattern in self.VALIDATORS:
        if re.search(pattern, command):
            failures.append((name, pattern))
    return failures
方法返回类型说明
validate(command)list[tuple]返回 [(名称, 正则), ...]，空列表表示安全
is_safe(command)bool便捷方法，True 表示所有验证都通过
describe_failures(command)str生成人类可读的描述，如 "Security flags: rm_rf (pattern: ...)"
严重级别区分：在 check() 中，命中 sudo 或 rm_rf 直接拒绝（不可绕过）；命中其他模式则改为询问用户（用户可以手动批准）。

4 正则表达式详解

代码位置涉及的正则：L57-61

4.1 \b — 单词边界

一句话：不匹配任何字符，只匹配一个"单词和非单词字符之间的缝隙"。
表达式匹配 "sudo"匹配 "sudoer"原因
sudo✅✅（会匹配前4个字符）无边界限制
\bsudo\b✅❌o 后面是 e（单词字符），没有边界

所以 \bsudo\b 是为了精确匹配 sudo 这个单词，而不是 sudoer、sudoapt。

4.2 \$ — 转义的美元符号

在正则中，$ 有特殊含义——匹配字符串末尾。但我们想匹配的是字面上的 $ 符号（如 $HOME、$(whoami)），所以要用 \$ 转义。

4.3 \( — 转义的左括号

( 在正则有特殊含义——创建捕获组。要匹配字面上的 (，用 \( 转义。

所以 \$\( 连起来匹配 $( 这两个字符——正是 shell 中命令替换的语法：

echo $(whoami)    # 执行 whoami，把结果嵌入到命令中

常用转义对照表

字符特殊含义转义写法匹配的字面量
.匹配任意字符\.句点 .
*重复 0 次或多次\*星号 *
$行尾\$美元符号 $
(分组开始\(左括号 (

4.4 re.search vs re.match

函数行为打个比方
re.match(pattern, string)从字符串开头匹配，开头对不上就放弃检查"名字是否以'张'开头"
re.search(pattern, string)在整个字符串中搜索，哪里能匹配就从哪里算"在全文里找'张'这个字"
import re

text = "hello, my name is zhangsan"

re.match(r"hello", text)   # ✅ 匹配，因为开头就是 hello
re.match(r"name", text)    # ❌ 不匹配，开头是 hello 不是 name

re.search(r"name", text)   # ✅ 匹配，在中间找到了
代码中用 search 的原因：要检查命令中任何位置是否出现危险模式，而不是只在开头检查。

re.search 的返回值：匹配成功返回 Match 对象（布尔上下文中为 True），失败返回 None。

if re.search(pattern, command):    # 匹配到 → 布尔 True → 进入分支
    failures.append(...)

4.5 \brm\s+(-[a-zA-Z]*)?r 详细拆解

这个正则的目标是匹配带 -r 标志（递归）的 rm 命令。

分解图

\b       rm       \s+       (           -[a-zA-Z]*          )?       r
│        │         │         │               │               │       │
│        │         │         │               │               │       │
单词    字面      至少1个    分组开始       破折号后跟      整个    字面
边界    "rm"     空白符                   0个或多个字母    分组    "r"
                                               │          可选
                                               │
                                            -r, -rf, -rfv 等

关键机制：正则回溯

[a-zA-Z]* 默认贪婪匹配（尽可能多吞字符），但正则引擎在遇到后续匹配失败时会回溯（吐出字符再试）。

以 rm -rf /tmp 为例，匹配过程：

字符串:  r  m     -  r  f     /  t  m  p

步骤1: \b rm 匹配前3个字符 ✅

步骤2:  \s+ 匹配空格 ✅

步骤3: 进入 (-[a-zA-Z]*)?r
  尝试A（贪婪）：(-[a-zA-Z]*) 吞 "-rf"，然后 r 需要匹配 " " → ❌
  尝试B（回溯）：(-[a-zA-Z]*) 吞 "-r"，然后 r 需要匹配 "f" → ❌
  尝试C（再回）：(-[a-zA-Z]*) 吞 "-"（[a-zA-Z]* 吞空串），然后 r 匹配 "r" → ✅！

匹配结果

命令匹配？说明
rm -rf /tmp✅ 匹配匹配 rm -r，f /tmp 剩余部分不要求匹配完
rm -r dir✅ 匹配匹配 rm -r
rm -fr✅ 匹配[a-zA-Z]* 吞 "f"，最后的 r 匹配后面的 r
rm file.txt❌ 不匹配没有 - 号，最后的 r 也找不到
rm -f file.txt❌ 不匹配有 -f 但没有 r
germ -rf❌ 不匹配\b 阻止了 germ 中的 rm

5 fnmatch — 通配符匹配引擎

代码位置：L226-229（_matches 中使用）

一句话：fnmatch 是 Python 内置库（File Name Match），用文件通配符规则做字符串匹配。
代码中用于匹配规则中的 path 和 content，让用户能写简单的通配符规则，不用学正则。

5.1 支持的通配符

符号含义匹配举例
*匹配任意数量字符（包括 0 个）*.py → a.py ✅、a.txt ❌
?匹配恰好 1 个字符?.py → a.py ✅、ab.py ❌
[abc]匹配方括号内任意 1 个字符[ab].py → a.py ✅、c.py ❌
[!abc]匹配不在方括号内的任意 1 个字符[!ab].py → c.py ✅、a.py ❌

5.2 常用函数

import fnmatch

# 1. fnmatch — 单个匹配（最常用）
fnmatch.fnmatch("hello.txt", "*.txt")      # ✅ True
fnmatch.fnmatch("hello.txt", "*.py")       # ❌ False

# 2. filter — 批量过滤列表
files = ["a.py", "b.py", "c.txt"]
fnmatch.filter(files, "*.py")                 # ['a.py', 'b.py']

5.3 代码中的实际用法

匹配路径：

# 规则中 path = "*.py" → 所有 Python 文件
# 规则中 path = "/tmp/*" → /tmp 下的所有文件
if "path" in rule and rule["path"] != "*":
    path = tool_input.get("path", "")
    if not fnmatch.fnmatch(path, rule["path"]):
        return False

匹配命令：

# 规则中 content = "sudo *" → 所有 sudo 开头的命令
# 规则中 content = "rm -rf /" → 精确匹配删根目录
if "content" in rule:
    command = tool_input.get("command", "")
    if not fnmatch.fnmatch(command, rule["content"]):
        return False
fnmatch vs 正则：fnmatch 内部也是用正则实现的（fnmatch.translate(pattern)），但语法更简单——只需要懂通配符。代码中 fnmatch 用于用户可配置的规则，正则用于内部硬编码的安全检查。

7 check() — 4 步权限管线

代码位置：L126-186

一句话：这是整个权限系统的核心，工具调用请求按 4 步顺序走，命中任意一步就返回决策。
check(tool_name, tool_input) │ ┌────────┴────────┐ │ Step 0: Bash │ → 高危(deny) / 低危(ask) │ 安全预检 │ └────────┬────────┘ │ 通过 ┌────────┴────────┐ │ Step 1: Deny │ → 匹配 → return deny │ 规则遍历 │ └────────┬────────┘ │ 没匹配 ┌────────┴────────┐ │ Step 2: 模式 │ → plan(deny写,allow读) │ 检查 │ auto(allow读,继续往下) └────────┬────────┘ default(继续往下) │ ┌────────┴────────┐ │ Step 3: Allow │ → 匹配 → return allow │ 规则遍历 │ └────────┬────────┘ │ 没匹配 ┌────────┴────────┐ │ Step 4: 询问 │ → return ask │ 用户 │ └─────────────────┘

Step 0: Bash 安全预检（L130-148）

Step 1: Deny 规则（L149-157）

for rule in self.rules:
    if rule["behavior"] != "deny":     # 只处理 deny 类型的规则
        continue
    if self._matches(rule, tool_name, tool_input):
        return {"behavior": "deny", ...}

遍历所有规则，只处理 behavior == "deny" 的规则。匹配到任意一条就立即返回拒绝。

Step 2: 模式检查（L159-171）

模式行为
plan写入工具（write_file, edit_file, bash）→ deny；读取工具 → allow
auto只读工具 → allow；其他 → 继续往下走（pass）
default两个 if 都不进，直接继续往下走

Step 3: Allow 规则（L172-181）

for rule in self.rules:
    if rule["behavior"] != "allow":     # 只处理 allow 类型的规则
        continue
    if self._matches(rule, tool_name, tool_input):
        self.consecutive_denials = 0
        return {"behavior": "allow", ...}

类似 Step 1，但只处理 behavior == "allow" 的规则。匹配到就放行，同时重置连续拒绝计数器。

核心设计：deny 始终优先于 allow。无论规则在列表中的顺序如何，deny 规则都先遍历，确保安全策略不被绕过。

Step 4: 询问用户（L183-186）

return {"behavior": "ask",
        "reason": f"No rule matched for {tool_name}, asking user"}

所有规则都没匹配 + 模式检查也没做决定 → 交给用户判断。这是"默认安全"的设计——宁可多问，不要擅自执行。

8 为什么 deny 和 allow 要分两次遍历

对应代码：L149-157（deny 循环）和 L172-181（allow 循环）

一句话：因为 deny 的优先级必须高于 allow，分两次遍历确保 deny 永远优先，不受规则顺序影响。

错误做法：一个循环同时处理

# ❌ 错误：规则顺序决定优先级
for rule in self.rules:
    if self._matches(rule, tool_name, tool_input):
        if rule["behavior"] == "deny":
            return {"behavior": "deny", ...}
        else:
            return {"behavior": "allow", ...}

如果规则列表是：

[
    {"tool": "bash", "path": "*",          "behavior": "allow"},  # allow 在前面
    {"tool": "bash", "content": "sudo *",  "behavior": "deny"},   # deny 在后面
]

执行 sudo rm -rf /：

  • 第一个循环：规则 0（allow）匹配 ✅ → 返回 allow — 危险命令被放行了！

正确做法：分两次遍历

Step 1（deny 循环）：

  • 规则 0：behavior != "deny" → continue 跳过
  • 规则 1：behavior == "deny"，sudo * 匹配 ✅ → 返回 deny

Step 3（allow 循环）：

  • 根本不会执行到（Step 1 已经 return 了）
本质：deny = 黑名单模式，allow = 白名单模式。先对所有请求做黑名单过滤，再对剩下的请求做白名单匹配。黑名单永远优先于白名单——这就是"拒绝优先"原则。

9 _matches — 规则匹配引擎（含实际运行例子）

代码位置：L224-232

一句话：判断"一条规则是否管当前这个工具调用"。只负责匹配判断，不关心匹配后是 allow 还是 deny。 
def _matches(self, rule: dict, tool_name: str, tool_input: dict) -> bool:
    # 第 1 步：检查工具名
    if rule.get("tool") and rule["tool"] != "*":
        if rule["tool"] != tool_name:
            return False

    # 第 2 步：检查路径
    if "path" in rule and rule["path"] != "*":
        path = tool_input.get("path", "")
        if not fnmatch.fnmatch(path, rule["path"]):
            return False

    # 第 3 步：检查内容（命令）
    if "content" in rule:
        command = tool_input.get("command", "")
        if not fnmatch.fnmatch(command, rule["content"]):
            return False

    return True  # 全部通过 → 匹配成功

三步匹配流程

步骤匹配条件代码逻辑
① 工具名规则指定了 tool 且不是 "*"当前工具名必须和规则一致
② 路径规则指定了 path 且不是 "*"从参数中取 path 字段，用 fnmatch 匹配
③ 内容规则指定了 content从参数中取 command 字段，用 fnmatch 匹配

Step 1（deny 循环）：

规则 1behavior: deny否 → continue不执行
规则 2{tool: read_file, path: "*", behavior: "allow"}是工具名匹配 ✅ + path 通配 ✅ → ✅ True

返回 {"behavior": "allow", "reason": "Matched allow rule: ..."}

实际运行例子 3：执行 bash + ls -la（default 模式，没有规则匹配）

Step 1：规则 0 和规则 1 都匹配失败，规则 2 被跳过 → 没匹配

Step 2：default 模式 → 继续

Step 3：规则 0 和规则 1 被跳过，规则 2 工具名 "read_file" ≠ "bash" → ❌ False

Step 4：返回 {"behavior": "ask", "reason": "No rule matched for bash, asking user"}

所以不是"除了 deny 就是 allow"：还有一个 ask。没被任何规则匹配的请求，既不自动拒绝也不自动放行，而是交给用户判断。这是"默认安全"的设计。

10 ask_user — 交互式用户确认

代码位置：L188-213

一句话：当权限管线走到 Step 4 时，在终端打印工具调用详情，让用户选择允许、拒绝或永久允许。 
def ask_user(self, tool_name: str, tool_input: dict) -> bool:
    # ① 展示工具调用内容（JSON 格式，截取前 200 字符）
    preview = json.dumps(tool_input, ensure_ascii=False)[:200]
    print(f"\n [permission] {tool_name}: {preview}")

    # ② 读取用户输入（捕获 Ctrl+C / Ctrl+D）
    try:
        answer = input(" Allow? (y/n/always): ").strip().lower()
    except (EOFError, KeyboardInterrupt):
        return False

    # ③ always → 添加永久 allow 规则到列表末尾
    if answer == "always":
        self.rules.append({"tool": tool_name, "path": "*", "behavior": "allow"})
        self.consecutive_denials = 0
        return True

    # ④ y/yes → 只本次允许，不添加规则
    if answer in ("y", "yes"):
        self.consecutive_denials = 0
        return True

    # ⑤ 拒绝 → 增加计数器，触发"断路器"提醒
    self.consecutive_denials += 1
    if self.consecutive_denials >= self.max_consecutive_denials:
        print(f"  [{self.consecutive_denials} consecutive denials -- "
              "consider switching to plan mode]")
    return False
用户输入效果
y / yes只本次允许，不改变规则列表
always本次允许 + 添加一条永久 allow 规则，之后同样的工具不再询问
n 或其他拒绝，增加连续拒绝计数器
Ctrl+C / Ctrl+D视为拒绝

"断路器"提醒

如果用户连续 3 次拒绝 AI 的请求，系统会打印提示：

[3 consecutive denials -- consider switching to plan mode]

意思是"AI 一直在请求你不想让它做的事，不如切换到 plan 模式，先让 AI 做计划给你看"。

13 safe_path — 路径安全检查

代码位置：L241-246

一句话：防止路径穿越攻击——确保所有文件操作都限制在项目工作目录内。 
def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()                    # ① 拼接后解析为绝对路径
    if not path.is_relative_to(WORKDIR):               # ② 检查是否还在工作目录内
        raise ValueError(f"Path escapes workspace: {p}")
    return path
步骤说明
① (WORKDIR / p).resolve()把路径拼接到工作目录后面，再解析为绝对路径。例如 /home/project/../etc/passwd → /home/etc/passwd
② is_relative_to(WORKDIR)检查最终路径是否以 WORKDIR 为前缀。如果用户传了 ../../etc/shadow，解析后跑出了工作目录，就拒绝并报错
经典攻击场景：如果 AI 被恶意提示词引导去读 /etc/passwd 或写 ~/.ssh/authorized_keys，safe_path 会拦截！所有涉及文件读写的函数（run_read、run_write、run_edit）都会调用它做检查。
