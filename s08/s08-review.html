1 本章核心设计理念

核心格言："Extend the agent without touching the loop."
—— 扩展 Agent 的行为，而不修改主循环代码。

这一章要解决什么问题

到了 s07，我们已经能在工具执行前做权限判断。但很多真实需求并不属于"允许/拒绝"这条线，而属于：

  • 在某个固定时机顺手做一点事
  • 不改主循环主体，也能接入额外规则
  • 让用户或插件在系统边缘扩展能力

例如：会话开始时打印欢迎信息、工具执行前做一次额外检查、工具执行后补一条审计日志。

如果每增加一个需求，你都去修改主循环，主循环就会越来越重，最后谁都不敢动。

什么是 Hook

你可以把 Hook 理解成一个"预留插口"：

  1. 主系统运行到某个固定时机
  2. 把当前上下文交给 Hook
  3. Hook 返回结果
  4. 主系统根据结果决定下一步怎么继续
最重要的一句话：Hook 让系统可扩展，但不要求主循环理解每个扩展需求。 主循环只需要知道三件事：现在是什么事件、要把哪些上下文交出去、收到结果以后怎么处理。

三个核心事件（教学版）

事件时机作用
SessionStart程序启动时，进入主循环之前初始化、打印欢迎信息、检查环境
PreToolUse工具执行之前安全检查、参数修改、阻止执行
PostToolUse工具执行之后审计日志、结果增强、注入消息

教学版退出码统一契约

退出码含义类比
0正常继续绿灯——一切正常，继续走
1阻止当前动作红灯——停下，不许执行
2注入一条补充消息，再继续黄灯——顺便传递一条消息

2 常量定义解析

代码位置：L42-L48

HOOK_EVENTS = {"PreToolUse", "PostToolUse", "SessionStart"}
HOOK_TIMEOUT = 30
TRUST_MARKER = WORKDIR / ".claude" / ".claude_trusted"
常量类型含义
HOOK_EVENTSset[str]定义了三个钩子事件：工具使用前、工具使用后、会话开始
HOOK_TIMEOUTint每个钩子命令最多执行 30 秒，超时会被杀掉
TRUST_MARKERPath工作区信任标记文件路径。钩子只在该文件存在时才执行
为什么需要信任机制？ 钩子会通过 subprocess.run 执行外部命令。如果工作区被恶意篡改，.hooks.json 可能包含危险命令。 信任标记文件确保只有用户主动"信任"的工作区才会执行钩子。

信任标记文件的完整路径示例：

D:\code\learn-claude-code\.claude\.claude_trusted

3 HookManager.__init__ — 加载配置

代码位置：L56-L70

def __init__(self, config_path: Path = None, sdk_mode: bool = False):
    self.hooks = {"PreToolUse": [], "PostToolUse": [], "SessionStart": []}
    self._sdk_mode = sdk_mode
    config_path = config_path or (WORKDIR / ".hooks.json")
    if config_path.exists():
        try:
            config = json.loads(config_path.read_text())
            for event in HOOK_EVENTS:
                self.hooks[event] = config.get("hooks", {}).get(event, [])
            print(f"[Hook loaded from {config_path}]")
        except Exception as e:
            print(f"[Hook config error: {e}]")

参数说明

参数默认值说明
config_pathNone默认为工作目录下的 .hooks.json
sdk_modeFalseSDK 模式下信任隐式生效，无需信任标记文件

执行流程

  1. 初始化三个空列表：{"PreToolUse": [], "PostToolUse": [], "SessionStart": []}
  2. 确定配置文件路径：如果没有传入 config_path，就用 WORKDIR / ".hooks.json"
  3. 检查文件是否存在：如果不存在，hooks 保持为空列表（什么都不做）
  4. 读取并解析 JSON：提取每个事件对应的钩子命令列表
  5. 容错处理：任何异常只打印错误，不崩溃程序
设计意图：.hooks.json 不是必须的。如果不创建，程序正常运行，只是没有任何钩子行为。 这体现了"扩展是可选的"设计思路。

4 _check_workspace_trust — 信任机制

代码位置：L72-L78

def _check_workspace_trust(self) -> bool:
    if self._sdk_mode:
        return True
    return TRUST_MARKER.exists()
条件行为
self._sdk_mode = TrueSDK 模式，信任隐式生效，直接返回 True
信任标记文件存在返回 True，允许执行钩子
信任标记文件不存在返回 False，拒绝执行任何钩子
安全原则：不信任的工作区，一个钩子都不执行。即使 .hooks.json 存在也不执行。 这是双层安全防护：第一层是信任标记，第二层才是钩子配置。

5 run_hooks — 核心方法总览

代码位置：L82-L155

一句话：接收一个事件名和上下文，执行所有匹配的钩子脚本，返回阻塞/消息结果。

方法签名

def run_hooks(self, event: str, context: dict = None) -> dict:
参数类型含义
eventstr事件名，如 "PreToolUse"
contextdict上下文信息，包含 tool_name、tool_input、tool_output（可选）

返回值结构

{
    "blocked": False,          # True 表示钩子阻止了执行
    "messages": [],             # 钩子注入的消息列表
    # 以下字段只在特定情况下出现:
    "block_reason": "...",     # 阻止原因（blocked=True 时）
    "permission_override": ...  # 权限决策覆写（JSON stdout 时）
}

6 run_hooks 内部详解（6 大步）

第 1 步：信任检查

if not self._check_workspace_trust():
    return result  # 直接返回空结果，一个钩子都不执行

第 2 步：按事件名筛选钩子列表

hooks = self.hooks.get(event, [])  # 只拿当前事件的钩子

第 3 步：Matcher 过滤

matcher = hook_def.get("matcher")
if matcher and context:
    tool_name = context.get("tool_name", "")
    if matcher != "*" and matcher != tool_name:
        continue  # 不匹配，跳过
matcher 值行为
没有 matcher 字段不过滤，任何工具都触发
"*"通配符，任何工具都触发
"bash"只有当前工具名为 "bash" 时才触发
其他字符串只有精确匹配工具名时才触发

第 4 步：构建环境变量

env = dict(os.environ)
if context:
    env["HOOK_EVENT"] = event
    env["HOOK_TOOL_NAME"] = context.get("tool_name", "")
    env["HOOK_TOOL_INPUT"] = json.dumps(context.get("tool_input", {}))[:10000]
    if "tool_output" in context:
        env["HOOK_TOOL_OUTPUT"] = str(context["tool_output"])[:10000]
环境变量内容长度限制
HOOK_EVENT当前事件名—
HOOK_TOOL_NAME正在调用的工具名—
HOOK_TOOL_INPUT工具的输入参数（JSON 字符串）前 10000 字符
HOOK_TOOL_OUTPUT工具的输出结果前 10000 字符
为什么有长度限制？ 防止超大 JSON 打爆操作系统的环境变量缓冲区。 坏数据会被静默截断，但不会让钩子崩溃。

第 5 步：执行子进程

r = subprocess.run(
    command, shell=True, cwd=WORKDIR, env=env,
    capture_output=True, text=True, timeout=HOOK_TIMEOUT,
)
参数作用
shell=True通过系统 Shell 解释执行（支持管道、重定向）
capture_output=True捕获 stdout 和 stderr，不打印到终端
text=True以字符串（而非 bytes）形式返回输出
timeout=3030 秒超时，超时则杀掉进程并抛异常
cwd=WORKDIR在工作目录下执行命令

第 6 步：异常处理（容错设计）

except subprocess.TimeoutExpired:
    print(f"  [hook:{event}] TIMEOUT ({HOOK_TIMEOUT}s)")
except Exception as e:
    print(f"  [hook:{event}] ERROR: {e}")
健壮性设计：钩子挂了（超时、异常、命令不存在），主流程不受影响。 只打印日志，不抛异常，不崩溃程序。

7 退出码契约详解（0 / 1 / 2）

退出码 0 — 继续执行

if r.returncode == 0:
    if r.stdout.strip():
        print(f"  [hook:{event}] {r.stdout.strip()[:100]}")
    try:
        hook_output = json.loads(r.stdout)
        if "updatedInput" in hook_output:
            context["tool_input"] = hook_output["updatedInput"]
        if "additionalContext" in hook_output:
            result["messages"].append(hook_output["additionalContext"])
        if "permissionDecision" in hook_output:
            result["permission_override"] = hook_output["permissionDecision"]
    except (json.JSONDecodeError, TypeError):
        pass  # stdout 不是 JSON —— 普通的简单钩子
stdout 类型行为
纯文本打印日志，正常继续
JSON，包含 updatedInput修改工具输入参数
JSON，包含 additionalContext注入附加上下文消息给 AI
JSON，包含 permissionDecision覆写权限决策

退出码 1 — 阻止执行

elif r.returncode == 1:
    result["blocked"] = True
    reason = r.stderr.strip() or "Blocked by hook"
    result["block_reason"] = reason
    print(f"  [hook:{event}] BLOCKED: {reason[:200]}")
    # 被阻止后，agent_loop 会跳过工具执行

退出码 2 — 注入消息

elif r.returncode == 2:
    msg = r.stderr.strip()
    if msg:
        result["messages"].append(msg)
        print(f"  [hook:{event}] INJECTED: {msg[:200]}")
    # 消息会在工具执行后追加到输出末尾
┌─────────────────────────────────────────────┐ │ 退出码 0 → 继续执行，可选 JSON 修改行为 │ │ 退出码 1 → 阻止工具执行，返回 block_reason │ │ 退出码 2 → 不阻止，但向 AI 注入一条消息 │ └─────────────────────────────────────────────┘

8 何时调用 Hook？三处调用点

调用点 ①：SessionStart（L335）

hooks.run_hooks("SessionStart", {"tool_name": "", "tool_input": {}})

时机：程序刚启动，还没进入主循环。

调用点 ②：PreToolUse（L289）

pre_result = hooks.run_hooks("PreToolUse", ctx)

时机：AI 返回了 tool_use，但工具还没执行。

这是最关键的一个调用点——它的结果直接影响是否执行工具：

if pre_result.get("blocked"):
    # 跳过工具执行，返回"被阻止"消息给 AI
    continue

# 没被阻止，才去执行工具
output = handler(**tool_input)  # 注意：tool_input 可能已被钩子修改

调用点 ③：PostToolUse（L317）

post_result = hooks.run_hooks("PostToolUse", ctx)

时机：工具已经执行完毕，但结果还没返回给 AI。

钩子可以通过 messages 在输出末尾追加内容：

for msg in post_result.get("messages", []):
    output += f"\n[Hook note]: {msg}"
不对称设计：PreToolUse 的 blocked 会被读取并阻止工具执行。 PostToolUse 的 blocked 没有被检查——因为工具已经执行完了，阻止没有意义。

主程序入口（L331-L353）

if __name__ == "__main__":
    hooks = HookManager()                          # 加载 .hooks.json
    hooks.run_hooks("SessionStart", ...)             # 触发 SessionStart

    history = []
    while True:
        query = input("\033[36ms04 >> \033[0m")         # 等待用户输入
        if query in ("q", "exit", ""): break           # 退出条件

        history.append({"role": "user", "content": query})
        agent_loop(history, hooks)                    # 进入主循环
        # 打印 AI 的最终回复
        response_content = history[-1]["content"]
        if isinstance(response_content, list):
            for block in response_content:
                if hasattr(block, "text"):
                    print(block.text)

10 subprocess — 启动子进程

代码位置：L116-L119

r = subprocess.run(
    command, shell=True, cwd=WORKDIR, env=env,
    capture_output=True, text=True, timeout=HOOK_TIMEOUT,
)
一句话：subprocess.run 是 Python 标准库中启动"子进程"的函数—— 在当前 Python 程序之外，另外开一个独立的操作系统进程去执行命令。

工作原理

Python 进程                       操作系统
┌──────────┐                   ┌──────────┐
│          │   subprocess       │          │
│  Hook    │ ────run()──────→  │  子进程  │
│ Manager  │                   │  (bash)  │
│          │ ←──结果返回─────  │          │
└──────────┘                   └──────────┘

各参数详解

参数值作用
command钩子定义的命令字符串要执行的命令，如 "echo hello" 或 "python check.py"
shell=True固定值通过 Shell 解释执行。不设的话，命令会被当作可执行文件路径
capture_output=True固定值把子进程的 stdout/stderr 捕获到内存，不打印到终端
text=True固定值返回的 stdout/stderr 是普通字符串而非 bytes
timeout=30秒数子进程最多跑 30 秒，超时杀掉进程并抛出异常
cwd=WORKDIR工作目录子进程从哪个目录开始运行
env=env环境变量字典子进程能看到的环境变量（含 HOOK_EVENT 等）

返回值 r（CompletedProcess）

r.returncode  # 退出码（整数）：0 成功，非 0 失败
r.stdout      # 标准输出（字符串）
r.stderr      # 标准错误（字符串）
退出码契约的实现基础：钩子系统通过检查 r.returncode 来判断钩子的意图： 0 → 继续，1 → 阻止，2 → 注入。

vs 其他方式

方式问题
os.system(cmd)返回退出码，但拿不到 stdout/stderr
os.popen(cmd)能读输出，但拿不到退出码，易资源泄漏
subprocess.run(...)退出码 + 输出 + 超时 + 环境变量全都能管

11 ctx 参数的生命周期

核心理解：同一个 ctx 对象在不同时间点有不同的状态

L286: ctx = {"tool_name": block.name, "tool_input": tool_input}
                ↑
         此时工具还没执行，ctx 里只有工具名和输入参数
                │
                ▼
L289: pre_result = hooks.run_hooks("PreToolUse", ctx)
                │
                ▼
        ...执行工具，拿到 output...
                │
                ▼
L316: ctx["tool_output"] = output    ← 执行完了，追加输出
                │
                ▼
L317: post_result = hooks.run_hooks("PostToolUse", ctx)
时间点ctx 的内容传给谁的
L286 刚创建{tool_name, tool_input}PreToolUse 钩子
L316 追加后{tool_name, tool_input, tool_output}PostToolUse 钩子
为什么 PreToolUse 不传 tool_output？ 因为工具还没执行，根本没有 output。
为什么 PostToolUse 还保留 tool_name 和 tool_input？ 钩子可能也需要知道"这个工具当初是用什么参数调用的"，方便做审计或逻辑判断。

可以把 ctx 理解成一个在流程中不断累积信息的通行证——每个阶段往里面添加上下文，下一个阶段就能用上。

12 Matcher 过滤机制

代码位置：L93-L98

matcher = hook_def.get("matcher")
if matcher and context:
    tool_name = context.get("tool_name", "")
    if matcher != "*" and matcher != tool_name:
        continue  # 不匹配，跳过这个钩子
一句话：事件名定大方向（PreToolUse / PostToolUse），matcher 定细粒度（只对某个工具生效）。 两个合在一起决定了哪个钩子该跑。

完整的双层过滤

run_hooks("PreToolUse", {"tool_name": "bash", ...}) │ │ ▼ ▼ 事件名过滤 工具名过滤（matcher） PreToolUse 只跑 matcher="bash" 或 "*" 的钩子 里的钩子 跳过 matcher="write_file" 的钩子

一个实际的例子

假设 .hooks.json 中 PreToolUse 配置了 3 个钩子，当前要调用 bash 工具：

钩子matcher当前 tool_name是否执行？
{"matcher": "bash", "command": "validate.py"}"bash""bash"✅ bash == bash → 执行
{"matcher": "*", "command": "echo running"}"*""bash"✅ 通配符 → 总是执行
{"matcher": "write_file", "command": "check.py"}"write_file""bash"❌ write_file != bash → 跳过

13 .hooks.json 配置详解

来源：需要手动创建。代码里没有自动生成它的逻辑，它由开发者/管理员手工编写。 如果文件不存在，程序正常运行，只是 hooks 为空列表，不会执行任何钩子。

典型结构

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "bash",
        "command": "python scripts/validate_command.py"
      },
      {
        "matcher": "*",
        "command": "echo Tool $HOOK_TOOL_NAME is about to run"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "write_file",
        "command": "python scripts/count_lines.py"
      }
    ],
    "SessionStart": [
      {
        "command": "echo Session started at $(date)"
      }
    ]
  }
}

每个钩子定义的字段

字段必需类型说明
matcher否字符串工具名过滤器。"*" 匹配全部，省略则不过滤
command是字符串要执行的命令。通过 subprocess.run 以 shell 方式执行
教学用意：不改 Python 代码，只改一个 JSON 配置文件，就能往 Agent 流程里插入任意行为。 这体现的就是"扩展而不修改"的思想。

14 Handler vs Hook 对比

核心区别：Handler 是给大模型用的"手和脚"；Hook 是给管理员用的"监视器和过滤器"。
维度工具 Handler（TOOL_HANDLERS）钩子（HookManager）
谁发起大模型你（通过 .hooks.json 配置）
执行时机大模型调用时才执行每次工具调用之前/之后自动触发
能否阻止工具？本身就是工具，不能阻止自己可以（退出码 1）
能否修改参数？接收参数并执行可以（JSON stdout 的 updatedInput）
能否注入消息？只能返回执行结果可以（退出码 2 或 JSON 的 additionalContext）
定义在哪里？Python 代码的 TOOL_HANDLERS 字典.hooks.json 配置文件
修改方式改 Python 代码，重启程序改 JSON 文件，即时生效

一个对比场景

假设你想"禁止 AI 删除文件"：

方案 A：改 Handler（改 Python 代码）

def run_bash(command):
    dangerous = ["rm -rf /", ...]  # 写在代码里，改规则要改代码
    if any(d in command for d in dangerous):
        return "Error: Dangerous command blocked"

方案 B：用钩子（改配置文件）

# .hooks.json 中配置
{
  "hooks": {
    "PreToolUse": [
      {"matcher": "bash", "command": "python check_dangerous.py"}
    ]
  }
}

# check_dangerous.py 完全是一个独立的外部脚本，用任何语言写都行
两者各司其职：Handler 提供能力，Hook 控制能力的使用方式。 把 Handler 搬到 Hook 里 = 砍掉了大模型的手臂；只在 Handler 里做限制 = 每次改规则都得改代码。 两者并存才是完整的设计。

17 为什么 tool_result 用 role:user

一句话：不是因为"用户说了这句话"，而是因为 Anthropic Messages API 只有 user 和 assistant 两种角色，没有专门的 tool 角色。

API 的消息格式

messages = [
  {"role": "user",      "content": "帮我看看这个目录"},
  {"role": "assistant", "content": [
    {"type": "text", "text": "好的"},
    {"type": "tool_use", "id": "toolu_abc123", "name": "bash", ...},
  ]},
  {"role": "user",      "content": [
    {"type": "tool_result", "tool_use_id": "toolu_abc123", "content": "file1.txt"},
  ]},
]
角色包含的内容
assistantAI 说的话 + AI 发起的工具调用（type: "tool_use"）
user用户说的话 + 工具执行结果（type: "tool_result"）

配对的真正机制

配对的不是 role，而是 tool_use_id。 assistant 消息里: tool_use { id: "toolu_abc123", name: "bash", input: {...} } ↑ id ┃ ┃ 配对依据 ┃ user 消息里: tool_result { tool_use_id: "toolu_abc123", content: "..." } ↑ tool_use_id 指向同一个 id

API 内部做的：

  1. 扫描 assistant 角色的消息，找到所有 type: "tool_use" 的 block，拿到它们的 id
  2. 扫描后续 user 角色的消息，找到所有 type: "tool_result" 的 block，拿到它们的 tool_use_id
  3. 通过 id == tool_use_id 来配对
理解方式：role: "user" 是"放回执的篮子"， tool_use_id 是"回执上写的订单号"， API 通过订单号找到对应的订单，而不是通过篮子。
