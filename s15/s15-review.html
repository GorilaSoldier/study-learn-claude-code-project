1 章节主旨

核心一句话：一个 Agent 搞不定整个系统——让 Lead 召唤队友，队友在后台线程独立工作，通过文件邮箱异步通信。

解决了什么问题："重构整个后端"涉及认证模块、数据库层、API 路由、测试。一个 Agent 在修 API 路由时，认证模块的细节已经不在上下文里了。上下文窗口就那么大，单个 Agent 的注意力覆盖不了所有模块。

s06 的子 Agent vs s15 的队友：

维度s06 子 Agents15 队友
生命周期一次性，用完销毁多轮（教学版限 10 轮，真实 CC 用 idle loop）
通信只回传结论异步收件箱，随时通信
上下文完全隔离通过消息共享信息
数量一个主 Agent + 偶尔子 Agent一个 Lead + 多个队友
最核心的设计思想：团队 = 邮箱。每个 Agent 有自己的收件箱文件，不需要共享内存来协调。

2 最小心智模型

1. 文件邮箱 (MessageBus) — 每个 Agent 一个 .jsonl 收件箱文件 2. 队友线程 (spawn_teammate_thread) — Lead 召唤队友在后台独立运行 3. 收件箱注入 — Lead 自动检查收件箱，队友消息注入到对话历史

它们的关系：spawn_teammate → 创建后台线程 → 队友独立调 LLM → 完成后 BUS.send() 发结果 → run_check_inbox / 主循环自动注入 → Lead 的 LLM 看到队友消息。

一句话串联全流程：Lead 招人 → 队友后台干活 → 干完发邮件 → Lead 查收件箱 → 看到结果。

4 MessageBus 文件消息总线

代码位置：L608-L586

核心设计：每个 Agent 有一个 .jsonl 邮箱文件。发消息 = 往对方的文件 append 一行 JSON；读消息 = 读文件内容 + 删除文件（消费式）。

4.1 .json vs .jsonl 格式

对比项.json（传统 JSON）.jsonl（JSON Lines）
格式一个文件包含一个 JSON 对象/数组每行一个独立的 JSON 对象
样子[{"a":1},{"a":2}]{"a":1}\n{"a":2}\n
追加新数据必须读→解析→追加→写回直接 f.write(...) 追加一行
内存占用大文件一次性全读可以逐行处理
为什么选 .jsonl？消息是持续追加的，每次发消息都读写整个文件不可接受。.jsonl 追加是 O(1) 操作。

4.2 send 方法

def send(self, from_agent: str, to_agent: str,
          content: str, msg_type: str = "message"):
    msg = {"from": from_agent, "to": to_agent,
           "content": content, "type": msg_type,
           "ts": time.time()}
    inbox = MAILBOX_DIR / f"{to_agent}.jsonl"
    with open(inbox, "a") as f:
        f.write(json.dumps(msg) + "\n")
参数含义示例
from_agent发送者名字"lead", "Bob"
to_agent接收者名字（邮箱文件名）"Bob" → Bob.jsonl
content消息正文"查一下磁盘"
msg_type消息类型（默认 "message"）"result", "message"

4.3 read_inbox 方法

def read_inbox(self, agent: str) -> list[dict]:
    inbox = MAILBOX_DIR / f"{agent}.jsonl"
    if not inbox.exists():
        return []
    msgs = [json.loads(line) for line in inbox.read_text().splitlines()
                       if line.strip()]
    inbox.unlink()    # 消费式读取：读完删除
    return msgs

拆解列表推导式：

Step代码结果
1inbox.read_text()整个文件 → 字符串
2.splitlines()按换行拆成行列表
3if line.strip()过滤空行
4json.loads(line)每行 JSON → Python 字典
5inbox.unlink()删除文件（不可恢复）
为什么 unlink（读完就删）？消息 = 队列，每读一次就是 pop 所有消息。不需要日志/保留，下次再读就是新文件。

5.2 嵌套函数 run() 的作用域（闭包）

def spawn_teammate_thread(name, role, prompt):
    system = f"You are '{name}'..."

    def run():                              # 嵌套函数
        messages = [{"role": "user", "content": prompt}]  # 访问外层 prompt
        BUS.send(name, "lead", summary)      # 访问外层 name + 全局 BUS
        result = client.messages.create(...) # 访问全局 client

run() 能访问三个层级：全局变量（BUS, client, run_bash, json 等）+ 外层函数局部变量（name, system, prompt）+ 自己的局部变量（messages, inbox 等）。

5.4 工具查表机制

sub_handlers = {
    "bash": run_bash,         # 字符串 "bash" → 函数 run_bash
    "read_file": run_read,    # 字符串 "read_file" → 函数 run_read
    "write_file": run_write,  # 字符串 "write_file" → 函数 run_write
    "send_message": lambda to, content: (BUS.send(name, to, content), "Sent")[1],
}

LLM 返回 block.name = "bash", block.input = {"command": "ls"} → sub_handlers.get("bash") 找到 run_bash → run_bash(**{"command": "ls"}) 等价于 run_bash(command="ls")。

lambda 技巧拆解：(BUS.send(name, to, content), "Sent")[1] —— 先执行 send() 获取副作用（写文件），然后取元组第二个元素返回 "Sent"。因为 send() 返回 None，不能直接给 LLM 看。

5.5 收尾：提取最后一段文本

summary = "Done."
for msg in reversed(messages):                   # 从最新消息往前
    if msg["role"] == "assistant" and isinstance(msg["content"], list):
        for b in msg["content"]:
            if getattr(b, "type", None) == "text":  # 找到 text block

                break
BUS.send(name, "lead", summary, "result")     # 发总结给 Lead

response.content 的 block 有两种类型："text"（LLM 说的话）和 "tool_use"（调用的工具）。"tool_result" 不在 response 中，是代码执行后构造并塞入 messages 的。

6.3 run_check_inbox

def run_check_inbox() -> str:
    msgs = BUS.read_inbox("lead")
    if not msgs:
        return "(inbox empty)"
    lines = []
    for m in msgs:
        lines.append(f" [{m['from']} {m['content'][:200]}]")
    return "\n".join(lines)

返回格式举例：[Bob 清理完成，释放了 2GB 空间]。LLM 看到这个字符串，就知道队友干了什么。

9 常见困惑与 FAQ

Q: .json 和 .jsonl 有什么区别？

.json 一个文件一个对象/数组。.jsonl 每行一个独立 JSON 对象，适合追加写入（O(1)）。消息是持续追加的，所以用 .jsonl。

Q: unlink 是什么意思？

删除文件。Unix 术语："文件名是指向硬盘数据的链接，删除文件就是断开这个链接"。Path.unlink() = os.remove()。

Q: json.loads 是把 JSON 转成字典吗？

不只是字典。它把 JSON 格式字符串转成对应的 Python 对象——可能是字典、列表、字符串、数字、None、布尔值，取决于 JSON 内容。

Q: read_inbox 是一次性全读出来吗？

是的。read_text() 一次读完整个文件，逐行解析，然后 unlink 删除文件。下次再读文件不存在，返回空列表。

Q: run() 能访问哪些变量（闭包作用域）？

三层：全局变量（BUS, client, run_bash 等）+ 外层函数局部变量（name, system, prompt）+ 自己的局部变量（messages, inbox 等）。

Q: "bash" 怎么和 run_bash 对应上？

通过 sub_handlers 字典查表。sub_handlers.get("bash") 找到 run_bash 函数对象，然后 handler(**block.input) 调用它。这是"命令模式"的简单实现。

Q: handler(**block.input) 为什么能直接调函数？

**dict 把字典的 key-value 展开为关键字参数。例如 block.input = {"command": "ls"} → 实际调用 run_bash(command="ls")。

Q: response.content 里的 block 有哪些类型？

response.content 中的 block："text"（LLM 说的话）和 "tool_use"（LLM 要调用的工具）。"tool_result" 不在 response 中，是代码执行工具后构造并塞入 messages 的。

Q: content 和 messages 是什么关系？

messages 是完整的对话历史（列表）。content 是其中一条消息的内容（可以是字符串或列表）。messages[-20:] 是取最近 20 条消息。

Q: 工具调用的循环流程是怎样的？

LLM 返回 text + tool_use → 执行工具 → 构造 tool_result → 注入 messages → 再调 LLM → 直到 LLM 返回纯文本（end_turn）→ 跳出循环。

Q: 提取最后一个 text 的原因？

最后一段文本是队友做完所有事情后的最终总结，最有信息量。把这段发给 Lead 汇报。

Q: run_check_inbox 和主循环自动注入不是重复吗？

不是重复，是两条互补路径。路径 A（check_inbox 工具）让 LLM 在工具循环中主动查询；路径 B（主循环自动注入）是安全网，防止 LLM 忘记查 inbox 导致队友消息永久丢失。因为 read_inbox 是"读+删"操作，谁先读谁消费，不会冲突。

Q: 队友线程和主线程是并行的吗？

Python 多线程受 GIL 限制不能并行 CPU 计算，但队友主要做 IO 密集任务（调 LLM API、读写文件）。一个线程等 API 响应时，另一个线程可以执行，所以实际上是并发的。

Q: 为什么工具处理器要包装一层（适配器模式）？

因为底层函数（如 BUS.send）的接口和工具调度系统 execute_tool 的接口不匹配——BUS.send 需要 from_agent 参数且返回 None，而工具只能从 block.input 得到 {to, content} 且需要返回字符串。包装函数补上了缺失的参数，调整了返回值。
